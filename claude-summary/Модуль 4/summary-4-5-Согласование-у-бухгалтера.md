# Модуль 4, Урок 8: Создание бизнес-процесса — Согласование у бухгалтера

## О чём этот урок

Урок посвящён построению многоуровневого бизнес-процесса согласования заявок в Bitrix24 «с нуля». На примере согласования у бухгалтера разбирается ключевая архитектурная проблема дублирования действий и способ её решения через управляющую переменную типа «Да/Нет». Это фундаментальный паттерн проектирования бизнес-процессов — понимание его позволит строить более читаемые, масштабируемые и поддерживаемые схемы.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Ветка бизнес-процесса** | Путь выполнения процесса после условия (Да или Нет) |
| **Переменная типа Да/Нет** | Логическая переменная (boolean), хранящая состояние True/False внутри процесса |
| **Управляющая переменная** | Переменная, значение которой определяет, по какой ветке пойдёт выполнение в финальном условии |
| **Дублирование действий** | Антипаттерн: одно и то же действие прописано в нескольких ветках — ведёт к проблемам при поддержке |
| **Константа** | Фиксированное значение (например, порог 15 000 руб.), которое не меняется в ходе процесса, но удобно держать в одном месте |
| **Условие** | Действие-развилка: разделяет выполнение на две и более ветки в зависимости от значения поля или переменной |
| **Запись в лог** | Действие для отладки: фиксирует в журнале текущий этап выполнения процесса |
| **Установка свойства** | Действие, изменяющее поле документа (например, статус заявки) |
| **Уведомление** | Действие, отправляющее сообщение пользователям портала о результате процесса |

---

## Проблема дублирования веток — почему это плохо

### Описание проблемы

В процессе согласования заявки возникают **две похожие ветки**, каждая из которых завершается одними и теми же действиями:

```
Руководитель ОТКЛОНИЛ → [Изменить статус] [Записать в отчёт] [Уведомить]
        ↕  (параллельно)
Бухгалтер ОТКЛОНИЛ   → [Изменить статус] [Записать в отчёт] [Уведомить]
```

То же касается и веток успеха:
- Сумма < 15 000 → руководитель одобрил → **финал: одобрено**
- Сумма ≥ 15 000 → руководитель одобрил → бухгалтер одобрил → **финал: одобрено**

### Почему дублирование — антипаттерн

1. **Сложность поддержки** — при изменении логики нужно вносить правки в нескольких местах, легко пропустить одно
2. **Сложность чтения** — схема разрастается, становится труднее отследить логику
3. **Риск рассинхронизации** — ветки могут «разъехаться» со временем и начать вести себя по-разному

---

## Решение: управляющая переменная

### Идея

Вместо дублирования финальных действий — вынести их **в одно место** (в конец процесса) и управлять выбором ветки через специальную переменную.

### Архитектура решения

```
НАЧАЛО
  │
  ├─ Установить переменную "Итог" = НЕТ (значение по умолчанию)
  │
  ├─ [Задание: утверждение у Руководителя]
  │       │
  │   ОДОБРИЛ?
  │   ДА ──────────────────────────────────────────────────────┐
  │   НЕТ → переменная остаётся НЕТ                            │
  │                                                            │
  │                                         Установить "Итог" = ДА
  │                                                            │
  │                                         Сумма > 15 000?
  │                                         ДА ────────────────┐
  │                                         НЕТ → "Итог" = ДА (остаётся)
  │                                                            │
  │                                         [Задание: утверждение у Бухгалтера]
  │                                                    │
  │                                               ОДОБРИЛ?
  │                                               ДА → "Итог" = ДА (остаётся)
  │                                               НЕТ → Установить "Итог" = НЕТ
  │
  └─ ФИНАЛЬНОЕ УСЛОВИЕ: переменная "Итог" = ?
          │
     ДА ──┴──► [Статус: Одобрена] [Уведомление об одобрении]
     НЕТ ────► [Статус: Отклонена] [Уведомление об отклонении]
```

### Сколько возможных состояний переменной «Итог»

| Сценарий | Значение «Итог» в финале |
|---|---|
| Руководитель отклонил | НЕТ (по умолчанию) |
| Руководитель одобрил, сумма < 15 000 | ДА |
| Руководитель одобрил, сумма ≥ 15 000, бухгалтер одобрил | ДА |
| Руководитель одобрил, сумма ≥ 15 000, бухгалтер отклонил | НЕТ (сброшено) |

## Пошаговые инструкции

### Шаг 1. Создать управляющую переменную

1. Открыть редактор бизнес-процесса
2. Перейти в раздел **Переменные**
3. Добавить новую переменную:
   - **Название:** например, `Итог_согласования` (или аналогичное понятное имя)
   - **Тип:** `Да/Нет` (boolean)
   - **Значение по умолчанию:** `Нет`
4. Сохранить переменную

### Шаг 2. Установить переменную в НЕТ в начале процесса

1. В самом начале схемы (до первого действия) добавить действие **«Установить переменную»**
2. Выбрать переменную `Итог_согласования`
3. Установить значение = `Нет`

> **Зачем:** гарантируем, что переменная всегда начинает с известного значения, даже если процесс запустился повторно или значение каким-то образом осталось от предыдущего запуска.

### Шаг 3. Установить переменную в ДА после одобрения руководителем

1. Найти ветку **«Руководитель одобрил» (ДА)** после условия утверждения
2. Первым действием в этой ветке добавить **«Установить переменную»**
3. Установить `Итог_согласования` = `Да`

### Шаг 4. Добавить ветку проверки суммы (условие на константу 15 000)

1. После установки переменной в ДА добавить действие **«Условие»**
2. Настроить условие: `Сумма > 15000` (используя константу)
3. Ветка **НЕТ** (сумма ≤ 15 000): переменная остаётся ДА, идём к финалу
4. Ветка **ДА** (сумма > 15 000): добавляем согласование у бухгалтера

### Шаг 5. Добавить задание для бухгалтера

1. В ветке «сумма > 15 000» добавить действие **«Задание»** (или «Запрос одобрения»)
2. Исполнитель: бухгалтер (на этапе тестирования — себя, чтобы не создавать отдельного пользователя)
3. Настроить варианты ответа: **Одобрить / Отклонить**

### Шаг 6. Сбросить переменную в НЕТ при отклонении бухгалтером

1. В ветке **«Бухгалтер отклонил» (НЕТ)** добавить **«Установить переменную»**
2. Установить `Итог_согласования` = `Нет`

> **Логика:** бухгалтер «откатывает» положительное решение руководителя.

### Шаг 7. Создать финальное условие

1. После того как все ветки слились обратно, добавить итоговое **«Условие»**
2. Проверяемое значение: переменная `Итог_согласования`
3. **Ветка ДА:**
   - Установить статус документа = `Одобрена`
   - Уведомить пользователя об одобрении
   - Запись в отчёт/лог
4. **Ветка НЕТ:**
   - Установить статус документа = `Отклонена`
   - Уведомить пользователя об отклонении
   - Запись в отчёт/лог (с детализацией: кто именно отклонил)

### Шаг 8. Добавить записи в лог для отладки

В ключевых точках схемы добавить действие **«Запись в журнал»** с понятными сообщениями:
- `"Процесс начат, Итог = НЕТ"`
- `"Руководитель одобрил, Итог = ДА"`
- `"Сумма > 15000, отправляем на согласование бухгалтеру"`
- `"Бухгалтер отклонил, Итог сброшен в НЕТ"`
- `"Финальное условие: Итог = [значение переменной]"`

### Шаг 9. Протестировать схему

1. Сохранить бизнес-процесс
2. Временно назначить **себя бухгалтером** (для удобства тестирования без создания новых пользователей)
3. Создать тестовые заявки для каждого из 4 сценариев (см. таблицу выше)
4. Проверить, что статусы проставляются корректно
5. Просмотреть лог для диагностики возможных ошибок

## Детали реализации: что куда переносим

### Финальный блок (один для всех исходов)

Вместо дублирования следующие действия размещаются **один раз** в конце процесса:

- Установка свойства документа (статус: Одобрена/Отклонена)
- Запись в отчёт
- Уведомление пользователей

### Промежуточные записи в лог (остаются в ветках)

Детализирующие записи — **кто именно** одобрил или отклонил — остаются в соответствующих ветках, чтобы лог был информативным:
- «Руководитель отклонил заявку»
- «Бухгалтер отклонил заявку»
- «Заявка одобрена без согласования с бухгалтером (сумма < 15 000)»

---

## О роли константы для «бухгалтера»

Бухгалтер задаётся через **константу** (а не прямым указанием пользователя), потому что:

- Бухгалтер — это роль, а не конкретный человек навсегда
- При смене сотрудника достаточно поменять значение константы в одном месте
- Это предотвращает ситуацию, когда задания уходят уволенному или переведённому сотруднику

---

## Главное

1. **Дублирование действий в ветках — антипаттерн.** Если одни и те же действия встречаются в нескольких ветках, схема становится хрупкой и трудной для поддержки. Всегда ищи способ вынести общую логику в одно место.

2. **Управляющая переменная типа Да/Нет** — стандартный инструмент для схлопывания нескольких веток в одну финальную развилку. Она «несёт» результат сквозь всю схему.

3. **Значение переменной по умолчанию устанавливается явно в начале процесса** — это защита от неожиданного поведения при повторных запусках или граничных случаях.

4. **Сброс переменной возможен в любой точке процесса** — если последующий шаг отменяет предыдущее положительное решение, переменная устанавливается обратно в НЕТ.

5. **Лог — обязательный инструмент при разработке.** Записи в журнал в ключевых точках позволяют быстро диагностировать ошибки в логике без длительной отладки.

6. **Тестируй все четыре сценария** многоуровневого согласования: два «отклонения» (руководитель, бухгалтер) и два «одобрения» (с бухгалтером и без).

7. **Константа для роли бухгалтера** позволяет менять исполнителя в одном месте — не нужно редактировать весь процесс при кадровых изменениях.

8. **Схема может быть объёмнее, но читабельнее** — увеличение количества блоков ради устранения дублирования оправдано: процесс легче понять и проще расширять (например, добавить цикл согласований).

9. **Временная подмена ролей** (назначить себя бухгалтером при тестировании) — стандартная практика для быстрой проверки процесса без создания тестовых пользователей.

10. **Переменные и константы — ключевые строительные блоки** сложных бизнес-процессов: первые хранят изменяемое состояние, вторые — фиксированные настройки. Умелое их использование определяет качество архитектуры процесса.
