# Запрос данных у пользователя и сохранение в документе

## О чём этот урок

Урок завершает построение цикла согласования заявки: добавляется ветка «отклонено» с реальным поведением — сотрудник получает задание доработать заявку, заполняет новые данные, и они автоматически сохраняются в документе. Вводится возможность «сдаться» — прервать процесс, если сотрудник не хочет продолжать. Разбирается ключевой нюанс: действие «Запрос данных» само по себе не сохраняет введённые значения — их нужно отдельно записывать через «Изменение документа».

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Запрос дополнительной информации** | Действие в конструкторе БП, которое показывает пользователю форму с полями ввода. Само по себе данные никуда не сохраняет — только собирает |
| **Запрос доп. информации с отклонением** | Расширенная версия действия «Запрос данных»: пользователь может заполнить форму (ветка «OK») или отказаться от неё (ветка «Нет»), нажав кнопку отклонения |
| **Прерывание процесса** | Действие в конструкторе БП, которое немедленно завершает выполнение бизнес-процесса |
| **Изменение документа** | Действие, которое обновляет поля записи (заявки) в Bitrix24 новыми значениями |
| **Поля действия** | Поля ввода, которые конфигурируются внутри действия «Запрос данных» и доступны пользователю для заполнения |
| **Дополнительные результаты действия** | Значения, которые действие возвращает после выполнения. Например, действие «Утверждение» возвращает комментарий последнего голосовавшего |
| **Комментарий последнего голосовавшего** | Результат действия «Утверждение у руководителя» — текст, который руководитель оставил при отклонении заявки |

---

## Проблема, которую решает этот урок

На предыдущем уроке был реализован цикл: руководитель одобряет или отклоняет заявку, и при отклонении цикл начинается заново. Но **ветка «отклонено» была пустой** — при отклонении просто ничего не происходило.

**Проблема:** Без обработки ветки «отклонено» цикл бесконечно гоняет заявку к руководителю, не давая сотруднику возможности её доработать. Также возникает тупиковый сценарий: руководитель никогда не согласится, а сотрудник не может выйти из процесса.

**Цель урока:** Наполнить ветку «отклонено» реальной логикой:
1. Дать сотруднику задание доработать заявку (с возможностью отказаться)
2. Сохранить введённые данные в документе
3. Добавить уведомления и записи в лог для информативности

---

## Архитектура ветки «отклонено»

### Сценарий «сдаться»

Если руководитель бесконечно отклоняет заявку, сотрудник должен иметь возможность выйти из цикла. Для этого используется **«Запрос доп. информации с отклонением»** — у него есть кнопка, позволяющая отказаться от доработки.

```
Руководитель отклоняет заявку
         ↓
Запрос доп. информации с отклонением (сотруднику)
    ├── Ветка «OK» (хочу доработать):
    │       → Изменение документа (сохраняем новые данные)
    │       → Следующая итерация цикла (заявка к руководителю)
    │
    └── Ветка «Нет» (хочу сдаться):
            → Прерывание процесса
```

**Почему выбрано «с отклонением», а не обычный «Запрос данных»:**
Обычный запрос данных вынуждает пользователя обязательно заполнить форму. Версия «с отклонением» даёт кнопку выхода — сотрудник может сказать «не буду дорабатывать» и процесс корректно завершится.

---

## Пошаговая инструкция: настройка ветки «отклонено»

### Часть 1 — Добавление «Прерывания процесса» в ветку «Нет»

**Шаг 1.** В ветку «Нет» действия «Запрос доп. информации с отклонением» добавить действие **«Прерывание процесса»**.

**Шаг 2 (опционально).** Перед прерыванием добавить запись в отчёт (лог) с текстом, например: «Сотрудник отказался от доработки заявки».

> Это позволяет в журнале бизнес-процесса видеть, почему процесс завершился — не по ошибке, а осознанно.

---

### Часть 2 — Настройка действия «Запрос доп. информации с отклонением»

**Шаг 1. Добавить действие** в ветку «отклонено» основного цикла.

**Шаг 2. Задать читаемое название**, например: «Доработка заявки сотрудником».

**Шаг 3. Указать исполнителя:**

```
Кто будет работать с заданием → Тот, кто отправил заявку
```

Используется системная переменная «Автор документа» или аналогичная — это сотрудник, создавший заявку.

**Шаг 4. Написать описание задания** — текст, который увидит сотрудник. Сюда рекомендуется передавать **комментарий руководителя при отклонении**:

```
Источник: Дополнительные результаты → [Действие утверждения у руководителя] → Комментарий последнего голосовавшего
```

Так сотрудник сразу видит, почему заявка отклонена и что нужно исправить.

**Шаг 5. Настроить именование кнопок** — задать более понятные названия кнопкам формы (вместо стандартных «OK» / «Отклонить»), например: «Отправить на повторное согласование» / «Отказаться от доработки».

**Шаг 6. Настроить поля ввода:**

Добавить два поля:

| Поле | Тип | Обязательное |
|---|---|---|
| Новая сумма | Число/деньги | Да |
| Новое описание (цели и обоснование) | Текст (многострочный) | Да |

> Обязательность гарантирует, что сотрудник не отправит пустую форму.

**Шаг 7. Сохранить действие.**

---

### Часть 3 — Сохранение введённых данных в документе

> **Критически важный нюанс:** Действие «Запрос доп. информации» только показывает форму и собирает данные в переменные. Само по себе оно **не записывает** эти данные в поля заявки. Нужно сделать это вручную.

**Шаг 1.** После действия «Запрос доп. информации» (в ветке «OK») добавить действие **«Изменение документа»**.

**Шаг 2.** В настройках «Изменения документа» обновить поля заявки:

```
Поле «Сумма» ← значение поля «Новая сумма» из предыдущего действия
Поле «Описание / Цели и обоснование» ← значение поля «Новое описание» из предыдущего действия
```

Поля, введённые пользователем в форме, доступны через **переменные** предыдущего действия — они появляются в списке доступных источников при выборе значения.

**Шаг 3. Сохранить.**

**Итог:** После выполнения этого блока поля заявки обновлены. Когда цикл начнёт следующую итерацию и руководитель откроет заявку — он увидит актуальные данные, как будто это новая заявка.

---

### Часть 4 — Добавление уведомлений и записей в лог

Для информативности процесса рекомендуется добавить:

**Уведомления:**
- Сотруднику — что его заявка отклонена и требует доработки (от руководителя)
- При необходимости — другие уведомления по ходу процесса

**Записи в отчёт (лог):**
- Фиксировать ключевые события: отклонение, доработка, прерывание
- Это помогает разобраться в истории процесса и отладить возможные ошибки

---

## Результат: как это выглядит для пользователя

После настройки процесс работает следующим образом:

1. Сотрудник подаёт заявку → руководитель получает задание на утверждение
2. Руководитель **отклоняет** с комментарием
3. Сотруднику (в данном случае — Ренате) возвращается задание на доработку
4. В тексте задания виден комментарий руководителя, сумма и описание из оригинальной заявки
5. Сотрудник выбирает: **приступить к доработке** (заполняет новую сумму и описание) или **отказаться**
6. При доработке: данные сохраняются в заявке → заявка снова уходит к руководителю
7. Руководитель видит обновлённую заявку (новая сумма, новое описание) и принимает решение
8. При одобрении — процесс идёт дальше (проверка суммы, бухгалтер и т.д.)

**Пример из урока:** После доработки сумма стала меньше 15 000 — заявка не ушла к бухгалтеру, а была сразу согласована руководителем.

---

## Ключевые нюансы и ловушки

| Ситуация | Правило |
|---|---|
| «Запрос данных» не сохраняет данные | После него **обязательно** добавлять «Изменение документа» |
| Нужно показать комментарий руководителя | Брать из «Дополнительных результатов» → «Комментарий последнего голосовавшего» |
| Бесконечный цикл без выхода | Использовать «Запрос доп. информации **с отклонением**» + «Прерывание процесса» в ветке «Нет» |
| Поля из формы недоступны в следующем блоке | Они появляются в **переменных** после выполнения действия — искать в списке источников |
| Обязательность полей | Устанавливать для критических полей, чтобы избежать пустых доработок |

---

## Главное

1. **Действие «Запрос доп. информации с отклонением»** — правильный выбор для сценариев, где пользователь должен либо заполнить форму, либо отказаться. Обычный «Запрос данных» не даёт кнопки выхода.

2. **«Запрос данных» только собирает — не сохраняет.** После него всегда нужно добавлять «Изменение документа», иначе введённые пользователем данные потеряются.

3. **Возможность «сдаться» — обязательная часть архитектуры.** Любой цикл согласования должен иметь выход для пользователя: «Прерывание процесса» в ветке отклонения формы.

4. **Комментарий руководителя передаётся через «Дополнительные результаты»** — это делает задание на доработку информативным: сотрудник сразу видит, что именно нужно исправить.

5. **После сохранения данных заявка выглядит «новой» для руководителя** — он читает обновлённые поля и принимает решение на основе актуальной информации.

6. **Уведомления и логи — не опциональный декор**, а инструмент отладки и коммуникации. Без них сложно понять, на каком этапе процесс и почему он завершился.

7. **Поля формы доступны как переменные** в последующих блоках — их нужно искать в списке источников значений при настройке «Изменения документа».

8. **Проверка суммы (условие «< 15 000») работает корректно** — если после доработки сумма стала меньше порога, заявка не уходит к бухгалтеру и согласуется только руководителем.
