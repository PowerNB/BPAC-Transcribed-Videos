# Права доступа в Bitrix24: Автоматизация бизнес-процессов

## О чём этот урок

Урок посвящён настройке прав доступа к объектам (заявкам) в связке с бизнес-процессом. Разбирается типовой сценарий: сотрудник может создавать заявки, но видит только свои — доступ к конкретной заявке выдаётся динамически самим бизнес-процессом через специальное действие **«Установка прав»**.

---

## Основные понятия

| Термин | Описание |
|---|---|
| **Права доступа** | Разрешения на выполнение операций с объектом (добавление, чтение, изменение, удаление) |
| **Доступ на добавление** | Пользователь может создавать новые записи, но не видит чужие |
| **Доступ на чтение** | Пользователь видит запись, но не может её изменить |
| **Действие «Установка прав»** | Специальное действие в бизнес-процессе Bitrix24, которое динамически назначает права на конкретный документ конкретным пользователям |
| **Статические права** | Права, заданные в настройках раздела — применяются ко всем записям |
| **Динамические права** | Права, выданные действием бизнес-процесса — применяются только к конкретной записи |

---

## Проблема: почему нельзя давать всем права на изменение

- После создания заявки и запуска бизнес-процесса согласования **любой пользователь мог зайти и изменить данные** (например, увеличить сумму уже после одобрения)
- Это нарушает смысл согласования: **данные должны меняться только по регламенту** — через специальные действия бизнес-процесса
- **Исправление:** права на изменение убираются, данные можно менять только через действие бизнес-процесса, а не вручную

> ⚠️ На этапе разработки удобно держать «Всем на изменение», но **перед выкаткой в прод — обязательно настроить реальные права**.

---

## Правильная модель прав доступа

### Базовые (статические) права

| Роль | Уровень доступа | Обоснование |
|---|---|---|
| **Все сотрудники** | Только добавление | Могут создавать заявки, но не видят чужие |
| **Бухгалтер** | Чтение | Должен видеть заявки на согласование, но не изменять их |
| **Руководитель** | Чтение | Одобряет/отклоняет, не редактирует |
| **Администратор** | Полный доступ | По умолчанию, как администратор портала |

> Доступ «только на добавление» означает, что **после создания заявки сотрудник не видит её в списке** — пока бизнес-процесс не выдаст ему права на чтение именно этой записи.

### Динамические права — выдаются бизнес-процессом

- **Автору заявки** — чтобы видел свою заявку после создания
- **Руководителю** — чтобы мог рассмотреть заявку на этапе согласования
- **Бухгалтеру** — когда заявка доходит до этапа согласования с бухгалтером

---

## Действие «Установка прав» в бизнес-процессе

### Ключевые особенности

- Действие вставляется **после определения переменной с исполнителем** — сначала определяем, кому давать права, потом даём
- **Работает точечно** — права выдаются только на тот документ, который участвует в данном конкретном бизнес-процессе, **не на все записи раздела**

### Что настраивается в действии

- **Пользователь/группа** — кому выдать права
- **Уровень доступа** — чтение / изменение / удаление и т.д.

---

## Итоговая архитектура прав в бизнес-процессе

```
[Создание заявки]
       ↓
[БП запускается автоматически]
       ↓
[Установка прав] → Автор получает: чтение
       ↓
[Определение руководителя]
       ↓
[Установка прав] → Руководитель получает: чтение
       ↓
[Задание руководителю: одобрить/отклонить]
       ↓
[Условие: результат согласования]
       ↓
[Установка прав] → Бухгалтер получает: чтение  ← (если одобрено)
       ↓
[Задание бухгалтеру: согласовать]
```

## Пошаговые инструкции

### Шаг 1. Настройка статических прав в разделе

1. Открыть настройки раздела → «Права доступа»
2. Выдать всем сотрудникам права **только на добавление** (убрать чтение и изменение)
3. Бухгалтеру и руководителю выдать права **на чтение**
4. Сохранить настройки

### Шаг 2. Добавление действия «Установка прав» в бизнес-процесс

1. Открыть редактор бизнес-процесса
2. После определения переменной с согласующим лицом добавить действие **«Установка прав»**
3. Указать: автор заявки — права на чтение; руководитель (из переменной) — права на чтение
4. Аналогично добавить «Установку прав» на этапе передачи бухгалтеру
5. Сохранить бизнес-процесс

### Шаг 3. Проверка работы

1. Зайти под учётной записью **обычного сотрудника** (не администратора)
2. Убедиться, что старые записи недоступны *(это нормально — они созданы до изменения прав)*
3. Создать новую заявку
4. Убедиться, что сотрудник **видит только свою заявку**
5. Проверить, что **руководитель видит заявку**
6. Убедиться, что сотрудник **не может изменить данные вручную**
7. Убедиться, что действие бизнес-процесса (запрос данных) **работает корректно**

---

## Главное

1. **Нельзя давать всем права на изменение** — это нарушает смысл согласования. После запуска бизнес-процесса данные заявки должны быть заморожены.
2. **Базовое правило для сотрудников — только «добавление»**. По умолчанию они не видят никаких записей раздела.
3. **Динамическая выдача прав через «Установку прав»** — ключевой инструмент для реализации принципа «вижу только свои заявки».
4. **Действие «Установка прав» работает точечно** — права выдаются только на конкретный документ, а не на весь раздел.
5. **Данные меняются только через действия бизнес-процесса**, а не через ручное редактирование.
6. **Изменение статических прав не затрагивает старые записи** — они становятся недоступны. Это ожидаемое, корректное поведение.
7. **Согласующие лица (руководитель, бухгалтер) получают права на чтение**, а не на изменение — их задача одобрить или отклонить через задание бизнес-процесса.
8. **Место вставки «Установки прав»** — сразу после определения переменной с исполнителем, до постановки задания этому исполнителю.
9. **Администратор портала видит всё** независимо от настроек — при тестировании нужно проверять под обычными пользователями.
10. **Связка «статические права + динамическая установка прав через БП»** покрывает большинство типовых сценариев управления доступом к данным.
