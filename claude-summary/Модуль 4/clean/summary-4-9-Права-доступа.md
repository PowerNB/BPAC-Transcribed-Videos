# Права доступа

## О чём этот урок

Урок посвящён настройке прав доступа к объектам (заявкам) в связке с бизнес-процессом в Bitrix24. Разбирается типовой сценарий: сотрудник может создавать заявки, но видит **только свои** — доступ к конкретной заявке выдаётся динамически самим бизнес-процессом через действие **«Установка прав»**. Это последний и обязательный шаг к полноценному бизнес-процессу согласования заявок.

---

## Основные понятия

| Термин | Описание |
|---|---|
| **Права доступа** | Разрешения на выполнение операций с объектом (добавление, чтение, изменение, удаление) |
| **Доступ на добавление** | Пользователь может создавать новые записи, но не видит чужие |
| **Доступ на чтение** | Пользователь видит запись, но не может её изменить |
| **Действие «Установка прав»** | Специальное действие в бизнес-процессе Bitrix24, которое динамически назначает права на конкретный документ конкретным пользователям |
| **Документ** | В терминологии бизнес-процессов Bitrix24 — та самая запись/заявка, по которой запущен процесс |
| **Статические права** | Права, заданные в настройках раздела — применяются ко всем записям |
| **Динамические права** | Права, выданные действием бизнес-процесса — применяются только к конкретной записи |

---

## Проблема: почему нельзя давать всем доступ на изменение

По умолчанию в демонстрационных целях выдаётся доступ «всем на изменение». Это **неправильно** по следующим причинам:

- После создания заявки и запуска бизнес-процесса **любой пользователь мог зайти и изменить данные** (например, увеличить сумму уже после одобрения)
- Это нарушает смысл согласования: данные должны меняться **только по регламенту** — через специальные действия бизнес-процесса
- **Исправление:** права на изменение убираются; данные можно менять только через действие бизнес-процесса (например, «Запрос данных у пользователя»)

> ⚠️ На этапе разработки удобно держать «Всем на изменение», но перед выкаткой в прод — **обязательно настроить реальные права**.

## Правильная модель прав доступа

### Базовые (статические) права — задаются в настройках раздела

| Роль | Уровень доступа | Обоснование |
|---|---|---|
| **Все сотрудники** | Только **добавление** | Могут создавать заявки, но не видят чужие |
| **Бухгалтер** | **Чтение** | Должен видеть заявки на согласование, но не изменять их |
| **Руководитель** | **Чтение** | Одобряет/отклоняет, но не редактирует напрямую |
| **Администратор** | Полный доступ | По умолчанию, как администратор портала |

> **Важно:** Доступ «только на добавление» означает, что после создания заявки сотрудник **не видит её в списке** — пока бизнес-процесс не выдаст ему права на чтение именно этой записи.

### Динамические права — выдаются бизнес-процессом

Бизнес-процесс сразу после запуска через действие **«Установка прав»** выдаёт нужным пользователям права на чтение конкретной заявки:

- **Автору заявки** — чтобы видел свою заявку
- **Руководителю** — чтобы мог её рассмотреть
- **Бухгалтеру** — когда заявка доходит до этапа согласования с бухгалтером

---

## Действие «Установка прав» в бизнес-процессе

### Где находится
В редакторе бизнес-процесса среди доступных действий — специальное действие **«Установка прав»**.

### Когда добавляется в процесс
Действие вставляется **после определения переменной с исполнителем** (после того как бизнес-процесс определил, кто будет согласовывать). Логика: сначала определяем, кому давать права — потом даём.

### Что настраивается
- **Пользователь/группа** — кому выдать права (автор заявки, руководитель, бухгалтер)
- **Уровень доступа** — чтение / изменение / удаление и т.д.

### Ключевая особенность
> Действие «Установка прав» выдаёт права **только на тот документ, который участвует в данном конкретном бизнес-процессе** — не на все записи раздела.

Это обеспечивает принцип: **«вижу только свои заявки»**.

## Пошаговые инструкции

### Шаг 1. Настройка статических прав в разделе

1. Открыть настройки раздела (элемента Живой ленты / смарт-процесса)
2. Перейти в раздел **«Права доступа»**
3. Выдать всем сотрудникам права **только на добавление** (убрать чтение и изменение)
4. Бухгалтеру и руководителю выдать права на **чтение**
5. Сохранить настройки

### Шаг 2. Добавление действия «Установка прав» в бизнес-процесс

1. Открыть редактор бизнес-процесса
2. Найти место **после определения переменной** с согласующим лицом
3. Добавить действие **«Установка прав»**
4. Указать пользователей и уровни доступа:
   - Автор заявки → права на **чтение**
   - Руководитель (из переменной) → права на **чтение**
5. Аналогично добавить «Установку прав» на этапе передачи бухгалтеру:
   - Бухгалтер → права на **чтение**
6. Сохранить бизнес-процесс

### Шаг 3. Проверка работы

1. Зайти под учётной записью обычного сотрудника (например, Рената)
2. Убедиться, что **старые записи недоступны** (это нормально — они были созданы до изменения прав)
3. Создать **новую заявку**
4. Убедиться, что сотрудник **видит только свою заявку**
5. Проверить, что **руководитель видит заявку** (бизнес-процесс выдал ему права)
6. Убедиться, что сотрудник **не может изменить** данные вручную (только чтение)
7. Убедиться, что **действие бизнес-процесса** «Запрос данных у пользователя» по-прежнему работает корректно

## Поведение системы после настройки

| Ситуация | Результат |
|---|---|
| Сотрудник создаёт заявку | БП запускается, выдаёт сотруднику права на чтение этой заявки |
| Сотрудник открывает список заявок | Видит только свои (те, по которым БП выдал ему доступ) |
| Руководитель открывает список | Видит все заявки, направленные ему на согласование |
| Бухгалтер открывает список | Видит заявки, дошедшие до его этапа согласования |
| Сотрудник пытается изменить заявку вручную | Невозможно — только права на чтение |
| БП запрашивает новые данные у сотрудника | Работает корректно — через механизм действий БП, не через ручное редактирование |
| Записи, созданные до изменения прав | Недоступны (статические права изменились) — ожидаемое поведение |

---

## Итоговая архитектура прав в бизнес-процессе

```
[Создание заявки]
       ↓
[БП запускается автоматически]
       ↓
[Установка прав] → Автор получает: чтение
       ↓
[Определение руководителя]
       ↓
[Установка прав] → Руководитель получает: чтение
       ↓
[Задание руководителю: одобрить/отклонить]
       ↓
[Условие: результат согласования]
       ↓
[Установка прав] → Бухгалтер получает: чтение  ← (если одобрено)
       ↓
[Задание бухгалтеру: согласовать]
```

## Главное

1. **Нельзя давать всем права на изменение** — это нарушает смысл согласования. После запуска БП данные заявки должны быть заморожены.

2. **Базовое правило для сотрудников — только «добавление»**: по умолчанию они не видят никаких записей раздела.

3. **Динамическая выдача прав через «Установку прав»** — ключевой инструмент для реализации принципа «вижу только свои заявки».

4. **Действие «Установка прав» работает точечно** — права выдаются только на конкретный документ в рамках текущего экземпляра бизнес-процесса, а не на весь раздел.

5. **Данные меняются только через действия бизнес-процесса** (например, «Запрос данных у пользователя»), а не через ручное редактирование — это и есть «управление по регламенту».

6. **Изменение статических прав делает старые записи недоступными** — записи, созданные до изменения прав, не будут видны. Это ожидаемое, корректное поведение.

7. **Согласующие лица (руководитель, бухгалтер) получают права на чтение**, а не на изменение — их задача одобрить или отклонить через задание БП, а не редактировать документ напрямую.

8. **Место вставки «Установки прав»** — сразу после определения переменной с исполнителем, до постановки задания этому исполнителю.

9. **Администратор портала видит всё** независимо от настроек — при тестировании нужно проверять под учётными записями обычных пользователей.

10. **Связка «статические права + динамическая установка прав через БП»** покрывает большинство типовых сценариев управления доступом к данным в Bitrix24.
