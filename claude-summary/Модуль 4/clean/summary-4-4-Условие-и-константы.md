# Условие и константы

## О чём этот урок

Урок посвящён усложнению схемы бизнес-процесса в Bitrix24: добавлению блока условной маршрутизации с действием **«Условие»** и введению нового типа параметров — **констант**. На практике разбирается, как разветвить логику процесса в зависимости от суммы заявки и как правильно хранить «фиксированных» участников процесса (например, главного бухгалтера).

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Условие** | Действие в бизнес-процессе, которое проверяет заданные критерии и направляет выполнение по одной из нескольких веток |
| **Ветка условия** | Отдельный путь выполнения бизнес-процесса, по которому процесс идёт при выполнении соответствующего критерия |
| **Константа** | Параметр шаблона БП с фиксированным значением, которое задаётся один раз и используется повторно во всех запускаемых экземплярах процесса |
| **Переменная** | Параметр процесса, значение которого меняется в ходе выполнения (в отличие от константы) |
| **Динамическое определение** | Способ задания участника процесса «на лету» — например, руководитель определяется по автору заявки |
| **Согласование у бухгалтера** | Дополнительный этап утверждения заявки, подключаемый при выполнении условия (сумма > 15 000 ₽) |

---

## Действие «Условие» — детальный разбор

### Назначение

Действие «Условие» создаёт **развилку** в бизнес-процессе:
- Проверяет заданное выражение (например, `Сумма > 15000`)
- В зависимости от результата выполняется **ветка «Да»** или **ветка «Нет»**
- Условий может быть несколько (elseif), а также ветка «Иначе» по умолчанию

### Ключевые особенности

1. **Несколько веток** — позволяет создавать не только 2, но и 3, 4 и более путей выполнения
2. **Проверка слева направо** — ветки проверяются строго по порядку, от левой к правой; это критически важно при проектировании логики
3. **Обязательная «страховочная» ветка** — классическая практика: **правая ветка всегда содержит условие «Истина»** (всегда выполняется), чтобы бизнес-процесс гарантированно прошёл через условие и не завис

### Правило проектирования условий (классика жанра)

```
Левая ветка  →  конкретное условие (например, сумма > 15 000)
Правая ветка →  Истина (всегда True — «иначе»)
```

> ⚠️ Это гарантирует, что хотя бы одна ветка сработает при любых данных.

### Где ставится условие в схеме

Блок **«Условие»** добавляется **после** того, как руководитель одобрил заявку. Согласование у бухгалтера — это не параллельный, а **последовательный** этап, который подключается только при необходимости.

## Логика расширенной схемы бизнес-процесса

### Общая структура после добавления условия

```
[Утверждение у руководителя]
              ↓
         [Условие]
        /          \
(сумма > 15 000)  (Истина — всегда)
        ↓                  ↓
[Согласование        [Завершение /
 у бухгалтера]        следующий шаг]
```

### Настройка условия для согласования с бухгалтером

| Параметр | Значение |
|---|---|
| Критерий | Поле «Сумма» заявки > 15 000 рублей |
| Левая ветка | Переходим к блоку согласования у бухгалтера |
| Правая ветка | Пропускаем бухгалтера, идём дальше |

## Константы — зачем и когда использовать

### Константа vs Переменная

| | Константа | Переменная |
|---|---|---|
| **Значение** | Задаётся один раз | Может меняться в ходе БП |
| **Использование** | Параметры, которые редко меняются | Промежуточные результаты, флаги |
| **Пример** | ФИО/ID главного бухгалтера | Флаг «нужно согласование бухгалтера» |
| **Как задаётся** | Один раз в настройках шаблона | Динамически в ходе выполнения |

### Проблема: бухгалтер vs руководитель

| Участник | Как определяется | Инструмент |
|---|---|---|
| **Руководитель** | Динамически — по автору заявки (у каждого сотрудника свой руководитель) | Переменная |
| **Бухгалтер (главбух)** | Статически — один конкретный человек для всей компании | Константа |

### Почему бухгалтер — константа

- Должность «главный бухгалтер» в компании одна; конкретный человек меняется редко
- Удобнее изменить значение константы в **одном месте** шаблона, чем искать все упоминания в действиях
- В отличие от руководителя, у бухгалтера нет прямой организационной связи с инициатором — его нельзя определить через профиль пользователя
- Это предотвращает ситуацию, когда задания уходят уволенному или переведённому сотруднику

### Преимущества константы

- Значение задаётся **один раз** в настройках шаблона
- Используется **во всех запускаемых экземплярах** процесса автоматически
- При смене главбуха достаточно **изменить константу один раз** — все будущие запуски подхватят новое значение
- Не нужно вручную прописывать конкретного пользователя в каждое действие

### Альтернативный (неудобный) способ — почему не рекомендуется

Можно войти в организационную структуру → найти бухгалтерию → выбрать главного бухгалтера → указать его напрямую в настройке действия. Но это **жёсткая привязка**: при смене сотрудника придётся редактировать каждое действие вручную.

## Пошаговые инструкции

### Шаг 1. Добавить блок «Условие» в схему

1. Открыть редактор бизнес-процесса
2. Найти место **после блока «Утверждение у руководителя»**
3. Добавить действие **«Условие»** между блоком руководителя и следующим шагом
4. Убедиться, что условие стоит именно **после одобрения руководителя** (не параллельно)

### Шаг 2. Настроить ветки условия

1. В блоке «Условие» настроить **левую ветку**:
   - Поле: `Сумма`
   - Оператор: `больше`
   - Значение: `15000`
   - В шаблоне: `{=Document:FIELD_SUMMA} > 15000`
2. В **правой ветке** установить условие **«Истина»** (всегда выполняется)
3. Сохранить настройки условия

### Шаг 3. Создать константу для бухгалтера

1. Перейти в **«Параметры шаблона»**
2. Открыть раздел **«Константы»**
3. Нажать **«Добавить константу»**
4. Задать имя константы: например, `BUHGALTER` или `Главный бухгалтер`
5. Указать тип: **Пользователь**
6. Выбрать значение — конкретный пользователь (главный бухгалтер) из списка сотрудников
7. Сохранить константу

### Шаг 4. Использовать константу в блоке согласования

1. Добавить блок **«Задание»** (согласование) в **левую ветку** условия
2. В поле «Исполнитель» / «Кому направить» выбрать не пользователя напрямую, а созданную **константу** — обращение через `{=Constant:BUHGALTER}`
3. Настроить варианты ответа: **Утвердить / Отклонить**
4. Добавить уведомления пользователям по результату
5. Сохранить

## Типичные ошибки и как их избежать

### Ошибка 1: Неправильный порядок веток
> ⛔ Если поставить «Истина» **слева** — она сработает первой, и процесс никогда не дойдёт до правой ветки с реальным условием.
>
> ✅ Всегда: **конкретное условие — слева**, **«Истина» — справа**.

### Ошибка 2: Неверное поле в условии
> ⛔ Самая частая ловушка — легко промахнуться и выбрать `ID элемента` вместо нужного поля (например, `Сумма`).
>
> ✅ Если условие «не срабатывает» — **первым делом проверяй, то ли поле выбрано**.
>
> 🔍 Симптом: лог показывает одно, а реальные данные — другое (например, лог пишет «сумма < 15 000», хотя реальная сумма > 20 000).

### Ошибка 3: Прямое указание пользователя вместо константы
> ⛔ Жёсткая привязка конкретного сотрудника в каждом действии означает ручное редактирование при любой кадровой перестановке.
>
> ✅ Используй константу — достаточно одного изменения для обновления всего процесса.

## Дополнительные замечания

- **Согласование у бухгалтера — дополнительный уровень**: если бухгалтер отклонил заявку, решение руководителя теряет силу
- **Переменная-флаг управляет ветками**: вместо дублирования условий меняй значение переменной и используй её в одном месте для принятия решения о направлении процесса
- **Руководителя определяй динамически** через организационную структуру, а не хардкодом — БП останется рабочим при смене людей
- **После настройки условия** необходимо также добавить уведомления пользователям по итогам работы бухгалтерского согласования

## Главное

1. **Действие «Условие»** создаёт развилку в бизнес-процессе и поддерживает любое количество веток — не только два пути
2. **Порядок проверки — строго слева направо**: первой всегда проверяется левая ветка; это определяет всю логику маршрутизации
3. **Правая ветка = «Истина»** — обязательный паттерн, гарантирующий, что процесс не зависнет на условии при любых входных данных
4. **Константа** — инструмент для участников с заранее известным, редко меняющимся значением (главбух, юрист компании и т.п.); задаётся один раз и применяется во всех экземплярах процесса
5. **Переменная** — для участников и данных, определяемых динамически в момент запуска (руководитель автора заявки, промежуточные флаги)
6. **Смена константы один раз** автоматически распространяется на все будущие запуски — это принципиально удобнее, чем редактировать каждое действие вручную
7. **Бухгалтер подключается только при сумме > 15 000 ₽** — пример условной маршрутизации в реальном бизнес-сценарии; блок ставится последовательно после руководителя, а не параллельно
8. **Согласование у бухгалтера по структуре аналогично согласованию у руководителя**, но исполнитель определяется через константу (`{=Constant:BUHGALTER}`), а не динамически
9. **Самая частая ошибка в условии** — выбор неверного поля (например, ID вместо суммы); симптом — лог противоречит реальным данным; решение — перепроверить выбранное поле
10. **Переменные и константы — ключевые строительные блоки** сложных бизнес-процессов: умелое их использование определяет качество архитектуры и удобство сопровождения процесса
