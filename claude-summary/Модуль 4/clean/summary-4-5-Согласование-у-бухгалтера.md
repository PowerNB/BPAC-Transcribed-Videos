# Согласование у бухгалтера

## О чём этот урок

Урок посвящён построению многоуровневого бизнес-процесса согласования заявок в Bitrix24. Разбирается добавление этапа согласования у бухгалтера с использованием действия **«Условие»** и нового типа параметров — **констант**. Ключевая архитектурная проблема — дублирование действий в ветках — решается через **управляющую переменную типа Да/Нет**. Это фундаментальный паттерн проектирования бизнес-процессов.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Условие** | Действие-развилка, которое проверяет заданные критерии и направляет выполнение по одной из нескольких веток |
| **Ветка условия** | Отдельный путь выполнения бизнес-процесса при выполнении соответствующего критерия |
| **Константа** | Параметр шаблона с фиксированным значением; задаётся один раз, используется во всех экземплярах процесса |
| **Переменная** | Параметр процесса, значение которого может меняться в ходе выполнения |
| **Переменная типа Да/Нет** | Логическая переменная (boolean), хранящая состояние True/False внутри процесса |
| **Управляющая переменная** | Переменная, значение которой определяет, по какой ветке пойдёт выполнение в финальном условии |
| **Динамическое определение** | Способ задания участника «на лету» — например, руководитель определяется по автору заявки |
| **Дублирование действий** | Антипаттерн: одно и то же действие прописано в нескольких ветках — ведёт к проблемам при поддержке |
| **Запись в лог** | Действие для отладки: фиксирует в журнале текущий этап выполнения процесса |
| **Установка свойства** | Действие, изменяющее поле документа (например, статус заявки) |

## Логика расширенной схемы бизнес-процесса

### Условие подключения бухгалтера

```
ЕСЛИ [Сумма] > 15000 И [Решение руководителя] = "Одобрено"
  → Ветка согласования с бухгалтером
ИНАЧЕ
  → Завершение процесса
```

### Общая структура после добавления условия

```
[Утверждение у руководителя]
          ↓
     [Условие]
    /          \
(сумма > 15 000)  (иначе — всегда True)
       ↓                   ↓
[Согласование        [Завершение /
 у бухгалтера]        следующий шаг]
```

- Блок **«Условие»** добавляется **после** одобрения руководителем
- Согласование у бухгалтера — **последовательный** этап, не параллельный
- Если бухгалтер отклонил заявку — решение руководителя теряет силу

## Проблема дублирования веток и её решение

### Описание проблемы

В процессе согласования возникают **две похожие ветки** с одинаковыми завершающими действиями:

```
Руководитель ОТКЛОНИЛ → [Изменить статус] [Записать в отчёт] [Уведомить]
Бухгалтер ОТКЛОНИЛ   → [Изменить статус] [Записать в отчёт] [Уведомить]
```

### Почему дублирование — антипаттерн

1. **Сложность поддержки** — при изменении логики нужно вносить правки в нескольких местах, легко что-то пропустить
2. **Сложность чтения** — схема разрастается, труднее отследить логику
3. **Риск рассинхронизации** — ветки могут «разъехаться» и начать вести себя по-разному

### Решение: управляющая переменная

Финальные действия выносятся **в одно место** в конец процесса, а выбором ветки управляет специальная переменная.

### Архитектура решения

```
НАЧАЛО
  │
  ├─ Установить переменную "Итог" = НЕТ (значение по умолчанию)
  │
  ├─ [Задание: утверждение у Руководителя]
  │       │
  │   ОДОБРИЛ?
  │   ДА ──────────────────────────────────────────────────┐
  │   НЕТ → переменная остаётся НЕТ                        │
  │                                                        │
  │                                     Установить "Итог" = ДА
  │                                                        │
  │                                     Сумма > 15 000?
  │                                     ДА ────────────────┐
  │                                     НЕТ → "Итог" = ДА  │
  │                                     (остаётся)         │
  │                                              [Задание: Бухгалтер]
  │                                                        │
  │                                               ОДОБРИЛ?
  │                                               ДА → "Итог" = ДА
  │                                               НЕТ → "Итог" = НЕТ
  │
  └─ ФИНАЛЬНОЕ УСЛОВИЕ: переменная "Итог" = ?
          │
     ДА ──┴──► [Статус: Одобрена] [Уведомление об одобрении]
     НЕТ ────► [Статус: Отклонена] [Уведомление об отклонении]
```

### Все возможные сценарии

| Сценарий | Значение «Итог» в финале |
|---|---|
| Руководитель отклонил | НЕТ (по умолчанию) |
| Руководитель одобрил, сумма < 15 000 | ДА |
| Руководитель одобрил, сумма ≥ 15 000, бухгалтер одобрил | ДА |
| Руководитель одобрил, сумма ≥ 15 000, бухгалтер отклонил | НЕТ (сброшено) |

## Действие «Условие» — детальный разбор

### Ключевые особенности

1. **Несколько веток** — можно создавать 3, 4 и более путей выполнения
2. **Проверка слева направо** — ветки проверяются строго по порядку; критически важно при проектировании логики
3. **Обязательная «страховочная» ветка** — правая ветка всегда содержит условие **«Истина»**, чтобы процесс гарантированно прошёл через условие и не завис

### Правило проектирования условий

```
Левая ветка  →  конкретное условие (например, сумма > 15 000)
Правая ветка →  Истина (всегда True — «иначе»)
```

> ⚠️ **Важно:** если поставить «Истина» слева — она сработает первой и процесс никогда не дойдёт до правой ветки с реальным условием. Всегда: конкретное условие — **слева**, «Истина» — **справа**.

## Константы — зачем и когда использовать

### Бухгалтер vs Руководитель

| Участник | Как определяется | Инструмент |
|---|---|---|
| Руководитель | Динамически — по автору заявки (у каждого сотрудника свой руководитель) | **Переменная** |
| Бухгалтер (главбух) | Статически — один конкретный человек для всей компании | **Константа** |

### Преимущества константы

- Значение задаётся **один раз** в настройках шаблона
- Используется **во всех запускаемых экземплярах** процесса автоматически
- При смене главбуха достаточно **изменить константу один раз** — все будущие запуски подхватят новое значение
- Не нужно вручную прописывать пользователя в каждое действие

### Неудобный альтернативный способ

Войти в организационную структуру → найти бухгалтерию → указать главного бухгалтера напрямую в настройке действия. При смене сотрудника придётся редактировать каждое действие вручную.

### Константа vs Переменная (сравнение)

| | Константа | Переменная |
|---|---|---|
| Значение | Задаётся один раз | Может меняться в ходе БП |
| Использование | Параметры, которые редко меняются | Промежуточные результаты |
| Пример | ФИО/ID главного бухгалтера | Флаг «нужно согласование бухгалтера» |

## Пошаговые инструкции

### Шаг 1. Создать управляющую переменную

1. Открыть редактор бизнес-процесса
2. Перейти в раздел **Переменные**
3. Нажать **«Добавить переменную»**
4. Задать параметры:
   - **Название:** например, `Итог_согласования`
   - **Тип:** `Да/Нет` (boolean)
   - **Значение по умолчанию:** `Нет`
5. Сохранить переменную

---

### Шаг 2. Установить переменную в НЕТ в начале процесса

1. В самом начале схемы (до первого действия) добавить действие **«Установить переменную»**
2. Выбрать переменную `Итог_согласования`
3. Установить значение = `Нет`

> **Зачем:** гарантируем, что переменная всегда начинает с известного значения, даже при повторном запуске процесса.

---

### Шаг 3. Добавить блок «Условие» в схему

1. Открыть редактор бизнес-процесса
2. Найти место **после** блока «Утверждение у руководителя»
3. Добавить действие **«Условие»** между блоком руководителя и следующим шагом
4. Убедиться, что условие стоит именно **после одобрения**, не параллельно

---

### Шаг 4. Настроить ветки условия (сумма > 15 000)

1. В блоке «Условие» настроить **левую ветку**:
   - Поле: `Сумма`
   - Оператор: `больше`
   - Значение: `15000`
2. В **правой ветке** установить условие **«Истина»** (всегда выполняется)
3. Сохранить настройки условия

---

### Шаг 5. Установить переменную в ДА после одобрения руководителем

1. Найти ветку **«Руководитель одобрил» (ДА)**
2. Первым действием в этой ветке добавить **«Установить переменную»**
3. Установить `Итог_согласования` = `Да`

---

### Шаг 6. Создать константу для бухгалтера

1. Перейти в **«Параметры шаблона»**
2. Открыть раздел **«Константы»**
3. Нажать **«Добавить константу»**
4. Задать параметры:
   - **Имя:** `BUHGALTER` (или `Главный бухгалтер`)
   - **Тип:** `Пользователь`
   - **Значение:** выбрать конкретного сотрудника — главного бухгалтера
5. Сохранить константу
6. В дальнейшем использовать как `{=Constant:BUHGALTER}` в действиях

---

### Шаг 7. Добавить задание для бухгалтера

1. В ветке «сумма > 15 000» добавить действие **«Задание»** (или «Запрос одобрения»)
2. В поле **«Исполнитель»** выбрать не пользователя напрямую, а созданную **константу**
3. Настроить варианты ответа: **Одобрить / Отклонить**
4. Добавить уведомления пользователям по результату
5. Сохранить

---

### Шаг 8. Сбросить переменную в НЕТ при отклонении бухгалтером

1. В ветке **«Бухгалтер отклонил» (НЕТ)** добавить **«Установить переменную»**
2. Установить `Итог_согласования` = `Нет`

> **Логика:** бухгалтер «откатывает» положительное решение руководителя.

---

### Шаг 9. Создать финальное условие

1. После слияния всех веток добавить итоговое **«Условие»**
2. Проверяемое значение: переменная `Итог_согласования`
3. **Ветка ДА:**
   - Установить статус документа = `Одобрена`
   - Уведомить пользователя об одобрении
   - Запись в отчёт/лог
4. **Ветка НЕТ:**
   - Установить статус документа = `Отклонена`
   - Уведомить пользователя об отклонении
   - Запись в отчёт/лог (с детализацией: кто именно отклонил)

---

### Шаг 10. Добавить записи в лог для отладки

В ключевых точках схемы добавить действие **«Запись в журнал»** с понятными сообщениями:

- `"Процесс начат, Итог = НЕТ"`
- `"Руководитель одобрил, Итог = ДА"`
- `"Сумма > 15000, отправляем на согласование бухгалтеру"`
- `"Бухгалтер отклонил, Итог сброшен в НЕТ"`
- `"Финальное условие: Итог = [значение переменной]"`

> **Примечание:** детализирующие записи («Руководитель отклонил», «Бухгалтер отклонил») остаются **в ветках**, а не выносятся в финал — чтобы лог был информативным.

---

### Шаг 11. Протестировать схему

1. Сохранить бизнес-процесс
2. Временно назначить **себя бухгалтером** (стандартная практика для быстрой проверки без создания тестовых пользователей)
3. Создать тестовые заявки для **всех четырёх сценариев**:
   - Руководитель отклонил
   - Руководитель одобрил, сумма < 15 000
   - Руководитель одобрил, сумма ≥ 15 000, бухгалтер одобрил
   - Руководитель одобрил, сумма ≥ 15 000, бухгалтер отклонил
4. Проверить, что статусы проставляются корректно
5. Просмотреть лог для диагностики возможных ошибок

## Что выносится в финальный блок, а что остаётся в ветках

### Финальный блок (один для всех исходов)

Следующие действия размещаются **один раз** в конце процесса:
- Установка свойства документа (статус: Одобрена / Отклонена)
- Запись в отчёт
- Уведомление пользователей

### Промежуточные записи (остаются в ветках)

Детализирующие записи остаются в соответствующих ветках:
- «Руководитель отклонил заявку»
- «Бухгалтер отклонил заявку»
- «Заявка одобрена без согласования с бухгалтером (сумма < 15 000)»

## Главное

1. **Дублирование действий в ветках — антипаттерн.** Одинаковые действия в нескольких ветках делают схему хрупкой и трудной для поддержки. Общую логику нужно выносить в одно место.

2. **Управляющая переменная типа Да/Нет** — стандартный инструмент для схлопывания нескольких веток в одну финальную развилку. Она «несёт» результат сквозь всю схему.

3. **Значение переменной по умолчанию устанавливается явно в начале** — это защита от неожиданного поведения при повторных запусках и граничных случаях.

4. **Переменную можно сбросить в любой точке процесса** — если последующий участник отменяет предыдущее положительное решение, переменная устанавливается обратно в НЕТ.

5. **Порядок веток в условии имеет значение:** конкретное условие — всегда **слева**, «Истина» — всегда **справа**. Нарушение этого правила ломает всю логику ветвления.

6. **Константа для роли бухгалтера** позволяет менять исполнителя в одном месте — при кадровых изменениях не нужно редактировать весь процесс.

7. **Лог — обязательный инструмент при разработке.** Записи в журнал в ключевых точках позволяют быстро диагностировать ошибки в логике без длительной отладки.

8. **Тестируй все четыре сценария** многоуровневого согласования: два «отклонения» (руководитель, бухгалтер) и два «одобрения» (с бухгалтером и без).

9. **Временная подмена ролей** (назначить себя бухгалтером при тестировании) — стандартная практика для быстрой проверки без создания тестовых пользователей.

10. **Переменные и константы — ключевые строительные блоки** сложных бизнес-процессов: переменные хранят изменяемое состояние, константы — фиксированные настройки. Грамотное их использование определяет качество архитектуры всего процесса.
