# Утверждение у руководителя
**Bitrix24 — Автоматизация бизнес-процессов | Модуль 4, Урок 8**

---

## О чём этот урок

Урок посвящён практическому созданию бизнес-процесса (БП) «с нуля» в Bitrix24. На примере процесса согласования заявки разбирается первая часть сценария — утверждение документа руководителем с исходом **«Одобрено»** или **«Отклонено»**. Урок закладывает основу архитектуры БП: переменные, действия, ветки, уведомления.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Бизнес-процесс (БП)** | Автоматизированный сценарий действий, запускаемый по событию (например, созданию объекта) |
| **Документ** | Объект Bitrix24, по которому запускается БП (в данном случае — заявка) |
| **Переменная** | Временное хранилище данных внутри одного запущенного экземпляра БП; существует только пока работает этот экземпляр |
| **Константа** | Постоянное значение, не меняющееся в ходе выполнения БП (используется для фиксированных данных, например ФИО бухгалтера) |
| **Действие** | Атомарный шаг в схеме БП (уведомление, задание, изменение документа и т.д.) |
| **Ветка** | Путь выполнения БП после условия («Да» / «Нет») |
| **Утверждающий** | Пользователь, которому ставится задание на согласование |
| **Автор / Сотрудник** | Пользователь, создавший заявку и запустивший БП |
| **Резервный пользователь** | Пользователь, который выбирается, если основной алгоритм не смог определить нужного |
| **Орг-схема** | Структура компании в Bitrix24, на основе которой определяется руководитель |

---

## Архитектура сценария

```
[Запуск БП]
    → Определить руководителя (действие «Выбор сотрудника»)
    → Присвоить переменные (утверждающий, сотрудник)
    → Установить статус «На согласовании»
    → Уведомить руководителя о новом задании
    → [Задание: Утверждение документа]
        ├── Да → Установить статус «Одобрено»
        │        → Уведомить сотрудника об одобрении
        └── Нет → Установить статус «Отклонено»
                  → Уведомить сотрудника об отклонении
```

## Раздел 1. Определение руководителя

### Почему нельзя прописывать пользователя жёстко

Жёстко прописывать конкретного пользователя в БП — **плохая практика**: если руководитель сменится, придётся вручную редактировать шаблон. Решение — использовать системные данные о пользователе, получая руководителя **динамически**.

### Действие: «Выбор сотрудника»

Специальное действие, умеющее определять руководителя по орг-схеме компании.

**Ключевые настройки:**

| Параметр | Значение |
|---|---|
| Тип определения | «Определение начальника» |
| Уровень руководителя | 1 (непосредственный руководитель отдела) |
| Для какого пользователя | Поле документа → «Кем создан» |
| Резервный пользователь | Указать конкретного человека (на этапе разработки — себя) |

> **Зачем нужен резервный пользователь:** если в орг-схеме не указан начальник отдела или произошла другая ошибка — БП не остановится, а передаст задание резервному пользователю. На продакшене должен быть реальный сотрудник (например, HR или руководитель подразделения), а не тестовый аккаунт.

## Раздел 2. Переменные — почему они важны

### Проблема без переменных

Можно напрямую подставить результат действия «Выбор сотрудника» в поле «Кто утверждает» задания. Но если в будущем логика определения утверждающего усложнится — придётся менять ссылку **во всех действиях**, где она используется.

### Решение: две переменные

Создаются в **Параметры шаблона → Переменные**:

| Переменная | Тип | Что хранит |
|---|---|---|
| `утверждающий` | Пользователь | Пользователь, который согласовывает заявку |
| `сотрудник` / `автор` | Пользователь | Пользователь, создавший заявку и запустивший БП |

**Преимущество:** при смене алгоритма выбора утверждающего достаточно поменять **одно место** — действие «Изменение переменных». Все остальные действия продолжают обращаться к той же переменной.

### Действие: «Изменение переменных»

Используется для присвоения значений переменным сразу после запуска БП.

**Настройка:**
- Переменная `утверждающий` ← Дополнительные результаты → Выбор сотрудника → **Выбранный сотрудник**
- Переменная `сотрудник` ← Поле документа → **Кем создан**

---

## Раздел 3. Изменение статуса документа

### Действие: «Изменение документа»

Позволяет программно менять значения полей объекта Bitrix24 прямо в ходе процесса.

**Использование в этом БП:**

| Момент | Статус |
|---|---|
| В начале БП (после запуска) | `«На согласовании»` |
| В ветке «Да» (одобрено) | `«Одобрено»` |
| В ветке «Нет» (отклонено) | `«Отклонено»` |

### Лайфхак: копирование действия с настройками

Чтобы не настраивать одно и то же действие трижды:
1. Настроить первое действие «Изменение документа» со статусом
2. Зажать **Ctrl** и перетащить действие в нужное место — создастся **копия со всеми настройками**
3. В копии изменить только значение статуса

## Раздел 4. Задание на утверждение документа

### Действие: «Утверждение документа»

Создаёт интерактивное задание для пользователя с кнопками «Да» / «Нет». Процесс **приостанавливается** и ждёт ответа. Пользователь получает уведомление в Живой Ленте.

**Ключевые настройки:**

| Параметр | Значение / Рекомендация |
|---|---|
| Кто утверждает | Переменная `утверждающий` |
| Описание / текст задания | Подробное описание: что нужно сделать + обоснование затрат из заявки |
| Текст статуса | Информативное описание текущего состояния БП (видно всем участникам) |
| Названия кнопок | Переименовать для ясности, например: «Утвердить» / «Отклонить» |
| Комментарий | Разрешить, сделать **необязательным** |

> **Текст статуса** — специальная опция, которая отображается участникам БП и показывает, что сейчас происходит с процессом. Делает БП более информативным. Всегда заполняй его.

> **Комментарий в задании** лучше делать необязательным, но доступным — руководитель должен иметь возможность объяснить причину отклонения, но не быть обязан это делать при одобрении.

## Раздел 5. Уведомления

В схеме — два уведомления.

### Уведомление 1 — Руководителю (до задания)

Сообщает руководителю, что поступило новое задание на согласование.

| Параметр | Значение |
|---|---|
| Отправитель | Переменная `сотрудник` (автор заявки) |
| Получатель | Переменная `утверждающий` |
| Текст | Краткое описание заявки |

### Уведомление 2 — Сотруднику (после решения)

Сообщает автору заявки о результате согласования. Размещается **в обеих ветках** («Одобрено» и «Отклонено») с соответствующим текстом.

| Параметр | Значение |
|---|---|
| Отправитель | **Системный** (не переменная `сотрудник`) |
| Получатель | Переменная `сотрудник` |
| Текст | Сообщение о результате с вставкой значений полей (сумма, ФИО, комментарий) |

> **Почему отправитель — система:** если отправитель и получатель совпадают (сотрудник сам себе), уведомление выглядит некрасиво в ленте. Системный отправитель решает эту проблему.

## Пошаговые инструкции

### Шаг 1. Добавить действие «Выбор сотрудника»
1. В редакторе БП найти действие **«Выбор сотрудника»**
2. Тип → **«Определение начальника»**
3. Для пользователя → **Поле документа → Кем создан**
4. Уровень → **1** (непосредственный руководитель)
5. Резервный пользователь → указать себя (временно для разработки)
6. Сохранить

### Шаг 2. Создать переменные
1. Открыть **Параметры шаблона → Переменные**
2. Создать переменную **«утверждающий»** (тип: Пользователь)
3. Создать переменную **«сотрудник»** (тип: Пользователь)
4. Сохранить

### Шаг 3. Добавить действие «Изменение переменных»
1. Добавить действие **«Изменение переменных»**
2. `утверждающий` ← Дополнительные результаты → Выбор сотрудника → **Выбранный сотрудник**
3. `сотрудник` ← Поле документа → **Кем создан**
4. Сохранить

### Шаг 4. Установить начальный статус
1. Добавить действие **«Изменение документа»**
2. Поле «Статус» → **«На согласовании»**
3. Сохранить

### Шаг 5. Добавить уведомление руководителю
1. Добавить действие **«Уведомление пользователю»**
2. Отправитель → переменная `сотрудник`
3. Получатель → переменная `утверждающий`
4. Текст → краткое описание заявки
5. Сохранить

### Шаг 6. Добавить задание «Утверждение документа»
1. Добавить действие **«Утверждение документа»**
2. Кто утверждает → переменная `утверждающий`
3. Описание → подробный текст с данными из заявки
4. Текст статуса → описание текущего этапа БП
5. Переименовать кнопки («Утвердить» / «Отклонить»)
6. Комментарий → разрешить, сделать **необязательным**
7. Сохранить

### Шаг 7. Настроить ветку «Да» (Одобрено)
1. Скопировать действие «Изменение документа» (**Ctrl + перетащить**)
2. Поместить в ветку **«Да»**
3. Статус → **«Одобрено»**
4. Добавить **«Уведомление пользователю»**: отправитель — система, получатель — `сотрудник`
5. Сохранить

### Шаг 8. Настроить ветку «Нет» (Отклонено)
1. Скопировать действие «Изменение документа» (**Ctrl + перетащить**)
2. Поместить в ветку **«Нет»**
3. Статус → **«Отклонено»**
4. Добавить **«Уведомление пользователю»**: отправитель — система, получатель — `сотрудник`
5. Сохранить

### Шаг 9. Сохранить и протестировать

## Сценарий тестирования

**Условие теста:** тестовый объект — заявка на сумму 15 000 руб. Структура подчинения: **Диана** является руководителем **Ренаты**.

### Пошаговый сценарий

1. Сотрудник (Рената) заполняет и отправляет заявку
2. БП автоматически определяет руководителя по орг-схеме (Диана)
3. В Живой Ленте руководителя появляется **задание БП** с заголовком «Утверждение документа» и описанием (сумма, автор)
4. Руководитель нажимает **«Приступить»** — открывается диалоговое окно
5. Руководитель выбирает **«Утвердить»** или **«Отклонить»**
6. В Живой Ленте сотрудника (Ренаты) появляется уведомление о результате
7. Статус БП обновляется в объекте

### Что важно проверить при тестировании

- ✅ Корректность определения руководителя по структуре компании
- ✅ Информативность задания в Живой Ленте (руководитель сразу понимает суть запроса)
- ✅ Появление уведомления у инициатора после принятия решения
- ✅ Финальный статус бизнес-процесса в объекте

> **Важно:** структура подчинения в Bitrix24 напрямую влияет на работу БП — переменная «Руководитель» берётся именно из неё. Перед тестированием убедись, что орг-схема компании настроена корректно.

## Главное

1. **Всегда используй переменные для ключевых участников БП** (`утверждающий`, `сотрудник` и т.д.) — это защищает от необходимости менять настройки во многих местах при изменении логики.

2. **Действие «Выбор сотрудника» → Определение начальника** автоматически находит руководителя по орг-схеме. Без настроенной орг-схемы не работает — всегда указывай **резервного пользователя**.

3. **Изменение документа** — обязательный элемент для отражения статуса процесса в объекте. Ставь статус в начале БП и в каждой ветке результата.

4. **Копирование действий через Ctrl+перетащить** сохраняет все настройки — используй для действий, которые повторяются с небольшими отличиями (например, установка разных статусов).

5. **Текст статуса** в задании «Утверждение документа» делает БП прозрачным для всех участников — всегда заполняй его.

6. **Резервный пользователь** — страховка от зависания БП. На продакшене должен быть реальный сотрудник (HR или руководитель подразделения), а не тестовый аккаунт.

7. **Отправитель уведомления = система**, когда получатель — сам автор заявки. Иначе уведомление выглядит как «вы написали себе».

8. **Паттерн построения БП: переменные → действия → ветки** — универсальный подход в Bitrix24. Сначала собираем данные, потом выполняем действия, потом ветвимся.

9. **Комментарий в задании на согласование** — делать необязательным, но доступным: руководитель может объяснить причину отклонения, но не обязан комментировать при одобрении.

10. **БП строится итеративно** — сначала минимальная рабочая схема, потом усложнение. Не пытайся сразу предусмотреть все случаи.
