# Модуль 4: Автоматизация бизнес-процессов в Bitrix24 — Итоговый обзор

## О модуле

Модуль посвящён построению полноценных автоматизированных бизнес-процессов в Bitrix24 на примере типового сценария согласования заявок. Центральная тема — как грамотно связать логику процесса с системой управления доступом, чтобы данные оставались защищёнными на каждом этапе. Особый акцент делается на разграничении статических и динамических прав: первые задают базовые ограничения, вторые гибко выдаются самим бизнес-процессом в нужный момент нужному участнику. Модуль формирует понимание того, что автоматизация — это не только маршрутизация задач, но и контроль над данными и доступом к ним на всём протяжении процесса.

---

## Смысловой блок 1: Проблематика и архитектурный принцип

### Почему «всем на изменение» — не решение

Типичная ошибка при первоначальной настройке — выдать широкие права ради удобства разработки. Это создаёт критическую уязвимость: **любой сотрудник может изменить данные заявки уже после её одобрения**, что полностью обесценивает согласование.

**Архитектурный принцип модуля:**
- Данные заявки «замораживаются» в момент запуска бизнес-процесса
- Изменение данных возможно **только через действия бизнес-процесса**, а не через ручное редактирование
- Доступ к записи открывается **точечно и динамически** — только тому, кому нужно, и только тогда, когда нужно

> ⚠️ Правило: на этапе разработки можно держать расширенные права, но **перед выкаткой в продакшн — обязательно настроить реальную модель доступа**.

## Смысловой блок 2: Двухуровневая модель прав доступа

Модуль раскрывает связку двух типов прав, которые работают в паре и дополняют друг друга:

### Уровень 1 — Статические права (настройки раздела)

Задают базовые ограничения, действующие на весь раздел целиком:

| Роль | Уровень доступа | Логика |
|---|---|---|
| Все сотрудники | Только добавление | Могут создавать заявки, но не видят чужие |
| Бухгалтер | Чтение | Видит заявки для согласования, но не редактирует |
| Руководитель | Чтение | Одобряет/отклоняет через задание, не через редактирование |
| Администратор | Полный доступ | Системный уровень, не зависит от настроек |

> **Важно:** «Только добавление» означает, что после создания заявки сотрудник не видит её в списке — пока бизнес-процесс не откроет доступ.

### Уровень 2 — Динамические права (действие «Установка прав» в БП)

Выдаются бизнес-процессом точечно — только на конкретный документ, только конкретному участнику, только в нужный момент:

| Момент выдачи | Кому | Что выдаётся |
|---|---|---|
| Сразу после создания заявки | Автор заявки | Чтение своей заявки |
| После определения руководителя | Руководитель | Чтение для рассмотрения |
| После одобрения руководителем | Бухгалтер | Чтение для финального согласования |

## Смысловой блок 3: Инструмент — действие «Установка прав»

Это ключевой инструмент динамического управления доступом внутри бизнес-процесса.

### Принцип работы

```
[Определение переменной с исполнителем]
              ↓
    [Установка прав] ← вставляется здесь
              ↓
  [Постановка задания исполнителю]
```

**Правило размещения:** действие «Установка прав» всегда вставляется **после** определения переменной с исполнителем и **до** постановки ему задания.

### Что настраивается

- **Кому** — пользователь или группа (может браться из переменной бизнес-процесса)
- **Какой уровень** — чтение, изменение, удаление и т.д.
- **На что** — только на документ текущего бизнес-процесса, не на весь раздел

### Итоговый маршрут с установкой прав

```
[Создание заявки]
        ↓
[БП запускается автоматически]
        ↓
[Установка прав] → Автор: чтение
        ↓
[Определение руководителя]
        ↓
[Установка прав] → Руководитель: чтение
        ↓
[Задание руководителю: одобрить / отклонить]
        ↓
[Условие: результат согласования]
        ↓
[Установка прав] → Бухгалтер: чтение  ← (ветка «одобрено»)
        ↓
[Задание бухгалтеру: согласовать]
```

## Смысловой блок 4: Взаимосвязь тем модуля

Темы модуля выстраиваются в единую логическую цепочку:

```
Бизнес-логика процесса (маршрут согласования)
            ↕
  Переменные и участники (кто согласует)
            ↕
   Задания и действия (что делают участники)
            ↕
   Права доступа (что участники видят и могут)
```

- **Автоматизация процесса** без прав доступа — небезопасна: данные открыты для изменения
- **Права доступа** без автоматизации — неудобны: нужно вручную управлять каждым разрешением
- **Связка БП + динамические права** — полноценное решение, где процесс сам управляет видимостью данных

## Ключевые выводы модуля

1. **Автоматизация и управление доступом неразделимы** — грамотный бизнес-процесс не только маршрутизирует задачи, но и сам управляет тем, кто что видит и может изменить.
2. **Широкие права на этапе разработки недопустимы в продакшне** — перед запуском системы в работу модель прав обязательно приводится в соответствие с регламентом.
3. **Базовый принцип для рядовых сотрудников — только «добавление»**: создать заявку можно, но видеть чужие — нельзя.
4. **Данные заявки замораживаются после запуска БП** — изменения допустимы только через специальные действия бизнес-процесса, не через ручное редактирование.
5. **Статические права задают рамки, динамические — открывают доступ в нужный момент**: эти два уровня работают в паре и не заменяют друг друга.
6. **Действие «Установка прав» работает точечно** — права выдаются только на конкретный документ, не на весь раздел.
7. **Порядок вставки «Установки прав» критичен** — сначала определяем исполнителя, потом выдаём ему права, потом ставим задание.
8. **Согласующие лица получают права на чтение, не на изменение** — их роль реализуется через задание бизнес-процесса, а не через редактирование полей.
9. **Автор заявки должен явно получить права на чтение своей же заявки** — без действия «Установка прав» он не увидит созданный им документ.
10. **Изменение статических прав не открывает доступ к старым записям** — только к новым, созданным после изменения настроек.
11. **Администратор портала видит всё независимо от настроек** — тестировать права нужно под учётными записями обычных пользователей.
12. **Каждый этап согласования требует своей «Установки прав»** — руководитель, бухгалтер и другие участники получают доступ последовательно, по мере прохождения процесса.
13. **Динамическое управление правами исключает необходимость создавать сложные статические роли** — бизнес-процесс сам знает, кому и когда нужен доступ.
14. **Связка «статические права + динамическая установка через БП»** — универсальный шаблон для большинства корпоративных сценариев согласования в Bitrix24.
15. **Правильно настроенная система прав — это не ограничение, а защита регламента**: она гарантирует, что процесс пройдёт именно так, как задумано, без возможности обойти его через прямое редактирование данных.
