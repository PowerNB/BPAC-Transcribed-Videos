# Модуль 4: Автоматизация бизнес-процессов в Bitrix24 — Итоговый обзор

## О чём этот модуль

Модуль посвящён практическому созданию полноценного многоуровневого бизнес-процесса согласования заявок в Bitrix24 — от проектирования объекта и настройки полей до управления правами доступа. На протяжении всего модуля строится единый сквозной процесс: сотрудник подаёт заявку на затраты, руководитель её согласовывает, при сумме свыше 15 000 ₽ подключается бухгалтер, а при отклонении сотрудник может доработать заявку и подать повторно. Модуль охватывает все ключевые инструменты конструктора БП: переменные, константы, условия, циклы, задания, запросы данных, логирование и права доступа. Особый акцент сделан на архитектурных паттернах — как строить бизнес-процессы, которые легко сопровождать и масштабировать.

## Смысловой блок 1. Проектирование: объект, поля, сценарий

### Что строим и зачем

Прежде чем открывать конструктор, необходимо:
1. **Сформулировать сценарий словами** — кто что делает, при каких условиях, что при отказе
2. **Выбрать объект** для бизнес-процесса — Живая Лента или Список в группе (не файлы: у них нет произвольных полей)
3. **Описать поля** объекта и их типы

### Объект «Заявки на затраты»

| Поле | Тип | Роль |
|---|---|---|
| Сумма | Число / деньги | Ключевое поле для маршрутизации |
| Описание целей | Большой текст | Обоснование заявки |
| Счёт на оплату | Файл | Вложение |
| Статус | Список | Техническое поле — меняет только БП |

**Значения поля «Статус»:** На рассмотрении / Одобрено / Отклонено / Отозвана

> **Ключевой принцип:** технические поля (статус) скрываются из формы создания — ими управляет только процесс, не пользователь.

### Тип бизнес-процесса

Используется **последовательный БП** — действия выполняются строго по порядку. На этапе разработки включаются оба триггера запуска («При добавлении» и «При изменении») для удобства тестирования.

## Смысловой блок 2. Переменные и константы — фундамент архитектуры

### Переменные

Переменные хранят данные, которые **меняются или определяются динамически** в ходе выполнения конкретного экземпляра БП.

| Переменная | Тип | Содержание |
|---|---|---|
| `утверждающий` | Пользователь | Кто согласовывает (руководитель) |
| `сотрудник` | Пользователь | Кто создал заявку |
| `Итог_согласования` | Да/Нет | Управляющая переменная финального условия |
| `Внутренний_статус` | Да/Нет | Управляет выходом из цикла |

**Зачем нужны переменные вместо прямых ссылок:** при смене логики достаточно изменить одно место — действие «Изменение переменных». Все остальные действия продолжают обращаться к той же переменной.

**Руководитель определяется динамически** — через действие «Выбор сотрудника» (тип: «Определение начальника», уровень 1, источник: «Кем создан документ»). Обязателен **резервный пользователь** — страховка от зависания при отсутствии начальника в орг-схеме.

### Константы

Константы хранят данные, которые **заданы один раз и редко меняются** — одинаковы для всех экземпляров процесса.

**Пример:** главный бухгалтер — один на всю компанию, не связан с автором заявки организационно.

| | Константа | Переменная |
|---|---|---|
| Значение | Задаётся один раз | Меняется в ходе БП |
| Пример | ФИО бухгалтера | Руководитель автора |
| Изменение | Один раз в шаблоне | Динамически в каждом запуске |

> **Правило:** при смене главбуха достаточно изменить одну константу — все будущие запуски подхватят новое значение автоматически.

## Смысловой блок 3. Основные действия конструктора БП

### Изменение документа
Программно меняет поля записи в ходе процесса. Используется для:
- Установки статуса в начале БП («На рассмотрении»)
- Обновления статуса по итогам согласования
- Сохранения данных, введённых пользователем через «Запрос данных»

> **Лайфхак:** копирование действия через Ctrl+перетащить сохраняет все настройки.

### Задание / Утверждение документа
Создаёт интерактивное задание пользователю (кнопки «Утвердить» / «Отклонить»). Процесс **приостанавливается** до ответа.

Ключевые настройки:
- **Исполнитель** — через переменную (не хардкодом)
- **Текст статуса** — всегда заполнять: показывает всем участникам, что сейчас происходит
- **Комментарий** — делать необязательным, но доступным

### Уведомления
- Руководителю — до задания (о новой заявке)
- Сотруднику — после решения (об итоге)
- **Отправитель = система**, когда получатель и автор совпадают (иначе сотрудник пишет сам себе)

### Условие
Создаёт развилку: проверяет условие и направляет выполнение по одной из веток.

**Обязательные правила:**
- Проверка строго **слева направо**
- Конкретное условие — **слева**, «Истина» (всегда True) — **справа**
- Правая ветка «Истина» — страховка от зависания при любых входных данных

```
Левая ветка  →  Сумма > 15 000  →  Согласование у бухгалтера
Правая ветка →  Истина          →  Завершение без бухгалтера
```

### Цикл
Повторяет набор действий до нарушения условия выхода.

**Архитектура управления циклом:**
```
До цикла:  Внутренний_статус = НЕТ
Цикл:      пока Внутренний_статус = НЕТ
  └─ При одобрении: Внутренний_статус = ДА → выход из цикла
  └─ При отклонении: переменная остаётся НЕТ → следующая итерация
После цикла: проверка суммы, бухгалтер и т.д.
```

> **Критично:** начальное значение переменной устанавливается **строго до цикла**, не внутри — иначе каждая итерация сбрасывает значение и выход невозможен. Всегда задавать **максимальное число итераций**.

### Запрос данных у пользователя
Показывает пользователю форму для ввода данных. **Само по себе не сохраняет данные в документ** — после него обязательно нужно «Изменение документа».

Версия **«с отклонением»** даёт пользователю кнопку выхода — применяется в ветке «отклонено», чтобы сотрудник мог отказаться от доработки.

### Прерывание процесса
Немедленно завершает выполнение БП. Используется в ветке «сотрудник отказался от доработки».

## Смысловой блок 4. Архитектурный паттерн: управляющая переменная

### Проблема дублирования

В многоуровневом согласовании возникают одинаковые финальные действия в разных ветках:
```
Руководитель отклонил  → [Статус] [Лог] [Уведомление]
Бухгалтер отклонил     → [Статус] [Лог] [Уведомление]
```
Это **антипаттерн**: при изменении логики правки нужны в нескольких местах, легко что-то пропустить.

### Решение: управляющая переменная типа Да/Нет

Финальные действия выносятся в **одно место**, а управление маршрутом осуществляется через переменную `Итог_согласования`:

| Сценарий | Итог_согласования |
|---|---|
| Руководитель отклонил | НЕТ (по умолчанию) |
| Руководитель одобрил, сумма < 15 000 | ДА |
| Руководитель одобрил, бухгалтер одобрил | ДА |
| Руководитель одобрил, бухгалтер отклонил | НЕТ (сброс) |

```
НАЧАЛО → Итог = НЕТ
  → Цикл: утверждение у руководителя
      → Одобрил: Итог = ДА
      → Отклонил: Итог = НЕТ (остаётся)
  → Условие: сумма > 15 000?
      → ДА: утверждение у бухгалтера
          → Одобрил: Итог = ДА
          → Отклонил: Итог = НЕТ (сброс)
ФИНАЛЬНОЕ УСЛОВИЕ: Итог = ?
  → ДА: [Статус: Одобрена] [Уведомление]
  → НЕТ: [Статус: Отклонена] [Уведомление]
```

## Смысловой блок 5. Логирование и отладка

### Действие «Запись в отчёт»

Добавляет произвольную строку в журнал выполнения БП. Выполняет **двойную роль**:
- При разработке — **отладка**: понять, по какой ветке фактически прошёл процесс
- В продакшне — **аудит**: кто, когда и какое решение принял

**Куда ставить записи:**
- До и после каждого условия
- В начале каждой ветки
- При изменении переменных
- В точках принятия решений

### Действие «Установить текст статуса»

Переопределяет статус по умолчанию («Завершён») на информативный («Заявка одобрена» / «Заявка отклонена»). Добавляется в каждую ветку завершения.

### Где найти лог

Список объектов → колонка «Бизнес-процесс» → ссылка на конкретный запуск.

### Диагностика по логу

Если лог пишет «сумма < 15 000», а реальная сумма > 20 000 — это сигнал: **условие читает не то поле**. Симптом самой частой ошибки: в поле условия выбран `ID элемента` вместо `Суммы`.

### Цикл отладки
1. Добавить «Запись в отчёт» в ключевых точках
2. Запустить тест с заведомо известными данными
3. Открыть лог → читать сверху вниз
4. Найти расхождение между ожидаемым и фактическим
5. Исправить → повторить тест
6. После завершения разработки — убрать лишние отладочные записи

## Смысловой блок 6. Права доступа

### Принцип: «вижу только свои заявки»

Базовые (статические) права задаются в настройках раздела:

| Роль | Уровень доступа |
|---|---|
| Все сотрудники | Только добавление |
| Руководитель | Чтение |
| Бухгалтер | Чтение |
| Администратор | Полный доступ |

### Динамические права через БП

Действие **«Установка прав»** выдаёт доступ только к **конкретному документу** в рамках текущего экземпляра процесса:

```
[Запуск БП] → [Установка прав] → Автор: чтение
[Определение руководителя] → [Установка прав] → Руководитель: чтение
[Одобрение руководителя] → [Установка прав] → Бухгалтер: чтение
```

**Место вставки:** сразу после определения переменной с исполнителем, до постановки задания.

### Ключевые правила
- После запуска БП данные заявки **заморожены** — изменить их можно только через действия процесса
- **Изменение статических прав делает старые записи недоступными** — ожидаемое поведение
- **Тестировать** нужно под учётными записями обычных пользователей, не администратора

## Смысловой блок 7. Полная схема бизнес-процесса

```
[Создание заявки]
    → Установка прав: автор получает чтение
    → Установка Итог = НЕТ, Внутренний_статус = НЕТ
    → Статус документа: «На рассмотрении»
    ┌─────────────────────────────────────────────┐
    │  ЦИКЛ (пока Внутренний_статус = НЕТ)        │
    │                                             │
    │  Уведомление руководителю                   │
    │  Задание: утверждение у руководителя        │
    │    → Одобрил:                               │
    │        Внутренний_статус = ДА               │
    │        Итог = ДА                            │
    │    → Отклонил:                              │
    │        Запрос доработки у сотрудника        │
    │          → Хочет доработать (OK):           │
    │              Изменение документа (новые данные)│
    │          → Не хочет (Нет):                  │
    │              Прерывание процесса            │
    └─────────────────────────────────────────────┘
    → УСЛОВИЕ: сумма > 15 000?
        → ДА:
            Установка прав: бухгалтер получает чтение
            Задание: согласование у бухгалтера
              → Одобрил: Итог = ДА
              → Отклонил: Итог = НЕТ
        → НЕТ (Истина): Итог остаётся ДА
    → ФИНАЛЬНОЕ УСЛОВИЕ: Итог = ?
        → ДА: Статус «Одобрена», уведомление, лог
        → НЕТ: Статус «Отклонена», уведомление, лог
    → Установить текст статуса БП
```

## Ключевые выводы модуля

1. **Сначала сценарий — потом конструктор.** Прежде чем открывать дизайнер, опиши логику словами: кто что делает, при каких условиях, что при отказе. Это экономит время и предотвращает архитектурные ошибки.

2. **Переменные защищают от ручного редактирования.** Использование переменных вместо прямых ссылок на пользователей позволяет менять логику в одном месте, а не искать все вхождения по схеме.

3. **Константы — для ролей, которые редко меняются.** Главбух, юрист, HR — один человек на всю компанию. Константа позволяет обновить исполнителя одним изменением для всех будущих запусков.

4. **Управляющая переменная типа Да/Нет — ключевой паттерн** для многоуровневых согласований. Она убирает дублирование финальных действий и делает схему читаемой и сопровождаемой.

5. **Правило условия: конкретное — слева, Истина — справа.** Нарушение этого порядка ломает всю логику маршрутизации — «Истина» срабатывает первой и блокирует реальное условие.

6. **Начальное значение переменной цикла устанавливается до цикла, не внутри.** Иначе каждая итерация сбрасывает значение, и выход из цикла становится невозможным.

7. **«Запрос данных» только собирает — не сохраняет.** После него обязательно нужно «Изменение документа», иначе введённые пользователем данные теряются.

8. **Лог — главный инструмент разработчика и инструмент аудита для бизнеса.** «Запись в отчёт» в ключевых точках схемы ускоряет отладку и повышает прозрачность процесса для всех участников.

9. **Статус «Завершён» неинформативен.** Всегда добавляй «Установить текст статуса» в каждую ветку завершения — пользователь должен видеть смысловой итог, а не технический статус системы.

10. **Права доступа — обязательный последний шаг.** Принцип «вижу только свои заявки» реализуется связкой: базовые права «только добавление» + динамическая «Установка прав» через БП для конкретного документа.

11. **Данные заявки меняются только через действия БП, не вручную.** После запуска процесса документ должен быть заморожен — это обеспечивает управление по регламенту.

12. **Тестируй все ветки, а не только «счастливый путь».** Ошибка в условии может годами оставаться незамеченной, если тестировать только сценарий одобрения.

13. **Резервный пользователь — обязательная страховка.** Без него БП может зависнуть, если в орг-схеме не указан руководитель отдела. На продакшне это должен быть реальный сотрудник.

14. **Дублирование действий в ветках — антипаттерн.** Одинаковая логика в нескольких местах делает схему хрупкой: при изменении легко пропустить одно из вхождений, и ветки «разъедутся».

15. **БП строится итеративно:** сначала минимальная рабочая схема (утверждение у руководителя), затем усложнение (бухгалтер, цикл, доработка, права). Не нужно предусматривать все случаи сразу.
