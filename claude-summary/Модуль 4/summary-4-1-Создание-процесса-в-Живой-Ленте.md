# Конспект: Модуль 4, Урок 8 — Создание бизнес-процесса с нуля

## О чём этот урок

Урок посвящён практическому созданию полноценного бизнес-процесса в Bitrix24 «с нуля» — от выбора объекта до настройки прав доступа. На примере согласования заявок на затраты разбираются все ключевые инструменты: переменные, константы, условия, циклы, задания пользователям и уведомления.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Бизнес-процесс (БП)** | Автоматизированный сценарий действий, запускаемый по объекту (документу, записи) |
| **Живая Лента** | Раздел Bitrix24, где можно создавать собственные типы записей (процессы) с произвольными полями |
| **Шаблон БП** | Описание логики процесса в дизайнере; по шаблону запускаются экземпляры процесса |
| **Последовательный БП** | Тип БП, где действия выполняются одно за другим в заданном порядке |
| **Переменная** | Именованное хранилище данных внутри БП; значение может меняться в ходе выполнения |
| **Константа** | Именованное хранилище данных внутри БП; значение задаётся один раз и не меняется |
| **Условие** | Действие-развилка, которое направляет выполнение процесса по одной из нескольких веток |
| **Цикл** | Действие, повторяющее набор вложенных действий до выполнения заданного условия |
| **Задание** | Действие, которое останавливает БП и ждёт реакции конкретного пользователя |
| **Запрос данных** | Действие, показывающее пользователю форму для ввода данных прямо в ходе БП |
| **Лог БП** | Журнал выполнения процесса; используется для отладки и аудита |
| **Статус** | Поле-список в объекте, отражающее текущее состояние записи (на согласовании / одобрено / отклонено) |
| **Права доступа** | Настройки видимости и редактирования записей для разных групп пользователей |

---

## 1. Сценарий процесса

Перед созданием БП формулируется бизнес-логика:

1. **Сотрудник** создаёт заявку на затраты (название товара/услуги, сумма, цель, счёт).
2. **Руководитель** рассматривает заявку — одобряет или отклоняет.
   - При отклонении сотрудник дорабатывает заявку по комментариям.
3. **Если сумма > 15 000** — после одобрения руководителем заявка дополнительно согласуется с **главным бухгалтером**.
   - Бухгалтер также может одобрить или отклонить.

> Ключевой принцип: **сначала описываешь сценарий на словах, потом переносишь в дизайнер.**

---

## 2. Создание объекта в Живой Ленте

### Почему Живая Лента, а не файлы

- Файл — ограниченный объект; к нему нельзя добавить произвольные поля.
- Живая Лента / Списки в группе позволяют создать **любые нужные поля**: сумма, описание, вложения, статус и т.д.
- Процессы в Живой Ленте и Списки в группе работают по схожим принципам.

### Пошаговое создание нового процесса

1. Перейти в раздел **Живая Лента**.
2. Нажать **«Новый процесс»**.
3. Задать **название** — например, `Заявки на затраты`.
4. Задать **сортировку** (например, `1`) — чтобы процесс был первым в списке.
5. Оставить подписи по умолчанию или изменить под нужды.
6. Настроить **доступ** — на этапе разработки поставить «Всем на изменение»; позже заменить на реальные права.
7. Нажать **Сохранить**.

### Создание полей объекта

После создания процесса добавить поля:

| Поле | Тип | Обязательное | Комментарий |
|---|---|---|---|
| **Сумма** | Число / деньги | Да | Главное поле для согласования |
| **Описание целей** | Большой текст | Да | Что покупаем и для чего |
| **Счёт на оплату** | Файл | Нет | Вложение, если счёт уже есть |
| **Статус** | Список | Нет | Техническое поле; скрыть из формы создания |

**Значения поля «Статус»** (пример):
- На рассмотрении
- Одобрено
- Отклонено

> **Важно:** техническое поле «Статус» не должно заполняться сотрудником вручную — его меняет бизнес-процесс. Такие поля **скрывают из формы создания**.

---

## 3. Создание шаблона бизнес-процесса

### Путь в интерфейсе

`Живая Лента → [нужный процесс] → Действия → Настроить бизнес-процессы → Создать последовательный бизнес-процесс`

### Настройки запуска шаблона

- **При добавлении** — запускать при создании новой записи.
- **При изменении** — запускать при редактировании записи.
- На этапе разработки удобно включить оба режима, чтобы тестировать без создания новых записей.

## 4. Утверждение у руководителя

### Определение руководителя через переменную

Жёстко прописывать конкретного пользователя в БП — плохая практика: если руководитель сменится, нужно редактировать шаблон.

**Решение:** использовать системные данные о пользователе.
- В Bitrix24 у каждого пользователя есть поле **«Руководитель»** (задаётся в профиле).
- В БП можно обратиться к инициатору процесса и получить его руководителя динамически.

### Изменение поля документа

Действие **«Изменить документ»** позволяет обновить поля записи прямо в ходе процесса.
- Используется для смены поля **«Статус»** (например, выставить «На рассмотрении» при старте, «Одобрено» или «Отклонено» — после решения).

### Задание на согласование

Действие **«Задание»** / **«Запрос подтверждения»**:
- Назначается конкретному пользователю (руководителю).
- Процесс **приостанавливается** и ждёт ответа.
- Пользователь получает уведомление и видит кнопки: **«Одобрить»** / **«Отклонить»** (+ поле для комментария).
- Результат задания сохраняется и используется в дальнейшей логике.

### Уведомления пользователям

Действие **«Уведомление»**:
- Отправляет сообщение в Bitrix24 указанным пользователям.
- Можно использовать вставку значений полей (сумма, ФИО, комментарий).
- Уведомляют: инициатора (о решении), руководителя (о новой заявке), бухгалтера (при необходимости).

---

## 5. Проверка работы, лог и статус

### Запись в лог

Действие **«Запись в журнал»** (лог):
- Позволяет зафиксировать текущее состояние переменных, результаты действий, промежуточные значения.
- Используется при **отладке** — помогает понять, по какой ветке пошёл процесс и с какими значениями.
- После отладки логи можно оставить для аудита или убрать для «чистоты».

### Отображение результатов

Чтобы результат работы БП был понятен пользователям:
- Поле **«Статус»** на форме отображает актуальное состояние заявки.
- Уведомления содержат **конкретные данные**: сумму, кто принял решение, комментарий.
- В самом задании выводится текст с подстановкой значений из полей документа.

## 6. Условие и константы

### Действие «Условие»

Позволяет создать **развилку** в бизнес-процессе:
- Проверяет заданное выражение (например, `Сумма > 15000`).
- В зависимости от результата выполняется **ветка «Да»** или **ветка «Нет»**.
- Условий может быть несколько (elseif), а также ветка «Иначе» по умолчанию.

### Константа vs Переменная

| | Константа | Переменная |
|---|---|---|
| Значение | Задаётся один раз | Может меняться в ходе БП |
| Использование | Параметры, которые редко меняются | Промежуточные результаты |
| Пример | ФИО/ID главного бухгалтера | Флаг «нужно согласование бухгалтера» |

**Почему бухгалтер — константа:**
- Должность «главный бухгалтер» в компании одна; конкретный человек меняется редко.
- Удобнее изменить значение константы в одном месте шаблона, чем искать все упоминания в действиях.
- В отличие от руководителя, у бухгалтера нет прямой организационной связи с инициатором — его нельзя определить через профиль пользователя.

---

## 7. Согласование у бухгалтера

### Условие для ветки бухгалтера

```
ЕСЛИ [Сумма] > 15000 И [Решение руководителя] = "Одобрено"
  → Ветка согласования с бухгалтером
ИНАЧЕ
  → Завершение процесса
```

### Переменная-флаг для управления ветками

Вводится переменная (например, `НужноСогласованиеБухгалтера`):
- Тип: булево (да/нет) или строка.
- Устанавливается в `Истина` до входа в ветку бухгалтера.
- Используется в условии цикла — позволяет повторять процесс согласования пока условие не выполнено.

> **Зачем переменная:** она даёт гибкость управлять потоком выполнения — по значению переменной можно направить процесс в нужную ветку, не дублируя условия.

## 8. Запуск и отладка

### Как выглядит БП для пользователя

- В форме записи появляется кнопка **«Запустить бизнес-процесс»** (или запускается автоматически).
- Ответственный видит **задание** в своём разделе задач или уведомление.
- В карточке записи отображается **статус** и **история** процесса.

### Поиск ошибок

Типичные ошибки в логике:
- Неверная ветка условия (перепутаны «Да» и «Нет»).
- Неправильная переменная подставлена в задание.
- Процесс уходит в бесконечный цикл из-за неверного условия выхода.

**Инструменты отладки:**
1. **Лог** — вставить «Запись в журнал» перед подозрительным местом.
2. **Журнал БП** — просмотр истории выполнения конкретного экземпляра.
3. Тестовый запуск с заведомо известными данными.

---

## 9. Цикл

### Для чего используется

Цикл позволяет **повторять набор действий** до тех пор, пока не выполнится условие выхода.

В нашем сценарии:
- Если руководитель **отклонил** заявку → сотрудник дорабатывает → снова на согласование к руководителю.
- Повторяется до тех пор, пока заявка не будет **одобрена** или сотрудник не **откажется от доработки**.

### Структура цикла

```
[Начало цикла] — условие продолжения
  │
  ├─ Задание: согласование у руководителя
  ├─ Условие: одобрено?
  │    ├─ Да → выход из цикла
  │    └─ Нет → запрос доработки у сотрудника
  │         └─ Условие: сотрудник хочет дорабатывать?
  │              ├─ Да → возврат в начало цикла
  │              └─ Нет → выход (заявка закрыта)
  │
[Конец цикла]
```

### Настройки действия «Цикл»

- **Условие продолжения** — выражение, при `Истина` которого цикл продолжается.
- **Максимальное число итераций** — защита от бесконечного цикла (рекомендуется ставить).
- Внутри цикла размещаются любые действия: задания, уведомления, изменения полей.

## 10. Запрос данных у пользователя

### Действие «Запрос данных»

- Показывает пользователю **форму с полями** прямо в ходе работы БП.
- Процесс **ждёт**, пока пользователь не заполнит и не отправит форму.
- Введённые данные можно сохранить в **поля документа** или в **переменные**.

### Сценарий доработки заявки

1. Руководитель отклонил заявку и написал комментарий.
2. БП запрашивает у сотрудника данные:
   - Обновлённое описание целей.
   - Обновлённая сумма (если нужно).
   - Дополнительные файлы.
3. Введённые данные сохраняются в поля документа (действие «Изменить документ»).
4. Цикл возвращает заявку на согласование.

### Возможность «сдаться»

- В форму запроса данных добавляется **чекбокс или кнопка** «Не дорабатывать / Отозвать заявку».
- Если сотрудник выбирает этот вариант — переменная-флаг меняет значение, цикл завершается.
- Заявка получает статус **«Отозвана»**.

---

## 11. Права доступа

### Типовой сценарий

**Задача:** сотрудник видит **только свои заявки**, не чужие.

### Настройка прав

1. Перейти в настройки процесса → раздел **«Права доступа»**.
2. Для группы «Сотрудники» установить право на **просмотр только своих записей** (где автор = текущий пользователь).
3. Для группы «Руководители» — просмотр **всех** записей или только своего отдела.
4. Для группы «Администраторы» — полный доступ.

> На этапе разработки удобно держать «Всем на изменение», но перед выкаткой в прод — **обязательно настроить реальные права**.

## Пошаговые инструкции

### Создание нового процесса в Живой Ленте

1. Открыть **Живую Ленту** в Bitrix24.
2. Нажать **«Новый процесс»**.
3. Ввести название: `Заявки на затраты`.
4. Сортировка: `1`.
5. Раздел «Доступ» → выбрать «Всем на изменение» (временно).
6. Сохранить.
7. Перейти в созданный процесс → **Действия** → **Настроить поля**.
8. Добавить поля: Сумма, Описание целей, Счёт на оплату (файл), Статус (список).
9. Для поля «Статус» добавить значения: «На рассмотрении», «Одобрено», «Отклонено», «Отозвана».
10. Скрыть поле «Статус» из формы создания.

### Создание шаблона БП

1. Перейти в процесс → **Действия** → **Настроить бизнес-процессы**.
2. Нажать **«Создать последовательный бизнес-процесс»**.
3. В настройках шаблона включить запуск **«При добавлении»** и **«При изменении»**.
4. Открыть **дизайнер** и начать добавлять действия.

### Добавление условия с двумя ветками

1. В дизайнере добавить действие **«Условие»**.
2. Настроить проверку: `{=Document:FIELD_SUMMA} > 15000`.
3. В ветку **«Да»** добавить действия согласования с бухгалтером.
4. В ветку **«Нет»** / **«Иначе»** — завершение процесса (или другая логика).

### Добавление константы

1. В дизайнере → вкладка **«Константы»**.
2. Нажать **«Добавить константу»**.
3. Имя: `BUHGALTER`, тип: `Пользователь`.
4. Значение: выбрать конкретного сотрудника — главного бухгалтера.
5. Сохранить. Далее использовать `{=Constant:BUHGALTER}` в действиях.

## Главное

1. **Сначала — сценарий на словах.** Прежде чем открывать дизайнер, опиши логику: кто что делает, при каких условиях, что происходит при отказе.

2. **Объект для БП — Живая Лента или Список.** Они позволяют добавить произвольные поля, в отличие от файлов. Поле «Статус» (тип список) — стандартный способ отображать состояние записи.

3. **Руководителя определяй динамически** через организационную структуру, а не хардкодом — БП останется рабочим при смене людей.

4. **Бухгалтер (фиксированная роль) — константа.** Значение меняется редко и в одном месте. Это лучше, чем вписывать ID пользователя в каждое действие.

5. **Переменная-флаг управляет ветками.** Вместо дублирования условий, меняй значение переменной — и используй её в одном месте для принятия решения о направлении процесса.

6. **Цикл + «возможность сдаться»** = правильная реализация итеративного согласования. Без ограничения числа итераций цикл может зависнуть — всегда задавай максимум.

7. **Поле «Статус» меняет БП, не пользователь.** Скрывай технические поля из формы создания; они управляются только автоматически.

8. **Лог — главный инструмент отладки.** Вставляй «Запись в журнал» в ключевых точках, проверяй значения переменных, затем убирай лишнее.

9. **Права доступа — последний шаг, но не менее важный.** Типовой сценарий: сотрудник видит только свои записи. Настраивать права нужно до выхода в прод.

10. **Действие «Запрос данных»** позволяет получать ввод пользователя прямо в ходе процесса и сохранять его в поля документа — это основа для реализации доработки заявки.
