# Урок 5.10: Параметры БП и работа с элементами списков — Создание, изменение и чтение элементов

## О чём этот урок

Урок посвящён работе с элементами списков напрямую из бизнес-процесса без необходимости запускать отдельный дочерний БП. Рассматриваются три ключевых действия: **создание**, **изменение** и **чтение** элементов списка. На практическом примере со списком «Поставщики» и «Заявки» показывается, как автоматически создавать новые записи, обновлять существующие и читать данные из связанных элементов.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Элемент списка** | Запись в пользовательском списке Bitrix24 (например, строка в списке «Поставщики») |
| **Создание элемента списка** | Действие в БП, автоматически добавляющее новую запись в указанный список |
| **Изменение элемента списка** | Действие в БП, обновляющее поля существующей записи в списке |
| **Чтение элемента списка** | Действие в БП, получающее данные из конкретной записи для использования в условиях и действиях |
| **Параметр БП** | Переменная, передаваемая в бизнес-процесс при его запуске (вручную или из другого БП) |
| **Результат действия** | Данные, возвращаемые действием после выполнения (например, ID созданного элемента) |
| **Ветка условия** | Ветвление в схеме БП, определяющее, по какому пути пойдёт выполнение в зависимости от значения |
| **Надёжность** | Пользовательское поле типа «Список» в примере урока — характеристика поставщика |
| **Сумма последней заявки** | Пользовательское числовое поле в примере урока — хранит актуальную сумму |

---

## Три действия для работы с элементами списков

В Bitrix24 есть три специализированных действия, позволяющих работать с записями списков **без запуска дочернего бизнес-процесса**:

1. **Создание элемента списка** — добавляет новую запись
2. **Изменение элемента списка** — обновляет поля существующей записи
3. **Чтение элемента списка** — получает данные из записи для последующего использования

> Это альтернатива схеме «запуск БП из БП» — проще, быстрее и прямолинейнее, когда не нужна сложная логика на стороне дочернего процесса.

---

## Подготовка: расширение списка «Поставщики»

Перед демонстрацией действий в список «Поставщики» добавляются два дополнительных поля:

- **Сумма последней заявки** — числовое поле, будет обновляться автоматически при каждой новой заявке
- **Надёжность** — поле типа «Список» с несколькими заданными значениями (например: Высокая / Средняя / Низкая)

Одному из существующих поставщиков вручную задаётся значение поля «Надёжность» для последующего тестирования.

## Раздел 1: Создание элемента списка

### Задача

Сейчас в бизнес-процессе можно выбрать поставщика только из уже существующих в системе. Нужно добавить возможность указать **нового** поставщика, которого система автоматически создаст в списке.

### Логика решения

```
Запрос параметра "Новый поставщик" (строка)
        ↓
Условие: указан ли новый поставщик?
    ├── ДА → Создать элемент в списке «Поставщики»
    │         ↓
    │         Записать ID нового элемента в поле «Поставщик» заявки
    └── НЕТ → [продолжить обычный сценарий]
```

### Пошаговая инструкция

#### Шаг 1: Добавить параметр «Новый поставщик»
1. Открыть редактор бизнес-процесса
2. Перейти в настройки параметров процесса
3. Добавить новый параметр:
   - **Название:** Новый поставщик
   - **Тип:** Строка *(не «Привязка к элементу», потому что объекта ещё не существует)*
4. Сохранить параметр

#### Шаг 2: Добавить ветку условия
1. В схеме БП добавить блок **«Условие»**
2. Задать простое условие: *«Параметр "Новый поставщик" не пустой»*
3. Создать ветку **«Да»** (новый поставщик указан) — здесь будет создаваться элемент

#### Шаг 3: Настроить действие «Создание элемента списка»
1. В ветку «Да» добавить действие **«Создание элемента списка»**
2. Указать целевой список: **«Поставщики»**
3. Заполнить поля нового элемента:
   - **Название** → выбрать из параметров: `{Новый поставщик}`
   - Остальные поля заполнить при необходимости или оставить пустыми
4. Сохранить действие

#### Шаг 4: Записать ID нового поставщика в заявку
1. После действия создания добавить **«Изменение документа»** (или аналогичное действие обновления заявки)
2. Для поля **«Поставщик»** выбрать источник значения: **«Результат действия»**
3. Выбрать действие создания элемента → оно возвращает **ID** созданной записи
4. Сохранить

> **Ключевой момент:** Действие «Создание элемента списка» возвращает **ID** нового элемента. Этот ID нужно использовать, чтобы сразу же привязать нового поставщика к текущей заявке.

### Результат

После запуска БП:
- В поле «Поставщик» заявки появляется значение «Новая компания» (или любое другое переданное название)
- В списке «Поставщики» автоматически создаётся новая запись с этим названием

## Раздел 2: Изменение элемента списка

### Задача

Передать данные в связанный элемент списка напрямую — без запуска дочернего БП. Например: при создании заявки автоматически обновлять у выбранного поставщика поле **«Сумма последней заявки»**.

### Логика решения

```
Заявка создана / обработана
        ↓
Действие «Изменение элемента списка»
    Список: «Поставщики»
    Элемент: ID поставщика из поля заявки
    Поле: Сумма последней заявки = Сумма текущей заявки
```

### Пошаговая инструкция

1. В схему БП добавить действие **«Изменение элемента списка»**
2. Указать список: **«Поставщики»**
3. Указать ID элемента: взять из поля «Поставщик» текущей заявки
4. Выбрать поле для обновления: **«Сумма последней заявки»**
5. Задать новое значение: взять из поля «Сумма» текущей заявки (через переменную документа)
6. Сохранить

> **Преимущество:** Это значительно проще, чем запускать отдельный бизнес-процесс на списке «Поставщики». Данные передаются одним действием.

---

## Раздел 3: Чтение элемента списка

### Задача

Получить данные из записи связанного списка (например, прочитать поле «Надёжность» у выбранного поставщика) и использовать эти данные в условиях или сообщениях внутри текущего БП.

### Логика решения

```
Действие «Чтение элемента списка»
    Список: «Поставщики»
    Элемент: ID поставщика из поля заявки
        ↓
Данные поставщика доступны как переменные:
    - Надёжность
    - Сумма последней заявки
    - и другие поля
        ↓
Используем «Надёжность» в условии:
    ├── Высокая → особый сценарий обработки
    └── Другое → стандартный сценарий
```

### Пошаговая инструкция

1. Добавить действие **«Чтение элемента списка»**
2. Указать список: **«Поставщики»**
3. Указать ID элемента: из поля «Поставщик» заявки
4. Сохранить действие — теперь все поля элемента доступны через **«Результат действия»**
5. Добавить блок **«Условие»** после чтения
6. В условии использовать: `{Результат чтения → Надёжность} = "Высокая"`
7. Настроить ветки условия под бизнес-логику

## Добавление значения в массив

В уроке упоминается, что в бизнес-процессах Bitrix24 есть возможность **добавления значения в массив** — это полезно при накопительных сценариях, когда нужно хранить несколько значений в одном поле или передавать список данных между действиями.

> Подробности реализации в контексте урока не детализируются, но это важная возможность, о которой стоит помнить при проектировании сложных БП.

---

## Запуск бизнес-процесса из бизнес-процесса (контекст урока)

Этот урок является частью более широкой темы модуля. До перехода к прямой работе с элементами рассматривался подход **«БП из БП»**:

- Создаётся отдельный БП для списка «Поставщики»
- Он запускается из БП для «Заявок» через специальное действие
- Через **параметры** передаются нужные значения из родительского в дочерний БП

**Когда использовать «БП из БП»:** когда нужна сложная логика обработки на стороне связанного объекта.  
**Когда использовать прямые действия (создание/изменение/чтение):** когда нужно просто передать данные или прочитать поле — без сложной логики.

---

## Пошаговые инструкции (сводная)

### Полный сценарий: «Новый поставщик» через параметр

```
1. Добавить параметр «Новый поставщик» (тип: Строка)
2. Добавить условие: «Новый поставщик» не пустой
3. В ветке «Да»:
   a. Действие «Создание элемента списка» (Поставщики)
      - Название = {Параметр: Новый поставщик}
   b. Действие «Изменить документ» (Заявка)
      - Поле «Поставщик» = {Результат создания: ID}
4. В ветке «Нет»:
   - Продолжить с уже выбранным поставщиком
```

### Обновление данных поставщика при создании заявки

```
1. Действие «Изменение элемента списка» (Поставщики)
   - ID = {Заявка: Поставщик}
   - Сумма последней заявки = {Заявка: Сумма}
```

### Чтение данных поставщика для условий

```
1. Действие «Чтение элемента списка» (Поставщики)
   - ID = {Заявка: Поставщик}
2. Условие: {Результат чтения: Надёжность} = нужное значение
3. Ветки по значению надёжности
```

## Главное

1. **Три прямых действия** — «Создание», «Изменение» и «Чтение» элемента списка — позволяют работать с данными связанных объектов без необходимости запускать дочерний бизнес-процесс.

2. **Действие «Создание элемента»** возвращает **ID** созданной записи — его нужно сразу использовать, если требуется привязать новый элемент к текущему документу.

3. **Параметр типа «Строка»** используется для передачи названия нового объекта, которого ещё нет в системе — потому что привязку к несуществующему элементу задать невозможно.

4. **Ветка условия** — стандартный способ разделить логику: «поставщик уже существует» vs «нужно создать нового».

5. **Действие «Изменение элемента»** — самый простой способ передать данные в связанный объект: одно действие вместо целого дочернего бизнес-процесса.

6. **Действие «Чтение элемента»** открывает доступ к данным другого объекта и позволяет строить условия на основе его полей — тем самым расширяя бизнес-логику текущего БП.

7. **Выбор подхода:** прямые действия (создание/изменение/чтение) — для простой передачи данных; «БП из БП» — для сложной логики на стороне связанного объекта.

8. **Поля типа «Список»** (например, «Надёжность») могут использоваться как критерии ветвления — это позволяет строить сценарии с разным поведением в зависимости от характеристик связанного объекта.

9. **Добавление значения в массив** — ещё одна полезная возможность БП для накопительных и агрегирующих сценариев.

10. Всё описанное **работает как для списков, так и для объектов CRM** — принципы применимы к сделкам, контактам, компаниям и другим сущностям Bitrix24.
