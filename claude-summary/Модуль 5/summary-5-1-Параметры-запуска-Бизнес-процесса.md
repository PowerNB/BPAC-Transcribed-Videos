# Параметры БП и работа с элементами списков

**Модуль 5 · Урок 10 из 14 · 26 мин**

---

## О чём этот урок

Урок посвящён двум мощным механизмам бизнес-процессов Bitrix24: **параметрам запуска** и **работе с элементами списков/CRM**. Параметры позволяют передавать данные в БП в момент его старта — либо от пользователя, либо из другого бизнес-процесса. Работа с элементами списков даёт возможность читать, создавать и изменять записи в других «документах» прямо внутри логики БП, без ручного вмешательства.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Параметры БП** | Переменные, значения которых запрашиваются у пользователя (или передаются из другого БП) в момент запуска бизнес-процесса |
| **Обязательный параметр** | Параметр, без указания значения которого бизнес-процесс не запустится |
| **Множественный параметр** | Параметр, допускающий несколько значений (например, несколько пользователей) |
| **Тип «Привязка к пользователю»** | Тип параметра для выбора одного или нескольких сотрудников системы |
| **Тип «Привязка к элементам»** | Тип параметра/поля для выбора записи из другого списка (например, поставщика из списка «Поставщики») |
| **Запуск БП из БП** | Механизм, при котором один бизнес-процесс инициирует запуск другого и передаёт ему параметры |
| **Элемент списка** | Запись в разделе «Списки» Bitrix24 (например, «Поставщики», «Заявки») |
| **Массив в БП** | Переменная-коллекция, в которую можно последовательно добавлять значения |
| **Создание элемента списка** | Действие БП, автоматически добавляющее новую запись в указанный список |
| **Изменение элемента списка** | Действие БП, обновляющее поля существующей записи в списке |
| **Чтение элемента списка** | Действие БП, загружающее данные существующей записи для использования в условиях и действиях |
| **Утверждение голосованием** | Тип действия согласования, при котором документ утверждается если проголосовало «за» не менее половины участников |

## Параметры запуска бизнес-процесса

### Что такое параметры и зачем они нужны

При запуске бизнес-процесса пользователю может автоматически показываться форма с полями для заполнения. Введённые данные становятся **переменными внутри БП** и доступны во всех последующих действиях.

**Ключевое отличие от полей документа:**
- У документов в Живой ленте или CRM есть собственные поля, доступные в БП автоматически
- У файлов на **Диске** таких полей нет — единственный способ передать нужные данные — это параметры
- Параметры также незаменимы, когда БП запускается **не в момент создания элемента** (например, по кнопке или по расписанию), и данные из формы создания недоступны

### Пример: БП согласования документа на Диске

Классический пример использования параметров — бизнес-процесс согласования файла:

1. Пользователь запускает БП для файла на Диске
2. Появляется окно с просьбой **указать согласующих сотрудников**
3. Указанные сотрудники сохраняются в параметр типа «Привязка к пользователю»
4. Действие «Утверждение документа» получает список согласующих **из этого параметра**

### Настройка параметра в шаблоне БП

Параметры настраиваются в разделе **«Параметры»** шаблона бизнес-процесса.

Для каждого параметра задаётся:
- **Название** — отображается в форме запуска
- **Тип** — определяет вид поля (текст, число, пользователь, дата, привязка к элементу и т.д.)
- **Обязательность** — если включено, БП не запустится без заполнения этого поля
- **Множественность** — если включено, можно указать несколько значений

### Пример параметра из урока (процесс в Живой ленте)

```
Название:     Поставщик
Тип:          Привязка к элементам
Обязательный: Нет  (сделан необязательным намеренно — чтобы обработать случай «не указан»)
Множественный: Нет
Связанный список: Процесс «Поставщики» (в Живой ленте)
```

> **Важно:** параметр сделан необязательным намеренно. Внутри БП добавлено условие: «если данные указаны». Это позволяет обработать оба случая (указан/не указан) и подготовить БП к будущим доработкам. Если бы параметр был обязательным, БП просто не запустился бы без него — этот вариант тоже допустим, но менее гибкий.

### Где применяются параметры

- **Файлы на Диске** — основной сценарий, т.к. нет собственных полей
- **Живая лента** — дополнительные данные, не предусмотренные в форме процесса
- **CRM-объекты** — когда БП запускается вручную, а не при создании/изменении
- **Списки** — аналогично CRM
- **Запуск БП из БП** — для передачи данных из родительского процесса в дочерний

## Создание параметра для процесса в Живой ленте: разбор примера

### Постановка задачи

В учебном примере уже есть список «Заявки» с бизнес-процессом согласования. После согласования заявку **нельзя редактировать** (это намеренное ограничение из предыдущих уроков). Однако нужно дать возможность **указывать и менять поставщика** — даже после того, как заявка согласована. Решение: отдельный бизнес-процесс, запускаемый вручную.

### Шаг 1: Создать список «Поставщики»

1. Перейти в раздел **«Списки»** (или «Живая лента» → «Процессы»)
2. Добавить новый процесс — **«Поставщики»**
3. Настроить права доступа: всем на чтение (минимум)
4. Добавить несколько тестовых элементов (для тестирования БП)

> Поставщики вынесены в отдельный список намеренно — это позволит далее демонстрировать создание, изменение и чтение элементов списка.

### Шаг 2: Добавить поле «Поставщик» в список «Заявки»

1. Открыть список «Заявки» → **настройки полей**
2. Добавить новое поле:
   - **Тип:** Привязка к элементам
   - **Список/процесс:** Поставщики
   - Остальные настройки — по умолчанию
3. Сохранить поле
4. Настроить отображение колонки в списке (если нужно)

### Шаг 3: Создать бизнес-процесс «Указать поставщика»

Цель БП — запросить у пользователя значение поставщика и записать его в поле заявки.

**Режим запуска:** только вручную (не автоматически).

#### Добавить параметр:
- Тип: Привязка к элементам → Поставщики
- Обязательный: Нет
- Множественный: Нет

#### Логика БП:
```
[Условие] Параметр «Поставщик» заполнен?
  ├── ДА → [Изменить документ] Записать значение параметра в поле «Поставщик»
  │         [Запись в лог] «Поставщик обновлён»
  └── НЕТ → [Запись в лог] «Поставщик не указан, поле не изменено»
```

### Результат

При запуске БП пользователю показывается форма с полем «Поставщик». После выбора значение сохраняется в заявке. Если пользователь ничего не выбрал — БП завершается без изменений (благодаря условию).

## Запуск бизнес-процесса из бизнес-процесса

### Концепция

Один бизнес-процесс может **инициировать запуск другого**. Это позволяет:
- Декомпозировать сложные процессы на небольшие переиспользуемые блоки
- Запускать логику для **другого типа документа** (например, из БП по «Заявкам» запустить БП по «Поставщикам»)
- Передавать данные через параметры запускаемого БП

### Практический пример из урока

**Сценарий:** есть список «Заявки» и список «Поставщики». У заявок добавлено поле «Поставщик». Нужно при обработке заявки автоматически запускать бизнес-процесс для связанного поставщика.

**Шаги:**
1. Создать список **«Поставщики»** в разделе «Списки»
2. В списке «Заявки» добавить поле **«Поставщик»** (тип: привязка к элементу списка «Поставщики»)
3. Создать отдельный шаблон БП для сущности «Поставщики»
4. В БП «Заявок» добавить действие **«Запустить бизнес-процесс»**
5. Указать: какой шаблон запускать, для какого элемента, какие значения передать в параметры дочернего БП

### Передача параметров при запуске

В действии «Запустить БП» параметры дочернего процесса заполняются значениями из текущего БП — через переменные, поля документа или другие параметры.

```
Действие: Запустить бизнес-процесс
  Шаблон:   БП для Поставщиков
  Документ: {=Document:supplier_field}   ← элемент из поля «Поставщик»
  Параметры дочернего БП:
    param_order_id = {=Document:ID}
    param_amount   = {=Document:amount}
```

## Добавление значения в массив

### Зачем нужны массивы

Внутри БП иногда требуется **накапливать несколько значений** — например, собирать список ID созданных элементов, список ошибок, набор согласующих, формируемый по условиям.

Bitrix24 поддерживает переменные-массивы, и в БП есть специальное действие для добавления элемента в массив.

### Как это работает

1. Создать переменную типа «Массив» (или с признаком «Множественное»)
2. Использовать действие **«Изменить переменную»** или специальный блок добавления, чтобы дописать новое значение в конец массива
3. Использовать массив далее — передавать в параметры, в поля документа, в условия цикла

> **Ключевой момент:** массивы позволяют динамически формировать наборы данных в ходе выполнения БП, что открывает возможность для сложных сценариев с циклами и агрегацией.

## Создание элемента списка

### Концепция

Бизнес-процесс может **автоматически создавать новые записи** в любом доступном списке Bitrix24 — без участия пользователя.

### Практический пример из урока

**Задача:** пользователь при заполнении заявки может указать нового поставщика (которого ещё нет в списке). БП должен автоматически создать запись в списке «Поставщики».

**Логика:**
1. В форме заявки (или через параметр БП) пользователь вводит **название нового поставщика** текстом
2. БП проверяет: существующий поставщик выбран или введён новый?
3. Если новый — выполняется действие **«Создать элемент списка»**
4. Созданный элемент возвращает свой **ID**, который можно сохранить в переменную
5. ID нового поставщика записывается в поле «Поставщик» заявки

### Настройка действия «Создать элемент списка»

```
Действие: Создать элемент списка
  Список:         Поставщики
  Поля для заполнения:
    Название:     {=Parameter:new_supplier_name}
    Статус:       Новый
    ...
  Сохранить ID в: переменная new_supplier_id
```

## Изменение элемента списка

### Концепция

БП может **обновлять поля существующей записи** в списке — это альтернативный способ передать данные в другой элемент, не запуская для него отдельный бизнес-процесс.

### Практический пример из урока

**Задача:** в карточке поставщика хранить сумму последней заявки, связанной с ним.

**Логика:**
1. При завершении обработки заявки — выполнить действие **«Изменить элемент списка»**
2. Указать: какой элемент (поставщик из поля «Поставщик» заявки)
3. Указать: какое поле обновить («Сумма последней заявки») и какое значение записать

### Когда использовать вместо «Запуска БП из БП»

| Сценарий | Подход |
|---|---|
| Нужно выполнить **сложную логику** для другого элемента (уведомления, согласования, условия) | Запуск БП из БП |
| Нужно просто **записать данные** в поля другого элемента | Изменение элемента списка |

> **Совет:** «Изменение элемента» — более простой и производительный способ, когда не нужна бизнес-логика, а нужна только синхронизация данных.

## Чтение элемента списка

### Концепция

БП может **загрузить данные из другого элемента** списка или CRM и использовать их в своей логике — в условиях, в текстах уведомлений, в расчётах.

### Практический пример из урока

**Задача:** при обработке заявки получить данные о выбранном поставщике (например, лимит кредита, категорию, контактное лицо) и применить их в условиях БП.

**Логика:**
1. Использовать действие **«Читать элемент списка»**
2. Указать: из какого списка («Поставщики»), какой элемент (из поля «Поставщик» заявки)
3. Поля прочитанного элемента становятся доступны как переменные: `{=читать_поставщика:credit_limit}` и т.д.
4. Добавить **условия**, которые ветвят логику БП в зависимости от данных поставщика

### Что открывает эта возможность

- Персонализировать обработку на основе связанных данных
- Проверять бизнес-правила («сумма заявки не превышает лимит поставщика»)
- Подставлять данные поставщика в уведомления и документы

## Пошаговые инструкции

### Как добавить параметр в шаблон БП

1. Открыть шаблон бизнес-процесса (раздел «Списки» → нужный список → «Бизнес-процессы» → «Шаблоны» → открыть шаблон)
2. В левой панели редактора найти раздел **«Параметры»**
3. Нажать **«Добавить параметр»**
4. Заполнить:
   - **Название** — имя, которое увидит пользователь
   - **Идентификатор** — системное имя (латиница, без пробелов)
   - **Тип** — выбрать из списка (пользователь, текст, число, дата, привязка к элементу и т.д.)
   - **Обязательный** — включить если нужно
   - **Множественный** — включить для нескольких значений
5. Сохранить параметр
6. В нужных действиях БП обращаться к параметру через кнопку выбора переменных → раздел «Параметры»

### Как использовать параметр в действии

1. Открыть настройки нужного действия (например, «Утверждение документа»)
2. В поле «Участники» нажать на иконку выбора переменной (часто выглядит как `{...}` или кнопка справа от поля)
3. В открывшемся окне перейти в раздел **«Параметры»**
4. Выбрать нужный параметр
5. Сохранить

### Как добавить поле «Поставщик» в список «Заявки»

1. Перейти в **«Списки»** → открыть список «Заявки»
2. Нажать **«Настройки»** (или «Поля» / «Свойства элемента»)
3. Добавить новое поле:
   - **Тип:** Привязка к элементу списка
   - **Связанный список:** Поставщики
   - **Название:** Поставщик
4. Сохранить
5. При необходимости настроить отображение нового поля в списке

### Как создать список «Поставщики» в Живой ленте

1. Перейти в **«Живая лента»** → **«Процессы»** (или «Списки»)
2. Добавить новый процесс — **«Поставщики»**
3. Настроить права: минимум — чтение для всех сотрудников
4. Добавить тестовые элементы (несколько записей поставщиков для тестирования)

### Как настроить запуск БП из БП

1. В шаблоне родительского БП добавить действие **«Запустить бизнес-процесс»** (ищется в группе «Другие» или «Процессы»)
2. Настроить:
   - **Тип документа** — выбрать тип, для которого создан дочерний БП
   - **Документ** — указать конкретный элемент (из переменной или поля)
   - **Шаблон** — выбрать нужный шаблон дочернего БП
   - **Параметры** — заполнить параметры дочернего БП значениями из текущего
3. Указать: **ждать завершения** дочернего БП или продолжить параллельно
4. Сохранить

### Как читать, создавать и изменять элементы списка

**Чтение:**
1. Добавить действие **«Читать элемент»** (группа «Список»)
2. Указать список и ID элемента (из поля-привязки)
3. Выбрать, в какие переменные сохранить поля

**Создание:**
1. Добавить действие **«Создать элемент»**
2. Указать список и заполнить нужные поля значениями
3. Сохранить ID созданного элемента в переменную

**Изменение:**
1. Добавить действие **«Изменить элемент»**
2. Указать список, ID элемента (из переменной или поля)
3. Указать поля и новые значения для них

## Главное

1. **Параметры = форма при запуске.** Когда у документа нет собственных полей (файлы на Диске) или когда БП запускается вручную — параметры единственный способ получить нужные данные от пользователя.

2. **Параметр необязательным + условие — гибче, чем обязательным.** Если сделать параметр необязательным и добавить проверку внутри БП, процесс можно запускать и без данных — и корректно обрабатывать оба сценария. Обязательный параметр проще, но не оставляет выбора.

3. **Тип параметра «Привязка к элементам» = выбор из другого списка.** Позволяет пользователю выбирать записи из другого списка (например, поставщика) прямо в форме запуска БП — без ручного ввода.

4. **Параметры работают везде.** Их можно использовать в БП для Живой ленты, CRM-объектов, Списков и Диска — везде, где есть смысл запрашивать данные при старте.

5. **Запуск БП из БП — для сложной логики.** Если при обработке одного элемента нужно выполнить серьёзную бизнес-логику (согласования, уведомления, условия) для другого — запускайте отдельный БП и передавайте данные через параметры.

6. **Изменение элемента — для простой синхронизации.** Если нужно просто записать данные в поля другого элемента — используйте «Изменить элемент», это проще и не порождает лишних процессов.

7. **Чтение элемента расширяет логику БП.** Загружая данные из связанных записей (поставщик, клиент, товар), можно принимать умные решения внутри процесса — проверять лимиты, подставлять реквизиты, ветвить сценарии.

8. **Создание элемента = автоматический ввод данных.** БП может сам добавлять новые записи в списки — это убирает ручной труд при регистрации новых сущностей (поставщики, контрагенты и т.д.).

9. **Массивы нужны для динамических наборов.** Когда количество значений заранее неизвестно — используйте переменные-массивы с последовательным добавлением элементов.

10. **Связанные списки = реляционная логика без базы данных.** Поле типа «Привязка к элементу списка» + действия чтения/изменения позволяют строить межсписочные зависимости и реализовывать сложные сценарии, близкие к реляционным базам данных.
