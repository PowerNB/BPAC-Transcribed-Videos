# Чтение элемента списка

## О чём этот урок

Урок посвящён действию **«Чтение элемента списка»** в бизнес-процессах Bitrix24. На практическом примере показано, как получить данные из связанного элемента другого списка (в данном случае — из справочника «Поставщики») и использовать эти данные для построения условий и ветвления логики процесса. Это завершающий раздел модуля 5, объединяющий ранее изученные механизмы: параметры, переменные, условия и работу с элементами списков.

---

## Основные понятия

| Термин | Описание |
|---|---|
| **Чтение элемента списка** | Действие в дизайнере БП, которое позволяет получить значения полей произвольного элемента списка/объекта CRM по его ID |
| **ID элемента** | Уникальный идентификатор элемента списка, по которому происходит его поиск и чтение |
| **Тип документа** | Настройка действия — указывает, из какого именно списка или объекта нужно читать данные |
| **Дополнительные результаты** | Специальный раздел в вставке значений, где доступны данные, возвращённые конкретным действием БП |
| **Переменная** | Именованная ячейка памяти внутри бизнес-процесса, в которую сохраняется значение для дальнейшего использования |
| **Преобразование к строке** | Явное указание типа значения при вставке из результатов действия — особенно важно для списковых полей |
| **Списковое поле** | Поле типа «список» (dropdown / enum), значение которого хранится как внутренний ключ, а не текст |
| **Условие в БП** | Проверка значения переменной (или поля) с последующим ветвлением на ветки «Да» / «Нет» |
| **Запись в отчёт** | Действие для отладки и мониторинга — фиксирует текстовое сообщение в журнале выполнения БП |

---

## Действие «Чтение элемента списка»

### Назначение

Позволяет **внутри бизнес-процесса** обратиться к произвольному элементу любого списка Bitrix24 и получить значения его полей. Это даёт возможность строить логику, опирающуюся на данные из связанных справочников — например, читать характеристики поставщика при обработке заявки.

### Настройка действия

При добавлении действия в дизайнере нужно указать три группы параметров:

1. **ID элемента** — идентификатор того элемента, который нужно прочитать.
   - В примере урока: ID поставщика, выбранного в заявке (передаётся как значение поля «Поставщик»).

2. **Тип документа** — список или объект CRM, в котором находится элемент.
   - В примере: список **«Поставщики»**.

3. **Поля для чтения** — выбираются только те поля, которые реально понадобятся в дальнейшем.
   - В примере: поле **«Надёжность»** (одно поле для демонстрации).

> **Принцип минимальности:** не нужно читать все поля подряд — выбирайте только те, что будут использоваться в логике процесса.

---

## Сохранение результата в переменную

### Почему нельзя использовать результаты действия напрямую в условии

В дизайнере Bitrix24 **условие (ветвление)** работает с типом «значение переменных», а не с «дополнительными результатами» действия. Поэтому после чтения элемента необходимо **явно пересохранить** нужное значение в переменную.

### Пошаговое сохранение

1. Добавить действие **«Установить переменную»** (или изменить переменную).
2. Выбрать переменную подходящего типа — в примере: **тип «Строка»**.
3. В поле значения открыть вставку значений → раздел **«Дополнительные результаты»**.
4. Найти действие чтения элемента списка → выбрать нужное поле (**«Надёжность»**).
5. Указать преобразование к нужному типу — **«Преобразовать к строке»**.

### Зачем преобразовывать к строке

Поле «Надёжность» является **списковым** (хранит внутренний ключ значения). При сравнении в условии удобнее работать с текстовым представлением. Хотя система может подставить тип автоматически, рекомендуется указывать его **явно** — это исключает неожиданное поведение при сравнении.

## Построение условия на основе прочитанных данных

### Настройка ветвления

После сохранения данных в переменную добавляется действие **«Условие»**:

| Параметр | Значение в примере |
|---|---|
| **Тип сравнения** | Значение переменной |
| **Переменная** | «Надёжность» |
| **Оператор** | Равно |
| **Значение** | `низкая` |

### Ветки условия

- **Ветка «Да» (надёжность = низкая):** отправка уведомления пользователям + запись в отчёт с меткой «поставщик с низкой надёжностью».
- **Ветка «Нет»:** стандартная обработка + запись в отчёт с меткой «поставщик указан».

## Пошаговые инструкции

### Полный алгоритм реализации чтения элемента и условия

```
1. Открыть дизайнер бизнес-процесса (список «Заявки»).

2. Добавить действие «Чтение элемента списка»:
   - ID элемента    → вставить значение поля «Поставщик» из текущей заявки
   - Тип документа  → выбрать список «Поставщики»
   - Поля           → отметить нужные поля (напр., «Надёжность»)

3. Добавить действие «Установить переменную»:
   - Тип переменной → Строка
   - Имя            → например, «НадёжностьПоставщика»
   - Значение       → Дополнительные результаты
                      → «Чтение элемента списка» → поле «Надёжность»
                      → Преобразовать к строке

4. Добавить действие «Условие»:
   - Тип            → Значение переменной
   - Переменная     → «НадёжностьПоставщика»
   - Оператор       → Равно
   - Значение       → «низкая»

5. В ветку «Да» добавить:
   - Уведомление пользователям о низкой надёжности поставщика
   - Запись в отчёт: «Поставщик с низкой надёжностью»

6. В ветку «Нет» добавить:
   - Запись в отчёт: «Поставщик указан»

7. Сохранить бизнес-процесс.

8. Проверить: запустить заявку с поставщиком «ООО Мебель»
   (у которого надёжность = «низкая»), убедиться в журнале,
   что БП прошёл по ветке «Да».
```

## Отладка и проверка результата

### Использование «Записи в отчёт»

Для понимания, по какой ветке прошёл бизнес-процесс, в каждую ветку условия добавляются **записи в отчёт** с понятными текстовыми метками. Это стандартная практика при разработке и отладке БП в Bitrix24.

### Просмотр журнала

После запуска БП открыть **лог (журнал) выполнения**. В примере из урока лог показал две записи:
1. `«Поставщик указан»` — базовая ветка выполнилась.
2. `«Поставщик с низкой надёжностью»` — условие сработало корректно.

Это подтвердило, что процесс прошёл именно по той ветке, которая была запланирована.

## Главное

1. **Действие «Чтение элемента списка»** позволяет получить поля любого элемента списка или CRM-объекта прямо внутри бизнес-процесса — без необходимости запускать отдельный БП для этого документа.

2. **Три обязательных параметра** действия: ID элемента, тип документа (список/объект), выбранные поля для чтения.

3. **Результаты действия нельзя использовать в условии напрямую** — необходимо сначала сохранить нужное значение в переменную через «Дополнительные результаты».

4. **Для списковых полей** при сохранении в переменную рекомендуется явно указывать преобразование к строке, чтобы избежать ошибок сравнения.

5. **Тип сравнения в условии — «Значение переменной»** — именно этот режим обеспечивает доступ к данным, полученным из прочитанного элемента.

6. **Записи в отчёт в каждой ветке** — обязательная практика при разработке условий: они позволяют быстро проверить, по какой ветке прошёл процесс.

7. **Чтение элемента списка + условие** даёт возможность строить сложную адаптивную логику, зависящую от характеристик связанных объектов (надёжность поставщика, статус клиента, категория товара и т.д.).

8. **Цепочка «ID → Чтение → Переменная → Условие»** — универсальный паттерн для работы с данными из связанных списков в любом бизнес-процессе Bitrix24.

9. Проверять работу БП нужно на **реальных тестовых данных** с известными значениями полей — в примере намеренно выбран поставщик с заранее установленной низкой надёжностью.

10. Действие «Чтение элемента списка» **не запускает бизнес-процесс** связанного элемента — это лёгкий способ получить данные без побочных эффектов, в отличие от «Запуска БП из БП».
