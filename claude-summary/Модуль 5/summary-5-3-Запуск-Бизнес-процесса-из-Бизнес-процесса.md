# Запуск бизнес-процесса из бизнес-процесса

## О чём этот урок

Урок посвящён механизму запуска одного бизнес-процесса из другого с передачей параметров между ними. На практическом примере показано, как бизнес-процесс по заявкам может автоматически запускать бизнес-процесс по поставщикам и передавать ему данные — ID заявки, которая инициировала запуск. Это позволяет связывать данные между разными объектами системы без ручных действий пользователя.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Параметр бизнес-процесса** | Переменная, которая передаётся в БП извне при его запуске — из интерфейса пользователя или из другого БП |
| **Запуск БП из БП** | Действие внутри одного бизнес-процесса, которое инициирует старт другого бизнес-процесса по другому объекту системы |
| **ID документа** | Уникальный идентификатор конкретного объекта (элемента списка, записи CRM и т.д.), по которому запускается дочерний БП |
| **Привязка к элементам** | Тип поля / параметра, хранящего ссылку (ID) на другой элемент системы |
| **Процесс в Живой ленте** | Сущность Bitrix24, аналог списка, поддерживающая бизнес-процессы; в уроке — «Поставщики» |
| **Множественное поле** | Поле, способное хранить несколько значений одновременно (например, несколько привязанных заявок) |
| **Шаблон БП** | Конфигурация бизнес-процесса, привязанная к конкретному процессу/списку; система подгружает доступные шаблоны при выборе сущности |

---

## Сценарий: связь «Заявки» ↔ «Поставщики»

### Общая идея

Есть два объекта:
- **Заявки на затраты** — основной объект, у которого запускается БП пользователем
- **Поставщики** — вспомогательный объект (процесс в Живой ленте)

Цель: когда в заявке выбирается поставщик, нужно автоматически зафиксировать эту заявку в карточке самого поставщика. Делается это через цепочку: БП заявки → запускает → БП поставщика → записывает данные.

### Почему нельзя просто записать напрямую

БП заявки работает в контексте заявки. Поле «Заявки» находится в объекте поставщика. Чтобы изменить данные в другом объекте, нужно запустить БП именно по этому объекту — отсюда механизм «запуск БП из БП».

---

## Шаг 1. Подготовка объекта «Поставщики»

### 1.1. Добавление поля «Заявки» в поставщике

1. Открыть настройки процесса **«Поставщики»** в Живой ленте
2. Добавить новое поле с типом **«Привязка к элементам»**
3. В настройках поля указать привязку к **«Заявкам на затраты»** (нужный список/процесс)
4. Включить опцию **«Множественное»** — чтобы поле могло хранить несколько заявок
5. Сохранить

> **Зачем множественное:** один поставщик может фигурировать в нескольких заявках. Если поле одиночное — каждая новая заявка перезапишет предыдущую.

---

## Шаг 2. Создание бизнес-процесса для «Поставщиков»

### 2.1. Создать новый шаблон БП

1. Перейти в настройки процесса **«Поставщики»**
2. Создать новый шаблон бизнес-процесса, например с именем **«Установить заявки»**
3. Настроить запуск: **не автоматически** — БП будет запускаться только из другого БП

### 2.2. Добавить параметр «Заявка»

1. В редакторе шаблона открыть **параметры бизнес-процесса**
2. Добавить параметр:
   - **Название:** Заявка (или «Заявка-источник»)
   - **Тип:** Привязка к элементам → Заявки на затраты
3. Сохранить параметр

> **Зачем параметр:** ID заявки нельзя получить изнутри этого БП, т.к. он запущен по поставщику, а не по заявке. Значение приходит снаружи — из вызывающего БП.

### 2.3. Добавить действие «Изменить документ»

1. Добавить в процесс единственное действие — **изменение/сохранение документа** (поставщика)
2. В настройке действия найти поле **«Заявки»**
3. В качестве значения указать **параметр «Заявка»**, переданный в БП
4. Сохранить шаблон

Итог: БП поставщика принимает ID заявки → записывает его в поле «Заявки» у поставщика.

---

## Шаг 3. Доработка бизнес-процесса по «Заявкам»

### 3.1. Найти нужную ветку

В существующем БП по заявкам уже есть условное ветвление: одна ветка — поставщик выбран, другая — не выбран. Работаем в ветке **«Поставщик выбран»**.

### 3.2. Добавить действие «Запуск бизнес-процесса»

1. В ветку «Поставщик выбран» добавить действие **«Запуск бизнес-процесса»**
2. Настроить параметры действия:

#### Параметр: ID документа
- Это **конкретный объект**, по которому запустится дочерний БП
- В данном случае — конкретный поставщик, выбранный пользователем в заявке
- Источник значения: **параметр текущего БП «Поставщик»** (то, что пользователь выбрал при запуске)

#### Параметр: Сущность
- Здесь перечислены все объекты Bitrix24, поддерживающие БП
- Выбрать **«Процессы»** (т.к. «Поставщики» — это процесс в Живой ленте)

#### Параметр: Процесс
- Выбрать конкретный процесс — **«Поставщики»**
- После выбора система подгрузит все шаблоны БП, привязанные к этому процессу

#### Параметр: Шаблон
- Выбрать **«Установить заявки»** (созданный на шаге 2)
- После выбора шаблона система покажет его параметры

#### Параметр: Заявка (параметр дочернего БП)
- Передать **ID текущей заявки** — системная переменная текущего документа
- Это тот ID, который будет записан в поле поставщика

3. Сохранить действие и шаблон БП

## Итоговая схема работы

```
Пользователь запускает БП по Заявке
    │
    ├── [Условие: Поставщик выбран?] → НЕТ → другая ветка
    │
    └── ДА
         │
         ▼
    [Действие: Запуск БП]
    • Объект: ID выбранного поставщика
    • Сущность: Процессы → Поставщики
    • Шаблон: «Установить заявки»
    • Параметр «Заявка» = ID текущей заявки
         │
         ▼
    БП «Установить заявки» запускается по поставщику
         │
         ▼
    [Действие: Изменить документ]
    Поле «Заявки» ← ID заявки из параметра
         │
         ▼
    В карточке поставщика появляется ссылка на заявку
```

---

## Проверка результата

1. Открыть список **Заявок** → запустить БП по нужной заявке
2. В диалоге запуска выбрать поставщика (например, «ООО Мебель»)
3. Дождаться завершения БП
4. Перейти в **Поставщики** → открыть карточку «ООО Мебель»
5. В поле **«Заявки»** должна появиться привязка к заявке (например, «Заявка на пылесос»)

---

## Ключевые особенности механизма

| Аспект | Важно знать |
|---|---|
| **Запуск** | Дочерний БП запускается **асинхронно** — основной БП не ждёт его завершения |
| **Контекст** | Дочерний БП выполняется **по другому объекту** (поставщику), а не по заявке |
| **Данные** | Единственный способ передать данные из родительского в дочерний — **параметры** |
| **Сущность** | Важно правильно выбрать сущность: CRM-объекты, Списки, Процессы — это разные типы |
| **Множественность** | Поле для сбора всех заявок у поставщика должно быть **множественным**, иначе предыдущие значения будут перезаписываться |

## Главное

1. **Запуск БП из БП** — это стандартное действие в дизайнере; оно позволяет воздействовать на любой объект Bitrix24 прямо из текущего процесса.

2. **ID документа** в действии «Запуск БП» — это не тип объекта, а конкретный экземпляр (конкретный поставщик). Его нужно передавать через параметр текущего БП.

3. **Параметры — единственный канал связи** между двумя БП. Дочерний БП не имеет доступа к переменным родительского; все нужные данные передаются явно через параметры при запуске.

4. **Сущность и шаблон выбираются последовательно**: сначала тип объекта (CRM / Процессы / Списки), потом конкретный процесс/список, потом шаблон. После выбора шаблона система автоматически подгружает его параметры.

5. **Множественные поля** обязательны там, где один объект может быть связан с несколькими другими (один поставщик — много заявок).

6. **Дочерний БП не запускается автоматически** — тип запуска в его настройках должен быть совместим с программным вызовом; в примере он запускается исключительно из родительского БП.

7. **Цепочка может быть длиннее**: дочерний БП сам может запускать следующий. Механизм не ограничен одним уровнем вложенности.

8. **Результат всегда проверяйте в UI**: после тестового запуска откройте карточку объекта, по которому сработал дочерний БП, и убедитесь, что данные записались корректно.
