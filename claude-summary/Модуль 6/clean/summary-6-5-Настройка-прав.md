# Настройка прав

## О чём этот урок

Урок посвящён настройке прав доступа в бизнес-процессах типа **«Со статусами»** в Bitrix24. В отличие от последовательных БП, где права задаются через отдельные действия, здесь права настраиваются напрямую в параметрах каждого статуса — это делает управление доступом более гибким, наглядным и удобным.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Бизнес-процесс «Со статусами»** | Тип БП в Bitrix24, где документ проходит через набор именованных статусов, а не линейную цепочку действий |
| **Статус** | Состояние, в котором находится документ (заявка) в определённый момент прохождения по БП |
| **Права статуса** | Настройки доступа (чтение/изменение), которые действуют, пока документ находится в данном статусе |
| **Переопределение прав** | Механизм, при котором при входе в новый статус права сбрасываются и применяются заново согласно настройкам этого статуса |
| **Операция чтения** | Право видеть элемент (заявку) в списках и открывать её |
| **Текущий исполнитель / Руководитель** | Роли участников БП, которым можно назначить права |

---

## Два способа задать права в Bitrix24

### Способ 1 — Через действие «Установка прав» *(для последовательных БП)*

- Используется в **последовательных** бизнес-процессах
- Действие «Установка прав» добавляется в цепочку как отдельный блок
- ⚠️ **Проблема при использовании в БП «Со статусами»**: права, заданные через действие внутри статуса, работают только для этого конкретного статуса. При переходе в следующий статус они **переопределяются** — сбрасываются и заменяются новыми

### Способ 2 — Через настройки статуса *(для БП «Со статусами»)* — ✅ Рекомендуемый

- Каждый статус имеет **встроенную форму настройки прав**
- Форма аналогична той, что в действии «Установка прав» — ничего нового учить не нужно
- Права задаются один раз в настройках статуса и **не требуют отдельного действия** в дизайнере
- Права видны непосредственно в настройках статуса — более наглядно

---

## Как работает переопределение прав

```
Статус 1 (Начальный)
    → применяются права статуса 1

Статус 2 (На согласовании)
    → права статуса 1 СБРАСЫВАЮТСЯ
    → применяются права статуса 2

Статус 3 (Одобрена)
    → права статуса 2 СБРАСЫВАЮТСЯ
    → применяются права статуса 3
```

> ⚠️ **Важно:** При каждом переходе между статусами права **полностью переопределяются**. Если в новом статусе права не настроены — документ может стать **невидимым** для участников.

---

## Возможности настройки прав в статусах

| Действие | Описание |
|---|---|
| **Показать / Скрыть** | Управлять видимостью заявки в списках для разных участников |
| **Дать на чтение** | Участник может видеть, но не редактировать заявку |
| **Дать на изменение** | Участник может редактировать поля заявки |
| **Ограничить доступ** | Запретить доступ к заявке на определённом этапе |

**Примеры применения:**
- В статусе **«Утверждение»** — только руководитель видит кнопки действий
- В статусе **«Одобрена»** — доступ только у финансового отдела
- Не нужно городить сложные условия в одном алгоритме

---

## Сравнение: «Последовательный» БП vs «Со статусами»

| Параметр | Последовательный БП | БП «Со статусами» |
|---|---|---|
| **Где задаются права** | Через действие «Установка прав» в цепочке | В настройках каждого статуса |
| **Гибкость** | Ниже — нужно добавлять отдельное действие | Выше — права встроены в статус |
| **Переопределение** | Действие срабатывает при выполнении | Автоматически при входе в статус |
| **Наглядность** | Права «спрятаны» внутри действия | Права видны в настройках статуса |

## Пошаговая инструкция: настройка прав в статусе

### Шаг 1 — Скопировать существующие значения прав (если они уже есть в действии)

1. Открыть **дизайнер бизнес-процесса**
2. Найти действие **«Установка прав»** в статусе «Начальный»
3. Посмотреть и скопировать настроенные значения — кто и какие права имеет
   - *Пример:* операция **Чтение** → **Текущий исполнитель** и **Руководитель**

> 💡 **Практический приём:** перед удалением действия «Установка прав» из дизайнера — скопируйте значения оттуда и перенесите в настройки статуса, чтобы ничего не потерять.

---

### Шаг 2 — Открыть настройки статуса

1. В дизайнере БП нажать на **настройки нужного статуса** (не на действие внутри него, а на **сам статус**)
2. В настройках найти форму прав — она выглядит аналогично форме действия «Установка прав»

---

### Шаг 3 — Добавить права

1. Нажать **«Добавить»** в форме прав
2. Выбрать операцию: **Чтение**
3. Указать участников: **Текущий исполнитель**, **Руководитель** (или другие нужные роли)
4. **Сохранить** настройки статуса

---

### Шаг 4 — Повторить для всех статусов БП

> ⚠️ **Это критически важно!** Если хотя бы в одном статусе права не настроены, при попадании документа в этот статус участники могут **потерять к нему доступ**.

Пройтись по каждому статусу БП и убедиться, что права настроены корректно.

---

## Главное

1. **Права переопределяются при каждом переходе** — если в новом статусе ничего не настроено, предыдущие права сбрасываются и документ может стать недоступным.
2. **Предпочтительный способ** — настройка прав через параметры статуса, а не через действие «Установка прав» внутри него: это чище и нагляднее.
3. **Права нужно настраивать в каждом статусе отдельно** — нельзя задать права один раз для всего БП.
4. **Форма прав в настройках статуса идентична** форме действия «Установка прав» — переучиваться не нужно, только другое место вызова.
5. **БП «Со статусами» гибче «Последовательного»** в управлении доступом — можно показывать или скрывать заявки от разных участников в зависимости от этапа согласования.
6. **Минимально необходимое право** для участника БП — операция **Чтение**, иначе он не будет видеть заявку в списках и не сможет с ней работать.
7. **Практический приём при миграции**: перед удалением действия «Установка прав» из дизайнера — скопируйте значения и перенесите в настройки статуса, чтобы ничего не потерять.
8. **Идентификаторы** в действии «Установка прав» менять не нужно — они остаются теми же (подробнее — в отдельном уроке о правах).
9. **Каждый статус может иметь уникальный набор прав** — это позволяет точечно управлять доступом на каждом этапе согласования без сложных условий в алгоритме.
