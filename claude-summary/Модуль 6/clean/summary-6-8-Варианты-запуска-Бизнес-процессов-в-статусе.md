# Варианты запуска Бизнес-процессов в статусе

## О чём этот урок

Урок посвящён типам запуска подпроцессов внутри статуса в бизнес-процессе **«Со статусами»** в Bitrix24. Разбирается, какие механизмы запуска существуют, как их комбинировать и в каких случаях каждый из них применяется. Понимание этих механизмов необходимо для построения гибких и сложных схем согласования.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Статус** | Состояние, в котором находится бизнес-процесс; внутри каждого статуса можно настроить несколько подпроцессов |
| **Подпроцесс в статусе** | Набор действий, запускаемый по определённому триггеру внутри одного статуса |
| **Обработчик входа в статус** | Подпроцесс, запускаемый автоматически при переходе в данный статус |
| **Обработчик выхода из статуса** | Подпроцесс, запускаемый в момент выхода из статуса (после того как все остальные подпроцессы отработали и инициирован переход) |
| **Команда** | Ручной запуск подпроцесса — пользователь нажимает кнопку/действие вручную |
| **Выполнение через заданное время** | Автоматический запуск подпроцесса через указанный промежуток времени или в конкретный момент времени |

---

## Четыре типа запуска подпроцессов внутри статуса

В Bitrix24 внутри одного статуса можно добавить несколько подпроцессов с разными типами запуска. Всего существует **четыре типа**.

---

### 1. Обработчик входа в статус

- Запускается **автоматически**, как только бизнес-процесс переходит в данный статус
- Добавляется **только один раз** — повторно добавить нельзя
- **Самый распространённый тип**: подходит для большинства задач и сценариев согласования

---

### 2. Команда (ручной запуск)

- **Ручное действие** — пользователь инициирует запуск подпроцесса явно (например, нажатием кнопки)
- Можно добавить **несколько команд** в рамках одного статуса
- Используется, когда нужно предоставить участнику процесса возможность вручную запустить определённую ветку логики

---

### 3. Выполнение через заданное время (Таймер)

- Автоматический запуск **через промежуток времени** (например, через 2 часа) или **в конкретный момент** (например, в понедельник в 09:00)
- Можно добавить **несколько таких обработчиков** в рамках одного статуса
- Полезно для: напоминаний, эскалаций, автоматических переходов по дедлайну

---

### 4. Обработчик выхода из статуса

- Запускается **в момент выхода из статуса** — когда все подпроцессы отработали и система готова перейти в следующий статус
- Добавляется **только один раз** — повторно добавить нельзя
- Используется для **финальной логики** перед переходом: уведомления, очистка данных и т.д.

---

### Сводная таблица типов запуска

| Тип запуска | Момент запуска | Кол-во на статус | Типичное применение |
|---|---|---|---|
| Вход в статус | Автоматически при переходе в статус | Только 1 | Основная логика статуса |
| Выход из статуса | Автоматически при выходе из статуса | Только 1 | Очистка данных, уведомления о завершении |
| Команда (вручную) | По кнопке пользователя | Неограниченно | Действия по требованию |
| Таймер | Через заданное время или по расписанию | Неограниченно | Эскалация, напоминания |

---

## Комбинирование типов запуска

- В рамках одного статуса можно **одновременно использовать несколько типов** запуска
- Пример цепочки: `Вход в статус → Команда → Таймер → Ещё одна команда → Выход из статуса`
- **Ограничение**: вход и выход из статуса — по одному разу каждый
- **Команд и таймеров** — можно добавить сколько угодно

---

## Важное правило приоритета

> ⚠️ Если один из подпроцессов (вход в статус, команда или таймер) **инициировал переход в другой статус**, то остальные подпроцессы в текущем статусе **выполняться не будут**.

**Исключение** — обработчик выхода из статуса: он **сработает в любом случае** при выходе из статуса.

---

## Практический пример

**Настройка статуса:** вход → команда → таймер → выход

**Сценарий:** обработчик «вход» отработал, и внутри него выполнен переход в следующий статус.

| Подпроцесс | Выполнится? | Причина |
|---|---|---|
| Обработчик входа | ✅ Да | Уже отработал |
| Команда | ❌ Нет | Переход уже инициирован |
| Таймер | ❌ Нет | Переход уже инициирован |
| Обработчик выхода | ✅ Да | Всегда срабатывает при выходе |

---

## Пошаговые инструкции

### Как добавить подпроцесс в статус

1. Открыть **Дизайнер бизнес-процесса**
2. Перейти в нужный **статус**
3. Нажать кнопку добавления подпроцесса (обычно **«+»** или **«Добавить»**)
4. Выбрать **тип запуска**:
   - **Команда** — ручной запуск
   - **Выполнение через заданное время** — указать промежуток или дату/время
   - **Обработчик входа** — автоматически при входе *(доступен только если ещё не добавлен)*
   - **Обработчик выхода** — при выходе из статуса *(доступен только если ещё не добавлен)*
5. Настроить **логику действий** внутри подпроцесса
6. При необходимости повторить **шаги 3–5** для добавления ещё одного подпроцесса

---

### Ограничения при повторном добавлении

- После добавления **обработчика входа** — кнопка его повторного добавления становится **недоступной**
- После добавления **обработчика выхода** — аналогично **недоступна**
- **Команды и таймеры** — доступны для добавления в неограниченном количестве

---

## Главное

1. **Четыре типа запуска** подпроцессов в статусе: вход, выход, команда (вручную), таймер.
2. **Вход и выход из статуса — по одному** на статус; команд и таймеров — сколько угодно.
3. **Переход в другой статус** внутри любого подпроцесса останавливает выполнение остальных подпроцессов в текущем статусе — кроме обработчика выхода.
4. **Обработчик выхода всегда срабатывает** при покидании статуса — это надёжное место для финальной логики (уведомления, очистка данных).
5. **Комбинирование типов** даёт гибкость: вход запускает основную логику, таймер — напоминание или эскалацию, если пользователь не отреагировал.
6. На практике **чаще всего достаточно обработчика входа** — он покрывает большинство сценариев согласования.
7. **Таймер незаменим** для автоматических эскалаций и дедлайнов — процесс сам переходит в следующий статус без участия пользователя.
8. **Бизнес-процесс «Со статусами»** значительно гибче последовательного именно за счёт многоуровневого управления запуском внутри каждого статуса.
