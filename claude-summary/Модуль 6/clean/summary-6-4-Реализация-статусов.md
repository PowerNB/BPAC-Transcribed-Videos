# Реализация статусов

## О чём этот урок

Урок посвящён практической реализации статусов в бизнес-процессе типа **«Со статусами»** в Bitrix24. На примере согласования заявки (с утверждением руководителем и бухгалтером) показывается:
- как настраивать каждый статус отдельно;
- какие действия включать в каждый статус;
- как организовывать переходы между статусами;
- как правильно завершать бизнес-процесс.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Статус** | Отдельный этап бизнес-процесса «Со статусами»; содержит свой набор действий и переходы в другие статусы |
| **Переход между статусами** | Связь из одного статуса в другой; создаётся явно в дизайнере и заменяет сложное ветвление внутри одного большого процесса |
| **Действие «Утверждение»** | Блок, в котором участник выбирает исход (одобрить / отклонить / доработать); результат определяет, в какой статус перейдёт процесс |
| **Действие «Уведомление»** | Отправляет сообщение указанным пользователям; используется для оповещения участников о начале их этапа |
| **Действие «Запись в отчёт»** | Фиксирует результат этапа в журнал/отчёт бизнес-процесса |
| **Действие «Изменение документа»** | Обновляет поля документа (заявки); применяется на этапе доработки сотрудником |
| **Живая лента** | Встроенный чат-инструмент Bitrix24; используется для обсуждения вместо поля «Комментарий» в форме утверждения |
| **Переменная** | Временное значение внутри бизнес-процесса; передаётся между статусами |
| **Константа** | Неизменяемое значение, заданное при настройке шаблона (пример: пороговая сумма сделки — 15) |
| **Завершение БП** | Происходит автоматически, когда в текущем статусе нет ни одного перехода в другой статус и все действия выполнены |

---

## Архитектура бизнес-процесса: общая схема статусов

```
[Начальный статус]
        ↓
[Утверждение руководителем]
    ├── На доработку → [Доработка сотрудником] → (возврат) → [Утверждение руководителем]
    │                         └── Отказ дорабатывать → [Отклонена]
    ├── Отклонено → [Отклонена]
    ├── Одобрено + сумма > 15 → [Утверждение бухгалтером]
    │                               ├── Одобрено → [Одобрена]
    │                               └── Отклонено → [Отклонена]
    └── Одобрено + сумма ≤ 15 → [Одобрена]
```

**Ключевая идея:** каждый этап согласования — отдельный, небольшой и простой статус. Переходы между ними создаются явными связями в дизайнере, а не усложнением логики внутри одного монолитного процесса.

---

## Описание каждого статуса

### Статус «Утверждение руководителем»

**Что входит в статус:**

1. **Уведомление** — отправляется руководителю о новой заявке на согласование:
   - Отправитель: `{=Variable:User}` (сотрудник)
   - Получатель: `{=Variable:UserBoss}` (руководитель)
   - Текст уведомления — **нейтральный**: подходит и для первичного согласования, и для повторного после доработки
2. **Утверждение** — блок выбора решения руководителем:
   - Галочка «Разрешить комментарии» — **снята**; обсуждение ведётся в живой ленте
3. **Условие по сумме сделки** — разветвление после решения «Одобрено»:
   - Сумма > 15 → переход в статус «Утверждение бухгалтером»
   - Сумма ≤ 15 → переход в статус «Одобрена»
4. **Запись в отчёт** — фиксирует факт одобрения руководителем

**Переходы из этого статуса:**

| Условие | Следующий статус |
|---|---|
| Одобрено + сумма > 15 | Утверждение бухгалтером |
| Одобрено + сумма ≤ 15 | Одобрена |
| Отклонено | Отклонена |
| На доработку | Доработка сотрудником |

**Что перенесено в другие статусы (убрано отсюда):**
- Блок утверждения бухгалтером → вынесен в отдельный статус
- Уведомления об итоге → вынесены в статусы «Одобрена» / «Отклонена»
- Логика доработки → вынесена в статус «Доработка сотрудником»

---

### Статус «Утверждение бухгалтером»

**Что входит в статус:**

1. **Уведомление** — бухгалтеру о новом задании:
   - Настройки те же, что в уведомлении руководителю
   - Комментарии отключены — обсуждение в живой ленте
2. **Утверждение** — блок выбора решения бухгалтером (одобрить / отклонить)
3. **Запись в отчёт** — отдельная строка для каждого исхода:
   - «Бухгалтер утвердил»
   - «Бухгалтер отклонил»

**Переходы:**

| Условие | Следующий статус |
|---|---|
| Одобрено | Одобрена |
| Отклонено | Отклонена |

**Особенности:**
- Переменные из предыдущих статусов не нужны — данные берутся напрямую из документа
- Статус намеренно простой: уведомление → утверждение → запись → переход

---

### Статус «Доработка сотрудником»

**Что входит в статус:**

1. **Уведомление** — сотруднику о необходимости доработки:
   - Текст нейтральный, без указания конкретного отправителя
   - Конкретный комментарий руководителя/бухгалтера не указывается — детали обсуждаются в живой ленте
2. **Изменение документа** — сотрудник вносит правки в поля заявки:
   - Поля — те же, что настраивались ранее (коды полей не изменились → настройка работает без изменений)
   - Поле «Комментарий» убрано — обсуждение через живую ленту
3. **Запись в отчёт** (в ветке отклонения) — фиксирует, что сотрудник отказался дорабатывать

**Переходы:**

| Условие | Следующий статус |
|---|---|
| Доработка выполнена | Утверждение руководителем (возврат) |
| Сотрудник отказался дорабатывать | Отклонена |

> ⚠️ **Важно:** ранее для выхода из цикла доработки использовалось «прерывание процесса». Теперь достаточно перейти в статус «Отклонена» — это чище и понятнее.

---

### Статусы «Одобрена» и «Отклонена»

Оба статуса — финальные узлы процесса, технически простые.

**Состав каждого статуса:**

1. **Запись в журнал/отчёт** — фиксирует итоговый результат
2. **Установка статуса документа** — меняет поле статуса в самой заявке (CRM/списке)

**Ключевое правило завершения БП:**
- Действие «Установка статуса бизнес-процесса» (переброс в другой статус) **не используется**
- Бизнес-процесс завершается **автоматически**, когда в текущем статусе выполнены все действия и нет ни одного перехода в другой статус

---

## Пошаговые инструкции

### Настройка статуса «Утверждение руководителем»

1. Открыть дизайнер шаблона → выбрать статус **«Утверждение руководителем»**
2. Добавить действие **«Уведомление»**:
   - Отправитель: `{=Variable:User}`
   - Получатель: `{=Variable:UserBoss}`
   - Текст: нейтральная формулировка
3. Добавить действие **«Утверждение»**:
   - Снять галочку **«Разрешить комментарии»** → обсуждение переносится в живую ленту
4. Добавить **«Условие»** после ветки «Одобрено»:
   - Поле: Сумма сделки, Оператор: `> 15`
   - Ветка «Да» → переход в «Утверждение бухгалтером»
   - Ветка «Нет» → переход в «Одобрена»
5. В ветке «Одобрено» добавить **«Запись в отчёт»**
6. Настроить переходы для веток «Отклонено» и «На доработку»
7. Сохранить статус

---

### Настройка статуса «Доработка сотрудником»

1. Открыть статус **«Доработка сотрудником»** в дизайнере
2. Добавить **«Уведомление»** сотруднику:
   - Отправитель: `{=Variable:User}` — нейтрально, без персонализации
   - Убрать упоминание конкретного руководителя из текста
3. Добавить действие **«Изменение документа»**:
   - Исполнитель: сотрудник
   - Убрать поле «Комментарий» (заменено живой лентой)
   - Остальные поля — без изменений
4. Настроить переходы:
   - После выполнения → «Утверждение руководителем»
   - В ветке отклонения → «Отклонена» + запись в отчёт
5. Сохранить

---

### Настройка финальных статусов «Одобрена» / «Отклонена»

1. Открыть статус **«Одобрена»**
2. Добавить **«Запись в журнал»** с итоговым результатом
3. Добавить **«Установку статуса документа»** (поле статуса в заявке)
4. **Не добавлять** действие перехода в другой статус БП — процесс завершится сам
5. Сохранить
6. Повторить аналогично для статуса **«Отклонена»**

---

## Архитектурные принципы

### Принцип «один статус — одна ответственность»
Каждый статус решает одну конкретную задачу:
> уведомить участника → получить его решение → записать результат → перейти дальше

### Принцип нейтральных уведомлений
Если один и тот же статус может быть достигнут из разных мест (например, «Доработка» — и от руководителя, и от бухгалтера):
- уведомление делается **нейтральным**: без указания конкретного отправителя
- детали обсуждаются в **живой ленте**

### Живая лента вместо комментариев
| Комментарии в форме утверждения | Живая лента |
|---|---|
| Закрытое поле | Открытое обсуждение |
| Доступно только участнику задачи | Доступно всем участникам |
| Не сохраняет общий контекст | Сохраняет контекст для всех |

**Вывод:** для согласований предпочтительнее живая лента.

### Автоматическое завершение БП
Специально «завершать» процесс не нужно. Как только:
- в текущем статусе выполнены все действия, **И**
- нет ни одного перехода в другой статус

→ бизнес-процесс завершается **автоматически**.

---

## Главное

1. **Статус «Со статусами» — это не монолит.** Каждый этап согласования — отдельный маленький процесс со своей логикой.
2. **Переходы между статусами заменяют сложное ветвление.** Вместо вложенных условий внутри одного большого процесса — явные стрелки-переходы между статусами в дизайнере.
3. **Условия можно ставить внутри статуса.** Пример: после одобрения руководителем — проверка суммы сделки. Если > 15 → к бухгалтеру, если нет → сразу «Одобрена».
4. **Нейтральные уведомления и живая лента** — обязательное правило для статусов, в которые можно попасть из нескольких разных мест.
5. **Действие «Изменение документа» не требует перенастройки**, если коды полей не изменились — повторное использование работает автоматически.
6. **Финальные статусы не нуждаются в явном завершении.** БП завершается сам, когда заканчиваются действия и нет переходов дальше.
7. **Переменные нужны не везде.** В простых статусах данные берутся напрямую из документа.
8. **Доработка сотрудником — отдельный статус** с двумя исходами: вернуть заявку руководителю или самостоятельно отклонить её.
9. **Комментарии в форме утверждения лучше отключать** — они изолированы от общего обсуждения. Живая лента доступна всем участникам и сохраняет контекст.
10. **Расширенный вариант решения руководителя** предусматривает три исхода: одобрить → «Одобрена»; отклонить → «Отклонена»; доработать → «Доработка сотрудником» (или возврат в начальный статус).
