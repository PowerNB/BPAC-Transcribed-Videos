# Выбор типа Бизнес процесса

## О чём этот урок

Урок посвящён знакомству с типом бизнес-процесса **«Со статусами»** в Bitrix24 — альтернативой «Последовательному» БП. Разбирается:
- В каких ситуациях тип «Со статусами» незаменим
- Как он устроен концептуально
- Как перейти от линейной схемы к схеме с повторяющимися этапами и переходами между ними

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Последовательный БП** | Бизнес-процесс, в котором шаги выполняются строго один за другим, без возможности легко вернуться на предыдущий этап |
| **БП «Со статусами»** | Бизнес-процесс, разделённый на отдельные этапы (статусы/подпроцессы) с настраиваемыми переходами между ними |
| **Статус** (в контексте БП) | Подпроцесс (или несколько подпроцессов) внутри большого бизнес-процесса. ⚠️ Не путать со статусом документа или сделки |
| **Переход** | Связь между статусами, определяющая, в какой статус перейдёт процесс после завершения текущего |
| **Начальный статус** | Первый статус, с которого стартует бизнес-процесс |

---

## Сравнение типов: Последовательный vs Со статусами

### Последовательный БП — подходит, когда:
- Алгоритм линейный: шаг A → шаг B → шаг C
- Нет этапов, которые нужно проходить повторно
- Схема относительно простая и не разветвлённая
- Один непрерывный алгоритм сверху вниз

### Недостатки последовательного БП:
- Все ветвления и циклы нужно реализовывать внутри единой структуры
- Сложно поддерживать при разветвлённой логике
- Труднее дорабатывать — изменение одного блока может повлиять на другие
- При усложнении схемы превращается в нечитаемый граф с многочисленными условиями

### БП «Со статусами» — подходит, когда:
- Алгоритм сложный и большой
- В нём явно выделяются этапы, которые могут **повторяться** или проходиться несколько раз
- Нужны переходы между этапами в **любом направлении** (не только вперёд)
- Логику сложно собрать в один линейный поток без нагромождения условий и циклов
- Есть несколько возможных исходов (одобрено / отклонено / на доработку)
- Разные участники имеют разные права на разных этапах

### Преимущества БП «Со статусами»:
- Логика разбита на независимые состояния (статусы)
- В любой момент можно передать управление любому другому статусу (аналог **GoTo** — легальный и удобный)
- Каждый статус — отдельный мини-процесс со своей логикой
- Проще поддерживать и дорабатывать: правишь только нужный статус
- Статусы можно посещать **многократно** — именно это решает проблему циклических согласований

> **Ключевое правило:** Если в задаче есть циклы и повторяющиеся этапы — «Со статусами» предпочтительнее. Если схема «Последовательного» БП превращается в нечитаемый граф — пора переходить на «Со статусами».

---

## Разбор примера: Согласование заявки

### Исходный бизнес-процесс (простая схема)

Три последовательных этапа:
1. Сотрудник подаёт заявку
2. Руководитель согласовывает или отправляет на доработку
3. Если сумма > 15 000 → Бухгалтер одобряет или отклоняет (при отклонении — завершение БП)

Эта схема работала нормально, пока оставалась простой.

---

### Усложнённая постановка задачи

Новые требования кардинально меняют логику:
- Если бухгалтер **отклоняет** заявку → она возвращается сотруднику на доработку
- После доработки → снова идёт к руководителю на одобрение
- После одобрения руководителем → снова к бухгалтеру
- Руководитель теперь имеет **три варианта решения**:
  - ✅ Принять заявку
  - 🔄 Отправить на доработку
  - ❌ Отклонить окончательно (если заявка не подходит ни по каким обстоятельствам)

### Почему последовательный БП плохо справляется с этой задачей:
- Появляются дополнительные циклы и ветвления
- «Пазл» из условий и переходов становится сложно собрать и поддерживать
- Схема теряет читаемость и превращается в запутанный граф

---

## Структура БП «Со статусами»

### Принцип работы

Большой бизнес-процесс делится на небольшие части (статусы), каждая из которых:
- Реализует свою логику **независимо**
- Может быть пройдена **несколько раз**
- Соединена с другими статусами через **переходы**

### Три естественных статуса в примере

| № | Статус | Содержание |
|---|---|---|
| 1 | **Утверждение руководителя** | Руководитель принимает решение: одобрить / доработать / отклонить |
| 2 | **Утверждение бухгалтера** | Бухгалтер принимает решение: одобрить / отклонить (→ на доработку) |
| 3 | **Доработка заявки сотрудником** | Сотрудник вносит правки и отправляет заново |

### Схема переходов

```
[Старт] → [Утверждение руководителя]
              ├── Одобрить      → [Утверждение бухгалтера]
              ├── На доработку  → [Доработка сотрудником] → [Утверждение руководителя]
              └── Отклонить     → [Завершение]

[Утверждение бухгалтера]
              ├── Одобрить      → [Завершение / Успех]
              └── Отклонить     → [Доработка сотрудником] → [Утверждение руководителя]
```

## Пошаговые инструкции

### План реализации БП «Со статусами» в модуле (последовательность уроков)

**Шаг 1. Создание статусов**
- Определить количество нужных статусов
- Создать их в конструкторе Bitrix24
- Задать переменные и константы

**Шаг 2. Реализация начального статуса**
- Перенести ранее настроенные действия из последовательного шаблона
- Использовать копирование блоков из одного шаблона в другой (экономит время при доработке)

**Шаг 3. Реализация статусов согласования**
- Реализовать статус «Утверждение у руководителя»
- Доработать варианты «Одобрена» и «Отклонена»

**Шаг 4. Настройка прав**
- Задать разные права для разных участников на каждом этапе
- ⚠️ В БП «Со статусами» это делается **проще**, чем в последовательном БП

**Шаг 5. Проверка работы**
- Запустить и протестировать готовый БП

**Шаг 6. Расширение вариантов выбора для руководителя**
- Добавить третий вариант решения: «Одобрить» / «Доработать» / «Отклонить»

**Шаг 7. Варианты запуска статусов**
- Изучить три типа запуска статуса:
  1. **По входу/выходу** из статуса
  2. **Вручную**
  3. **По таймеру**

## Главное

1. **Два типа БП в Bitrix24** — «Последовательный» и «Со статусами»: выбор зависит от сложности задачи и наличия повторяющихся этапов.

2. **Статус ≠ статус документа**: в контексте БП «статус» — это подпроцесс (этап) с собственной логикой, а не просто метка на документе или сделке.

3. **Критерий выбора «Со статусами»**: если в бизнес-процессе есть этапы, которые повторяются (циклы согласования, возврат на доработку) — этот тип предпочтительнее.

4. **Главное преимущество**: сложная схема разбивается на небольшие независимые блоки — каждый проще реализовать, понять и поддерживать.

5. **Переходы — ключевой элемент**: именно переходы между статусами формируют логику всего процесса, заменяя громоздкие условия и циклы в последовательном БП.

6. **Права настраиваются проще**: в БП «Со статусами» удобнее разграничить права разных участников для разных этапов процесса.

7. **Статусы можно проходить многократно**: в отличие от шагов последовательного БП, статус можно посещать снова — это решение проблемы циклических согласований.

8. **Перенос блоков между шаблонами**: Bitrix24 позволяет копировать настроенные блоки из одного шаблона в другой — это экономит время при доработке существующих процессов.

9. **Три типа запуска статуса**: вручную, по входу/выходу из статуса, по таймеру — это даёт широкую гибкость в автоматизации.

10. **Аналогия для программистов**: БП «Со статусами» — это легальное использование GoTo: не нужно «складывать один большой пазл» из условий, достаточно передать управление нужному статусу.
