# Выбор для руководителя: одобрить, доработать, отклонить

## О чём этот урок

Урок посвящён расширению возможностей согласования в бизнес-процессе «Со статусами» в Bitrix24. Стандартное действие «Утверждение документа» даёт только два исхода («Одобрить» / «Отклонить»), но бизнес-логика часто требует трёх вариантов. В уроке показано, как заменить «Утверждение документа» на действие «Запрос дополнительной информации» и построить разветвлённую логику обработки трёх вариантов решения руководителя.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Утверждение документа** | Стандартное действие с двумя исходами: «Одобрен» / «Отклонён». Не подходит при необходимости третьего варианта |
| **Запрос дополнительной информации** | Гибкое действие, позволяющее задать произвольные поля (в т.ч. список вариантов) и получить ответ от участника процесса |
| **Поле типа «Список»** | Тип поля в настройке действия «Запрос дополнительной информации»; позволяет задать конечный набор вариантов для выбора |
| **Ветка условия** | Одно из направлений выполнения БП после проверки условия (аналог if / else if / else) |
| **Переменная БП** | Хранимое значение внутри шаблона, доступное для чтения и сравнения в условиях |
| **Статус** | Состояние документа в рамках БП «Со статусами»; переходы управляются логикой условий |

---

## Зачем заменять «Утверждение документа» на «Запрос дополнительной информации»

- Действие **«Утверждение документа»** поддерживает ровно **два исхода**: Одобрен / Отклонён.
- Когда бизнес-логика требует **трёх вариантов** (Одобрить / Отклонить / Доработать) — это действие становится недостаточным.
- Решение — использовать **«Запрос дополнительной информации»**, в котором вручную формируется список вариантов любой длины.

> **Ключевой принцип:** Если нужно больше двух исходов для руководителя — всегда использовать «Запрос дополнительной информации» вместо «Утверждения документа».

---

## Три варианта решения руководителя

| Вариант | Итоговый статус документа | Описание |
|---|---|---|
| **Одобрить** | «Одобрена» | Заявка принята, процесс завершается успешно |
| **Доработать** | «Начальный» или статус доработки | Заявка возвращается инициатору на доработку |
| **Отклонить** | «Отклонена» (финальный) | Заявка окончательно отклонена, без права на доработку |

> **Важно:** «Отклонить» — это принципиально отличный от «Доработать» исход: документ завершает процесс **немедленно**, без промежуточных шагов и без возможности возврата.

---

## Логика ветвления в дизайнере БП

После того как руководитель выбирает вариант, значение сохраняется в переменную. Далее строится цепочка условий:

```
[Запрос доп. информации] → Поле «Что сделать?»
  ├── Равно «Одобрить»   → [Ветка одобрения]  → Запись в отчёт «Одобрено»
  ├── Равно «Доработать» → [Ветка доработки]  → Уведомление + возврат в статус доработки
  └── (иначе / else)     → [Ветка отклонения] → Переход в финальный статус «Отклонена»
```

### Настройка ветки «Одобрить»
- **Тип:** Значение переменной
- **Переменная:** поле ответа из «Запроса» («Что сделать?»)
- **Оператор:** Равно
- **Значение:** `Одобрить`
- **Действия в ветке:** все действия предыдущей реализации одобрения + запись в отчёт «Одобрено»

### Настройка ветки «Доработать»
- **Тип:** Значение переменной
- **Переменная:** то же поле («Что сделать?»)
- **Оператор:** Равно
- **Значение:** `Доработать`
- **Действия в ветке:** отправка уведомления инициатору + возврат в статус доработки

### Настройка ветки «Отклонить» (else)
- Отдельное условие **не настраивается** — используется ветка **else (иначе)**
- **Логика:** если не «Одобрить» И не «Доработать» — значит, руководитель выбрал «Отклонить»
- **Действия в ветке:** переход документа в финальный статус «Отклонена»

> **Важно:** Третье условие (else) настраивать отдельно не нужно — оно охватывает все оставшиеся случаи. Это упрощает схему и снижает риск ошибок при изменении вариантов списка.

---

## Настройка действия «Запрос дополнительной информации»

### Ключевые параметры настройки
- Поле **«Комментарий»** — не использовать (оставить пустым или убрать).
- Добавить новое поле:
  - **Тип поля:** Список
  - **Название поля:** например, «Что сделать?»
  - **Варианты списка:** Одобрить / Отклонить / Доработать

> **Примечание:** Порядок вариантов в списке влияет на удобство работы руководителя — рекомендуется ставить наиболее частый вариант **первым**.

---

## Перенос существующих блоков между ветками

При перестройке логики важно **перетащить** ранее настроенные действия в нужные ветки, а не создавать их заново:

1. Найти блок действий в старой ветке (например, запись в отчёт «Одобрено»).
2. Перетащить его в новую ветку «Одобрить» в дизайнере БП.
3. Аналогично — действие возврата на доработку перенести в ветку «Доработать».

> Перетаскивание позволяет сохранить все настройки блока — не нужно пересоздавать и перенастраивать действия заново.

## Пошаговые инструкции

### Замена «Утверждения документа» на «Запрос дополнительной информации»

1. Открыть шаблон БП → перейти в нужный статус (согласование у руководителя).
2. Найти действие **«Утверждение документа»** и **удалить** его.
3. Добавить действие **«Запрос дополнительной информации»**.
4. В настройках действия нажать **«Добавить поле»**.
5. Выбрать тип поля — **«Список»**.
6. Ввести название поля: **«Что сделать?»**.
7. Ввести варианты: **Одобрить**, **Отклонить**, **Доработать** (в нужном порядке).
8. Нажать **«Сохранить»**.

---

### Настройка условий ветвления

1. После действия «Запрос» добавить блок **«Условие»**.
2. В **первой ветке** задать условие: `[поле ответа «Что сделать?»]` = `«Одобрить»`.
3. Перенести (перетащить) в эту ветку все действия одобрения + запись в отчёт «Одобрено».
4. Добавить **вторую ветку** с условием: `[поле ответа «Что сделать?»]` = `«Доработать»`.
5. Перенести в неё действие возврата на доработку + уведомление инициатору.
6. Ветку **else** оставить для отклонения — добавить переход в финальный статус «Отклонена».
7. **Сохранить** шаблон.
8. Запустить тестовый экземпляр БП.

---

### Проверка работы (тестирование)

1. Открыть документ и **запустить БП**.
2. Войти под учётной записью **руководителя**.
3. В задаче согласования убедиться, что появилось поле **«Что сделать?»** с тремя вариантами.
4. Выбрать вариант **«Отклонить»** — проверить новую ветку.
5. Убедиться, что документ сразу перешёл в финальный статус **«Отклонена»**, минуя этапы доработки.
6. Повторить тест для вариантов **«Одобрить»** и **«Доработать»** — убедиться в корректности каждой ветки.

> **Ожидаемый результат:** После выбора «Отклонить» заявка немедленно переходит в последний статус без промежуточных шагов.

---

## Главное

1. **«Утверждение документа» — только для двух исходов.** Как только нужен третий вариант — использовать «Запрос дополнительной информации» с полем типа «Список».
2. **Поле типа «Список»** позволяет задать любое количество вариантов ответа, не ограничиваясь «Да / Нет».
3. **Ветка else не требует отдельного условия** — она автоматически перехватывает все случаи, не попавшие в явные условия. Это упрощает схему и снижает риск ошибок.
4. **Существующие блоки действий можно перетаскивать между ветками** — не нужно пересоздавать и перенастраивать их заново.
5. **Тестирование обязательно** — после каждого изменения структуры условий запускать тестовый экземпляр и проверять каждую ветку вручную.
6. **БП «Со статусами» гибче «Последовательного»** именно за счёт возможности возвращаться в предыдущие статусы (доработка) или сразу завершать процесс (отклонение).
7. **«Отклонить» через else** означает: если руководитель выбрал «Отклонить», документ завершает процесс **немедленно**, без права на доработку — это принципиально отличает его от «Доработать».
8. **Порядок вариантов в списке имеет значение** — наиболее частый вариант рекомендуется ставить первым для удобства руководителя.
9. **Три статуса-исхода** для документа: «Одобрена» → «Начальный/Доработка» → «Отклонена» — каждый управляется своей веткой условия в дизайнере БП.
