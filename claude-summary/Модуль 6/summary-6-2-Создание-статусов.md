# Модуль 6, Урок 12: Создание бизнес-процесса со статусами

## О чём этот урок

Урок посвящён созданию бизнес-процессов типа «Со статусами» в Bitrix24 — альтернативному подходу к автоматизации согласований по сравнению с «Последовательным» БП. Этот тип позволяет реализовывать любые сценарии согласования на портале без необходимости выстраивать единый линейный алгоритм. Урок охватывает полный цикл: от создания статусов до запуска и проверки работы готового процесса.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Бизнес-процесс «Со статусами»** | Тип БП в Bitrix24, где логика разбита на независимые состояния (статусы), между которыми можно свободно передавать управление |
| **Бизнес-процесс «Последовательный»** | Тип БП, где все действия выполняются в строгом линейном порядке — один большой алгоритм |
| **Статус** | Независимый блок БП «Со статусами», содержащий свою часть логики. Аналог «состояния» в теории конечных автоматов |
| **Начальный статус** | Первый статус в БП «Со статусами», который всегда запускается при старте процесса |
| **Обработчик входа в статус** | Триггер/событие внутри статуса: запускает описанные в нём действия в момент перехода в этот статус |
| **Переменные** | Изменяемые хранилища данных внутри шаблона БП (например, текущий исполнитель, результат согласования) |
| **Константы** | Неизменяемые параметры шаблона БП (например, email руководителя, название отдела) |
| **GoTo** | Безусловный переход к другому статусу — легальный и поддерживаемый механизм в БП «Со статусами» |
| **Дизайнер БП** | Визуальный редактор шаблонов бизнес-процессов в Bitrix24 |
| **Идентификатор (код) переменной** | Уникальное имя переменной/константы внутри шаблона, по которому она используется в действиях |

---

## Отличие «Со статусами» от «Последовательного» БП

### Последовательный БП
- Один непрерывный алгоритм сверху вниз
- Все ветвления и циклы нужно реализовывать внутри единой структуры
- Сложно поддерживать при разветвлённой логике
- Труднее дорабатывать — изменение одного блока может повлиять на другие

### БП «Со статусами»
- Логика разбита на **независимые состояния (статусы)**
- В любой момент можно передать управление **любому другому статусу** (аналог GoTo)
- Каждый статус — это отдельный мини-процесс со своей логикой
- Проще поддерживать и дорабатывать: правишь только нужный статус
- Для программистов: это легальное использование GoTo — не нужно «складывать один большой пазл»

> **Когда БП «Со статусами» незаменим:**
> - Когда есть несколько возможных исходов (одобрено / отклонено / на доработку)
> - Когда нужны циклы (например, повторная отправка на согласование)
> - Когда разные участники имеют разные права на разных этапах
> - Когда логика слишком разветвлённая для линейного алгоритма

---

## Архитектура статусов: проектирование

### Принцип декомпозиции
Статусы создаются **в соответствии с блоками/подпроцессами**, которые явно выделены в задаче. Каждый логический этап согласования — отдельный статус.

### Типичный набор статусов для процесса согласования
```
[Начальный] → [Утверждение у руководителя] → [Одобрена] / [Отклонена]
```

| Статус | Назначение |
|---|---|
| **Начальный** | Технические действия при старте (подготовка данных, уведомления о запуске) |
| **Утверждение у руководителя** | Основная логика согласования — задача руководителю, ожидание решения |
| **Одобрена** | Финальные действия при положительном исходе |
| **Отклонена** | Финальные действия при отрицательном исходе |

> Начальный статус — **всегда первый**, запускается автоматически при старте БП. В нём размещают технические действия, а не бизнес-логику.

---

## Создание статусов: пошаговая инструкция

1. Открыть шаблон БП типа «Со статусами» в дизайнере
2. В дизайнере будет доступна кнопка **добавления статусов** (отличие от последовательного БП)
3. Нажать «Добавить статус»
4. Задать **название** статуса (например, «Начальный»), сохранить
5. Повторить для каждого статуса согласно архитектуре процесса
6. Минимальный набор для согласования: **Начальный + Утверждение у руководителя + Одобрена + Отклонена**

---

## Настройка переменных и констант

### Ключевой приём: сохранение идентификаторов
Если вы **переносите логику из существующего последовательного БП**, используйте **те же коды (идентификаторы) переменных и констант**.

**Зачем это нужно:**
- Действия внутри статусов ссылаются на переменные по их коду
- Если код совпадает — все настройки действий переносятся без изменений
- Не нужно перенастраивать каждое действие заново

### Порядок настройки параметров шаблона
1. Открыть «Параметры шаблона» нового БП «Со статусами»
2. Перенести **переменные** из старого последовательного БП (с теми же идентификаторами)
3. Перенести **константы** из старого БП (с теми же идентификаторами)
4. Проверить, что коды совпадают с оригинальными

---

## Реализация логики внутри статусов

### Добавление действий в статус
При нажатии «Добавить» внутри статуса система предлагает несколько вариантов:

| Вариант | Когда срабатывает |
|---|---|
| **Обработчик входа в статус** | Сразу при переходе в этот статус |
| Обработчик выхода из статуса | При выходе из статуса |
| Ручной запуск | По действию пользователя |
| По таймеру | По расписанию / через заданное время |

> **Самый используемый вариант — «Обработчик входа в статус»**: понятен, предсказуем, срабатывает при переходе в статус. Рекомендуется как основной инструмент.

### Редактор внутри статуса
После выбора варианта открывается **знакомый редактор** — такой же, как в последовательном БП. Все те же действия, условия, циклы доступны внутри каждого статуса.

---

## Перенос блоков из старого шаблона

### Приём «копирование блоков между шаблонами»
Bitrix24 позволяет копировать настроенные блоки действий из одного шаблона в другой.

**Зачем это нужно:**
- Если уже настроен последовательный БП с нужными действиями
- Не нужно настраивать действия заново — просто скопировать
- Работает благодаря совпадению идентификаторов переменных/констант

**Алгоритм:**
1. Открыть старый последовательный БП в дизайнере
2. Выбрать нужные блоки действий, скопировать
3. Открыть новый БП «Со статусами», зайти в нужный статус
4. Вставить скопированные блоки

---

## Статус «Начальный»: что в него помещать

- **Технические действия**: подготовка данных, вычисления начальных значений переменных
- **Уведомления о старте** процесса (если нужны)
- **НЕ** бизнес-логику согласования — её в отдельные статусы

После выполнения начального статуса — передача управления следующему статусу (например, «Утверждение у руководителя»).

---

## Статус «Утверждение у руководителя»

Основная логика согласования:
- Создание задачи руководителю на рассмотрение заявки
- Ожидание решения (одобрить / отклонить / отправить на доработку)
- Передача управления в статус «Одобрена» или «Отклонена» в зависимости от выбора

### Три варианта решения руководителя (расширенный вариант)
Вместо двух вариантов (одобрить/отклонить) можно добавить третий:
```
Одобрить → статус «Одобрена»
Отклонить → статус «Отклонена»
Доработать → статус «Начальный» (или специальный статус доработки)
```
Это реализуется через соответствующий переход к нужному статусу.

---

## Настройка прав доступа

### Отличие от последовательного БП
В БП «Со статусами» **проще задать разные права для разных участников** на разных этапах:
- Каждый статус может иметь **свои права доступа**
- Например: в статусе «Утверждение» только руководитель видит кнопки действий
- В статусе «Одобрена» — только финансовый отдел
- Не нужно городить сложные условия в одном алгоритме

---

## Варианты запуска действий внутри статуса

| Тип запуска | Описание | Типичное применение |
|---|---|---|
| **Вход в статус** | Автоматически при переходе в статус | Основная логика статуса |
| **Выход из статуса** | Автоматически при выходе из статуса | Очистка данных, уведомления о завершении |
| **Вручную** | По кнопке пользователя | Действия по требованию |
| **По таймеру** | Через заданное время или по расписанию | Эскалация, напоминания |

---

## Проверка работы БП

После настройки всех статусов:
1. Сохранить шаблон
2. Запустить БП на тестовом документе/заявке
3. Проверить прохождение по каждому статусу
4. Убедиться, что переходы между статусами работают корректно
5. Проверить, что права доступа работают для каждого участника

---

## Главное

1. **БП «Со статусами» = конечный автомат**: логика разбита на независимые состояния, управление передаётся свободно между ними — это его главное преимущество перед последовательным БП.

2. **Начальный статус — всегда первый**: он запускается автоматически при старте БП, используйте его для технических подготовительных действий, а не для бизнес-логики.

3. **Один статус = один этап согласования**: проектируйте статусы по реальным этапам процесса (начало → согласование → финал), это делает БП понятным и легко поддерживаемым.

4. **Идентификаторы переменных — ключ к переносу**: при создании нового БП «Со статусами» на основе существующего последовательного, используйте **те же коды переменных и констант** — это избавит от необходимости перенастраивать все действия заново.

5. **Обработчик входа — основной инструмент**: из всех вариантов добавления логики в статус чаще всего используйте «Обработчик входа в статус» — он самый понятный и предсказуемый.

6. **Три варианта решения лучше двух**: добавляйте возможность «Доработать» (не только одобрить/отклонить) — это делает согласование гибким и реалистичным.

7. **Права доступа проще, чем в последовательном БП**: каждый статус имеет свои права, поэтому не нужно городить сложные условия — просто назначьте права на уровне статуса.

8. **GoTo — не плохая практика, а инструмент**: в БП «Со статусами» переходы между статусами (аналог GoTo) являются штатным механизмом, не нужно их избегать.

9. **Редактор внутри статуса — тот же, что и в последовательном БП**: все знакомые действия, условия и циклы доступны внутри каждого статуса без переобучения.

10. **Блоки можно копировать между шаблонами**: не нужно настраивать всё с нуля — скопируйте готовые блоки из существующего БП и вставьте в нужный статус нового.
