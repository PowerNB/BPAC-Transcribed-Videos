# Модуль 6, Урок 12: Выбор типа бизнес-процесса — «Со статусами»

## О чём этот урок

Урок посвящён знакомству с типом бизнес-процесса «Со статусами» в Bitrix24 — альтернативой «Последовательному» БП. Разбирается, в каких ситуациях этот тип незаменим, как он устроен концептуально, и как перейти от линейной схемы к схеме с повторяющимися этапами и переходами между ними.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Последовательный БП** | Бизнес-процесс, в котором шаги выполняются строго один за другим, без возможности легко вернуться на предыдущий этап |
| **БП «Со статусами»** | Бизнес-процесс, разделённый на отдельные этапы (статусы/подпроцессы) с настраиваемыми переходами между ними |
| **Статус** (в контексте БП) | Подпроцесс (или несколько подпроцессов) внутри большого бизнес-процесса; не путать со статусом документа или сделки |
| **Переход** | Связь между статусами, определяющая, в какой статус перейдёт процесс после завершения текущего |
| **Начальный статус** | Первый статус, с которого стартует бизнес-процесс |

---

## Когда использовать «Последовательный» vs «Со статусами»

### Последовательный БП — подходит, когда:
- Алгоритм линейный: шаг A → шаг B → шаг C
- Нет этапов, которые нужно проходить повторно
- Схема относительно простая и не разветвлённая

### БП «Со статусами» — подходит, когда:
- Алгоритм **сложный и большой**
- В нём **явно выделяются этапы**, которые могут **повторяться** или проходиться **несколько раз**
- Нужны переходы между этапами в любом направлении (не только вперёд)
- Логику сложно собрать в один линейный поток без нагромождения условий и циклов

> **Ключевое правило:** Если в задаче есть циклы и повторяющиеся этапы — «Со статусами» предпочтительнее.

---

## Разбор примера: Согласование заявки

### Исходный бизнес-процесс (из предыдущих уроков)

Три последовательных этапа:
1. **Сотрудник** подаёт заявку
2. **Руководитель** согласовывает или отправляет на доработку
3. Если сумма > 15 000 → **Бухгалтер** одобряет или отклоняет (при отклонении — завершение БП)

Это работало нормально, пока схема была простой.

---

### Усложнённая постановка задачи

Новые требования меняют логику кардинально:

- Если **бухгалтер отклоняет** заявку → она возвращается **сотруднику на доработку**
- После доработки → снова идёт к **руководителю** на одобрение
- После одобрения руководителем → снова к **бухгалтеру**
- **Руководитель** теперь имеет три варианта решения:
  - Принять заявку
  - Отправить на доработку
  - Отклонить окончательно (если заявка не подходит ни по каким обстоятельствам)

### Почему последовательный БП плохо справляется

- Появляются **дополнительные циклы** и **ветвления**
- «Пазл» из условий и переходов становится сложно собрать и поддерживать
- Схема теряет читаемость и превращается в запутанный граф

## Структура БП «Со статусами»

### Принцип работы

Большой бизнес-процесс делится на **небольшие части (статусы)**, каждая из которых:
- Реализует свою логику независимо
- Может быть пройдена **несколько раз**
- Соединена с другими статусами через **переходы**

### Три естественных статуса в примере

Из постановки задачи сразу видны три блока, каждый из которых может выполняться многократно:

1. **Утверждение руководителя** — руководитель принимает решение (одобрить / доработать / отклонить)
2. **Утверждение бухгалтера** — бухгалтер принимает решение (одобрить / отклонить → на доработку)
3. **Доработка заявки сотрудником** — сотрудник вносит правки и отправляет заново

### Схема переходов

```
[Старт]
   ↓
[Утверждение руководителя]
   ├── Одобрить → [Утверждение бухгалтера]
   ├── На доработку → [Доработка сотрудником] → [Утверждение руководителя]
   └── Отклонить → [Завершение]

[Утверждение бухгалтера]
   ├── Одобрить → [Завершение / Успех]
   └── Отклонить → [Доработка сотрудником] → [Утверждение руководителя]
```

## Что будет реализовано в модуле (план урока)

### 1. Создание статусов
- Определить количество нужных статусов
- Создать их в конструкторе
- Задать переменные и константы

### 2. Реализация начального статуса
- Перенос ранее настроенных действий из последовательного шаблона
- Как скопировать блоки из одного шаблона в другой (облегчает доработку)

### 3. Реализация статусов
- Утверждение у руководителя
- Доработка вариантов «Одобрена» и «Отклонена»

### 4. Настройка прав
- В БП «Со статусами» проще задать **разные права для разных участников**
- Это отличие от последовательного БП

### 5. Проверка работы
- Запуск и тестирование готового БП

### 6. Расширение вариантов выбора для руководителя
- Добавление третьего варианта: «Одобрить» / «Доработать» / «Отклонить»

### 7. Варианты запуска статусов
- Вход в статус и выход из него
- Запуск **вручную**
- Запуск **по таймеру**

## Пошаговые инструкции

> Подробные шаги по созданию БП «Со статусами» будут раскрыты в следующих уроках модуля. Данный урок является вводным и концептуальным.

### Общий алгоритм создания БП «Со статусами»

1. **Проанализировать задачу** — выделить этапы, которые могут повторяться
2. **Определить количество статусов** — каждый повторяющийся блок = отдельный статус
3. **Создать шаблон** типа «Со статусами» в Bitrix24
4. **Создать статусы** и дать им понятные имена
5. **Задать переменные и константы**, нужные для работы статусов
6. **Реализовать логику каждого статуса** (добавить действия внутри каждого)
7. **Настроить переходы** между статусами
8. **Настроить права** участников
9. **Протестировать** работу

## Главное

1. **Два типа БП в Bitrix24**: Последовательный и Со статусами — выбор зависит от сложности задачи.

2. **Статус ≠ статус документа**: В контексте БП «статус» — это подпроцесс (этап) с собственной логикой, а не просто метка на документе.

3. **Критерий выбора «Со статусами»**: Если в бизнес-процессе есть этапы, которые повторяются (циклы согласования, возврат на доработку) — этот тип предпочтительнее.

4. **Главное преимущество**: Сложная схема разбивается на небольшие независимые блоки, каждый из которых проще реализовать и понять.

5. **Переходы — ключевой элемент**: Именно переходы между статусами формируют логику всего процесса, заменяя громоздкие условия и циклы в последовательном БП.

6. **Права настраиваются проще**: В БП «Со статусами» удобнее разграничить права разных участников для разных этапов процесса.

7. **Статусы можно проходить многократно**: В отличие от шагов последовательного БП, статус можно посещать снова — это и есть решение проблемы циклических согласований.

8. **Перенос блоков между шаблонами**: Bitrix24 позволяет копировать настроенные блоки из одного шаблона в другой — это экономит время при доработке.

9. **Три типа запуска статуса**: вручную, по входу/выходу из статуса, по таймеру — это даёт гибкость в автоматизации.

10. **Практический вывод**: Если схема «Последовательного» БП превращается в нечитаемый граф с многочисленными условиями — пора переходить на «Со статусами».
