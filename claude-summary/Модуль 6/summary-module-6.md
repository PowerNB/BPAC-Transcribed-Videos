# Модуль 6: Автоматизация бизнес-процессов — Бизнес-процессы «Со статусами»

## О чём этот модуль

Модуль посвящён освоению бизнес-процессов типа **«Со статусами»** в Bitrix24 — мощной альтернативы последовательным БП для автоматизации сложных многоэтапных согласований. На протяжении восьми уроков слушатели проходят путь от теоретического выбора типа БП до полноценной практической реализации: создают статусы, переносят настроенные блоки, управляют правами доступа, расширяют логику ветвления и тестируют готовый процесс. Сквозной пример — согласование заявки сотрудника через руководителя и бухгалтера с возможностью возвратов на доработку и безусловного отклонения.

---

## Блок 1. Концептуальный выбор: когда нужен БП «Со статусами»

### Два типа БП в Bitrix24

| Тип | Когда подходит |
|---|---|
| **Последовательный** | Линейная схема без повторяющихся этапов, простая логика |
| **«Со статусами»** | Сложная схема с циклами, возвратами, несколькими исходами |

### Критерий выбора

Если в процессе есть **повторяющиеся этапы** (циклы согласования, возврат на доработку) или схема «Последовательного» БП превращается в нечитаемый граф из условий — это сигнал переходить на «Со статусами».

### Ключевые преимущества «Со статусами»

- Логика разбита на **независимые состояния** (статусы) — каждое проще реализовать и поддерживать
- Управление передаётся **в любом направлении** между статусами (аналог легального GoTo)
- Статусы можно **посещать многократно** — это решает проблему циклических согласований
- Права участников настраиваются **отдельно для каждого этапа**

> ⚠️ **Важно:** «Статус» в контексте БП — это подпроцесс (этап) с собственной логикой, а не метка на документе или сделке.

## Блок 2. Проектирование архитектуры: статусы и переходы

### Принцип декомпозиции

Каждый логический этап согласования = **отдельный статус**. Типовой набор для согласования заявки:

```
[Начальный] → [Утверждение руководителем] → [Утверждение бухгалтером]
                    ↕                              ↕
              [Доработка сотрудником] ←────────────┘
                    ↓
              [Одобрена] / [Отклонена]
```

### Роль каждого статуса

| Статус | Назначение |
|---|---|
| **Начальный** | Технические подготовительные действия: определение участников, установка переменных, смена статуса документа |
| **Утверждение руководителем** | Уведомление → решение руководителя → переход по результату |
| **Утверждение бухгалтером** | Уведомление → решение бухгалтера → переход по результату |
| **Доработка сотрудником** | Возврат к инициатору, внесение правок, повторная отправка |
| **Одобрена / Отклонена** | Финальные статусы: запись результата, смена статуса документа, автозавершение БП |

### Ключевое правило начального статуса

В начальном статусе — **только технические действия**, бизнес-логика согласования выносится в отдельные статусы. После выполнения — обязательный «Переход в статус» к следующему звену.

---

## Блок 3. Практическая реализация: создание и наполнение статусов

### Перенос действий из существующего шаблона

Bitrix24 позволяет **копировать настроенные блоки** между шаблонами, что существенно экономит время при доработке:

1. Сохранить цепочку в **«Блок действий»** → добавить в **«Мои действия»**
2. Перетащить блок в нужный статус нового шаблона
3. **Обязательно проверить** ссылки на переменные результатов действий — их идентификаторы в новом БП меняются

> **Лайфхак:** используйте одинаковые **идентификаторы переменных и констант** в новом шаблоне — тогда большинство настроенных действий переносится без правки.

### Действие «Переход в статус»

- Находится в разделе **«Конструкции»**, доступно **только** в БП «Со статусами»
- Соединяет статусы — без него они существуют изолированно
- Флаг **«Прерывать исполнение текущего статуса»**: включён → немедленная передача управления; выключен → параллельное выполнение
- Автоматически рисует **стрелки** на схеме — инструмент визуального контроля архитектуры

### Принципы наполнения статусов согласования

**Формула каждого статуса:**
> Уведомить участника → получить решение → записать результат → перейти в следующий статус

**Нейтральные уведомления** — обязательны для статусов, достижимых из нескольких мест (например, «Доработка» — и от руководителя, и от бухгалтера).

**Живая лента вместо комментариев** в форме утверждения — открытое обсуждение, доступное всем участникам.

**Автозавершение БП** — специально «завершать» процесс не нужно: когда в текущем статусе выполнены все действия и нет переходов дальше, БП завершается автоматически.

## Блок 4. Расширенная логика: три варианта решения руководителя

### Проблема стандартного действия «Утверждение документа»

Поддерживает ровно **два исхода**: Одобрен / Отклонён. Недостаточно, когда нужен третий вариант — «Доработать».

### Решение: действие «Запрос дополнительной информации»

- Добавляется поле типа **«Список»** с произвольными вариантами
- Поддерживает **любое количество исходов**
- Значение сохраняется в переменную и используется в условиях ветвления

### Логика ветвления трёх вариантов

```
[Запрос: «Что сделать?»]
  ├── Равно «Одобрить»   → Запись в отчёт → переход к бухгалтеру / «Одобрена»
  ├── Равно «Доработать» → Уведомление инициатору → статус «Доработка»
  └── else (иначе)       → Переход в финальный статус «Отклонена»
```

> **Ветка else** для отклонения — не требует отдельного условия, автоматически охватывает все оставшиеся случаи. Это упрощает схему и снижает риск ошибок.

**Принципиальное различие исходов:**
- **«Доработать»** — возврат к инициатору, процесс продолжается
- **«Отклонить»** — немедленное завершение процесса, без права на доработку

## Блок 5. Управление правами доступа

### Два способа задать права

| Способ | Для какого типа БП | Особенности |
|---|---|---|
| Действие «Установка прав» в цепочке | Последовательный БП | Права срабатывают при выполнении действия |
| **Настройки статуса** *(рекомендуемый)* | БП «Со статусами» | Права встроены в статус, применяются автоматически при входе |

### Ключевое правило переопределения

При каждом переходе между статусами права **полностью сбрасываются** и заменяются настройками нового статуса. Если в новом статусе права не настроены — документ может стать **невидимым** для участников.

### Практические рекомендации

- Настраивать права **в каждом статусе отдельно** — нельзя задать один раз для всего БП
- Минимально необходимое право — **Чтение**, иначе участник не видит заявку
- При миграции с последовательного БП: скопировать значения из действия «Установка прав» → перенести в настройки статуса
- Форма прав в настройках статуса **идентична** форме действия — переучиваться не нужно

## Блок 6. Типы запуска подпроцессов внутри статуса

### Четыре типа запуска

| Тип | Момент запуска | Кол-во | Применение |
|---|---|---|---|
| **Обработчик входа** | Автоматически при переходе в статус | Только 1 | Основная логика — используется чаще всего |
| **Обработчик выхода** | Автоматически при выходе из статуса | Только 1 | Финальные действия: уведомления, очистка данных |
| **Команда** | Вручную пользователем | Неограниченно | Действия по требованию |
| **Таймер** | Через заданное время / по расписанию | Неограниченно | Эскалация, напоминания, дедлайны |

### Важное правило приоритета

Если любой подпроцесс **инициировал переход в другой статус**, остальные подпроцессы текущего статуса **не выполняются**. Исключение — обработчик выхода: он срабатывает **всегда**.

### Комбинирование типов

В одном статусе можно сочетать несколько типов запуска:
> `Вход → Команда → Таймер (напоминание) → Ещё таймер (эскалация) → Выход`

## Блок 7. Тестирование и отладка

### Обязательные сценарии проверки

| Сценарий | Что проверяется |
|---|---|
| «Счастливый путь» | Все одобряют — процесс завершается корректно |
| Отклонение на раннем этапе | Руководитель отклоняет → возврат к инициатору |
| Отклонение на позднем этапе | Бухгалтер отклоняет → возврат к инициатору (не к руководителю) |
| Многократные доработки | Цикл повторяется без зависания |
| Финальное отклонение | «Отклонить» завершает БП немедленно |

### Инструменты отладки

- **Лог бизнес-процесса** — полная история всех событий и переходов с временны́ми метками; главный инструмент при поиске ошибок
- **Живая лента** — точка входа для участников; проверять корректность и полноту уведомлений
- Тестирование **под разными учётными записями** — каждый участник должен видеть именно то, что ему предназначено

### Связь с остальными блоками

Тестирование подтверждает корректность всех предыдущих решений: архитектуры статусов, настройки переходов, прав доступа и логики ветвления.

## Ключевые выводы модуля

1. **Выбор типа БП определяет всё:** если в процессе есть повторяющиеся этапы или возвраты — «Со статусами» предпочтительнее последовательного БП; усложнение последовательного превращает его в неподдерживаемый граф.

2. **Один статус — одна ответственность:** каждый статус решает одну конкретную задачу (уведомить → получить решение → записать → передать дальше), что делает БП понятным и легко поддерживаемым.

3. **Статусы можно проходить многократно:** это штатное поведение, именно оно решает проблему циклических согласований — возврат на доработку реализуется простым переходом в нужный статус.

4. **«Переход в статус» — связующее звено всей архитектуры:** без него статусы существуют изолированно; именно это действие формирует нелинейную маршрутизацию и отображает схему визуально.

5. **Права переопределяются при каждом переходе:** настраивать права нужно в каждом статусе отдельно — если хотя бы один статус пропущен, участники могут потерять доступ к документу.

6. **Перенос блоков между шаблонами экономит время:** совпадение идентификаторов переменных и констант позволяет копировать настроенные действия без повторной ручной настройки.

7. **«Запрос дополнительной информации» с полем «Список» снимает ограничение двух исходов:** это универсальный инструмент для любого количества вариантов решения участника; ветка else упрощает схему для «крайнего» варианта.

8. **Обработчик входа в статус — основной рабочий инструмент:** покрывает большинство сценариев; таймер незаменим для эскалаций и дедлайнов; обработчик выхода гарантированно срабатывает при покидании статуса.

9. **Живая лента предпочтительнее комментариев в форме утверждения:** обсуждение открыто всем участникам, сохраняет контекст и не изолирует переписку внутри одной задачи.

10. **Автозавершение БП — встроенный механизм:** специально «завершать» процесс не нужно — БП завершается сам, когда в финальном статусе нет переходов дальше.

11. **Нейтральные уведомления — обязательный принцип** для статусов, достижимых из нескольких мест: текст не должен содержать конкретного отправителя, детали — в живой ленте.

12. **«Отклонить» ≠ «Доработать»:** отклонение немедленно завершает процесс без права на исправление, доработка возвращает документ к инициатору — это принципиально разные исходы с разной бизнес-логикой.

13. **Лог БП — первый инструмент при отладке:** полная хронология событий с временны́ми метками позволяет найти любую ошибку маршрутизации или настройки прав.

14. **БП «Со статусами» — универсальный инструмент согласований** на портале Bitrix24: закупки, командировки, отпуска, договоры — любой многоэтапный процесс с возвратами реализуется именно через этот тип.

15. **Тестирование всех веток обязательно:** перед вводом в эксплуатацию необходимо вручную пройти каждый сценарий — «счастливый путь», отклонения на каждом этапе, многократные доработки и финальное отклонение.
