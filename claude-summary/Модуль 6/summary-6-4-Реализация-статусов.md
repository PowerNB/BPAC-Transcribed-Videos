# Модуль 6, Урок 12: Реализация статусов бизнес-процесса «Со статусами»

## О чём этот урок

Урок посвящён практической реализации статусов в бизнес-процессе типа «Со статусами» в Bitrix24.
На примере согласования заявки (с утверждением руководителем и бухгалтером) показывается, как
настраивать каждый статус отдельно: какие действия в него включать, как организовывать переходы
между статусами и как правильно завершать бизнес-процесс.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Статус** | Отдельный этап бизнес-процесса «Со статусами»; содержит свой набор действий и переходы в другие статусы |
| **Переход между статусами** | Связь из одного статуса в другой; создаётся явно в дизайнере и заменяет сложное ветвление внутри одного большого процесса |
| **Действие «Утверждение»** | Блок, в котором участник выбирает исход (одобрить / отклонить / доработать); результат определяет, в какой статус перейдёт процесс |
| **Действие «Уведомление»** | Отправляет сообщение указанным пользователям; используется для оповещения участников о начале их этапа |
| **Действие «Запись в отчёт»** | Фиксирует результат этапа в журнал/отчёт бизнес-процесса |
| **Действие «Изменение документа»** | Обновляет поля документа (заявки); применяется на этапе доработки сотрудником |
| **Живая лента** | Встроенный чат-инструмент Bitrix24; используется для обсуждения вместо поля «Комментарий» в форме утверждения |
| **Переменная** | Временное значение внутри бизнес-процесса; передаётся между статусами |
| **Константа** | Неизменяемое значение, заданное при настройке шаблона (пример: пороговая сумма сделки — 15) |
| **Завершение БП** | Происходит автоматически, когда в текущем статусе нет ни одного перехода в другой статус и все действия выполнены |

---

## Архитектура бизнес-процесса: общая схема статусов

В уроке реализуется согласование заявки со следующими статусами:

```
[Начальный статус]
       │
       ▼
[Утверждение руководителем]
       │
   ┌───┼───────────────┐
   ▼   ▼               ▼
[Доработка  [Утверждение    [Одобрена]
сотрудником] бухгалтером]       │
   │   │         │             ▼
   │   │     ┌───┴───┐    [Завершение]
   │   │     ▼       ▼
   │   │ [Одобрена] [Отклонена]
   │   │     │           │
   │   └─────┘       [Завершение]
   │
   ├──► [Назад к руководителю]
   │
   └──► [Отклонена] ──► [Завершение]
```

**Ключевая идея:** каждый этап согласования — отдельный, небольшой и простой статус.
Переходы между ними создаются явными связями в дизайнере, а не усложнением логики внутри одного
монолитного процесса.

---

## Статус «Утверждение руководителем»

### Что входит в этот статус

1. **Уведомление** — отправляется руководителю (юзербосс) о новой заявке на согласование.
   - Отправитель: пользователь (сотрудник).
   - Получатель: руководитель (юзербосс).
   - Текст уведомления — нейтральный: подходит и для первичного согласования, и для повторного
     после доработки.

2. **Утверждение** — блок выбора решения руководителем.
   - Комментарии в форме утверждения **отключены** — обсуждение ведётся в **живой ленте**.

3. **Условие по сумме сделки** — разветвление после решения «Одобрено»:
   - Если сумма > 15 → переход в статус **«Утверждение бухгалтером»**.
   - Если сумма ≤ 15 → переход в статус **«Одобрена»** (процесс завершается успехом).

4. **Запись в отчёт** — фиксирует факт одобрения руководителем.

### Переходы из этого статуса

| Исход | Следующий статус |
|---|---|
| Одобрено + сумма > 15 | Утверждение бухгалтером |
| Одобрено + сумма ≤ 15 | Одобрена |
| Отклонено | Отклонена |
| На доработку | Доработка сотрудником |

### Что убрано из этого статуса (перенесено)

- Блок утверждения бухгалтером → вынесен в отдельный статус.
- Уведомления об итоге → вынесены в статусы «Одобрена» / «Отклонена».
- Логика доработки → вынесена в статус «Доработка сотрудником».

---

## Статус «Утверждение бухгалтером»

### Что входит в этот статус

1. **Уведомление** — бухгалтеру о новом задании.
   - Настройки те же, что и в уведомлении руководителю.
   - Комментарии **отключены** — обсуждение в живой ленте.

2. **Утверждение** — блок выбора решения бухгалтером (одобрить / отклонить).

3. **Запись в отчёт** — отдельная строка для каждого исхода:
   - «Бухгалтер утвердил»
   - «Бухгалтер отклонил»

### Переходы из этого статуса

| Исход | Следующий статус |
|---|---|
| Одобрено | Одобрена |
| Отклонено | Отклонена |

### Особенности

- Переменные из предыдущих статусов **не нужны** — данные берутся напрямую из документа.
- Статус намеренно простой: уведомление → утверждение → запись → переход.

---

## Статус «Доработка сотрудником»

### Что входит в этот статус

1. **Уведомление** — сотруднику о необходимости доработки.
   - Отправитель: пользователь (не персонализировано — может быть и от руководителя, и от бухгалтера).
   - Текст — нейтральный, без указания конкретного отправителя.
   - Комментарий от конкретного руководителя/бухгалтера **не указывается** — используется
     **живая лента** для обсуждения деталей.

2. **Изменение документа** — сотрудник вносит правки в поля заявки.
   - Кто заполняет: сотрудник.
   - Поля — те же самые, что настраивались ранее (коды полей не изменились → настройка
     действия работает без изменений).
   - Комментарии убраны → обсуждение через живую ленту.

3. **Запись в отчёт** (в ветке отклонения) — фиксирует, что сотрудник отказался дорабатывать.

### Переходы из этого статуса

| Исход | Следующий статус |
|---|---|
| Доработка выполнена | Утверждение руководителем (возврат) |
| Сотрудник отказался дорабатывать | Отклонена |

> **Важно:** раньше для выхода из цикла использовалось «прерывание процесса». Теперь достаточно
> перейти в статус «Отклонена» — это чище и понятнее.

---

## Статусы «Одобрена» и «Отклонена»

Оба статуса технически простые — финальные узлы процесса.

### Состав каждого статуса

1. **Запись в журнал/отчёт** — фиксирует итоговый результат.
2. **Установка статуса документа** — меняет поле статуса в самой заявке (CRM/списке).

> **Ключевое правило завершения БП:**
> Действие «Установка статуса бизнес-процесса» (переброс в другой статус) **не используется**.
> Бизнес-процесс завершается **автоматически**, когда в текущем статусе выполнены все действия
> и нет ни одного перехода в другой статус.

---

## Пошаговые инструкции

### Как настроить статус «Утверждение руководителем»

1. Открыть дизайнер шаблона → выбрать статус «Утверждение руководителем».
2. Добавить действие **«Уведомление»**:
   - Отправитель: `{=Variable:User}` (пользователь).
   - Получатель: `{=Variable:UserBoss}` (руководитель).
   - Текст: нейтральная формулировка (подходит и для первого запроса, и для повторного).
3. Добавить действие **«Утверждение»**:
   - Снять галочку «Разрешить комментарии» → обсуждение переносится в живую ленту.
4. Добавить **«Условие»** после ветки «Одобрено»:
   - Поле: `Сумма сделки` (поле документа).
   - Оператор: `> 15`.
   - Ветка «Да» → установить переход в статус **«Утверждение бухгалтером»**.
   - Ветка «Нет» → установить переход в статус **«Одобрена»**.
5. В ветке «Одобрено» добавить **«Запись в отчёт»**.
6. Настроить переходы для веток «Отклонено» и «На доработку».
7. Сохранить статус.

### Как настроить статус «Доработка сотрудником»

1. Открыть статус «Доработка сотрудником» в дизайнере.
2. Добавить **«Уведомление»** сотруднику:
   - Отправитель: `{=Variable:User}` — нейтрально, без персонализации.
   - Убрать упоминание конкретного руководителя из текста.
3. Добавить действие **«Изменение документа»**:
   - Исполнитель: сотрудник.
   - Убрать поле «Комментарий» (заменено живой лентой).
   - Остальные поля — без изменений (коды совпадают с ранее настроенными).
4. Настроить переходы:
   - После выполнения доработки → переход в **«Утверждение руководителем»**.
   - В ветке отклонения → переход в **«Отклонена»** + запись в отчёт.
5. Сохранить.

### Как настроить финальные статусы «Одобрена» / «Отклонена»

1. Открыть статус «Одобрена».
2. Добавить **«Запись в журнал»** с результатом.
3. Добавить **«Установку статуса документа»** (поле статуса в заявке).
4. **Не добавлять** действие перехода в другой статус БП — процесс завершится сам.
5. Сохранить.
6. Повторить аналогично для статуса «Отклонена».

---

## Архитектурные принципы, показанные в уроке

### Принцип «один статус — одна ответственность»

Каждый статус решает одну конкретную задачу:
- Уведомить участника.
- Получить его решение.
- Записать результат.
- Перейти дальше.

Не нужно «пихать» всю логику в один большой блок.

### Принцип нейтральных уведомлений

Если один и тот же статус может быть достигнут из разных мест (например, доработка — и от
руководителя, и от бухгалтера), уведомление делается **нейтральным**: без указания конкретного
отправителя. Детали — в живой ленте.

### Живая лента вместо комментариев

Комментарии в форме утверждения — закрытое поле. Живая лента — открытое обсуждение, доступное
всем участникам. Для согласований предпочтительнее живая лента.

### Автоматическое завершение БП

Специально «завершать» процесс не нужно. Как только в текущем статусе:
- Выполнены все действия, И
- Нет ни одного перехода в другой статус —

бизнес-процесс завершается **автоматически**.

---

## Главное

1. **Статус «Со статусами» — это не монолит.** Каждый этап согласования — отдельный маленький
   процесс. Это делает схему читаемой и легко дорабатываемой.

2. **Переходы между статусами заменяют сложное ветвление.** Вместо вложенных условий внутри
   одного большого процесса — явные стрелки-переходы между статусами в дизайнере.

3. **Условия можно ставить внутри статуса.** Пример: после одобрения руководителем — проверка
   суммы сделки. Если > 15 → к бухгалтеру, если нет → сразу «Одобрена».

4. **Нейтральные уведомления и живая лента** — правило для статусов, в которые можно попасть
   из нескольких мест. Не привязывайте текст к конкретному отправителю.

5. **Действие «Изменение документа» не требует перенастройки**, если коды полей не изменились —
   оно работает как есть даже при переносе в другой статус.

6. **Финальные статусы («Одобрена», «Отклонена») не нуждаются в явном завершении.** БП
   завершается сам, когда заканчиваются действия и нет переходов дальше.

7. **Переменные нужны не везде.** В простых статусах (уведомление → утверждение → запись) данные
   берутся напрямую из документа; лишние переменные только усложняют схему.

8. **Сложная схема — не значит сложный код.** На итоговой схеме БП много связей, но каждый
   отдельный статус остаётся простым и понятным.

9. **Доработка сотрудником — отдельный статус** с возможностью либо вернуть заявку руководителю,
   либо самостоятельно отклонить её (переход в «Отклонена»).

10. **Комментарии в форме утверждения лучше отключать** — они изолированы от общего обсуждения.
    Живая лента доступна всем участникам и сохраняет контекст.
