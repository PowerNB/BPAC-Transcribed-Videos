# Дизайнер и действия

## О чём этот урок

Урок посвящён визуальному редактору шаблонов бизнес-процессов (БП) в Bitrix24 — **Дизайнеру**. Рассматриваются структура дизайнера, все доступные блоки действий, их назначение, ключевые возможности и документация к каждому блоку, а также рекомендации по практическому освоению.

---

## Основные понятия

| Термин | Определение |
|---|---|
| **Дизайнер** | Визуальный редактор шаблонов бизнес-процессов |
| **Шаблон БП** | Набор действий, расположенных в рабочей области дизайнера |
| **Действие** | Элементарный шаг (блок) в шаблоне БП |
| **Документ** | Текущий объект (сущность), по которому запущен БП (строка, сделка, задача и т. д.) |
| **Последовательность** | Линейная цепочка шагов без разветвлений |
| **Ветвление (условие)** | Развилка с несколькими путями выполнения в зависимости от данных |
| **Цикл** | Блок, обведённый замкнутыми линиями; повторяется, пока не выполнено условие выхода |

---

## Структура дизайнера БП

- Дизайнер — это **визуальный редактор** шаблонов
- Шаблон строится из **действий**, расположенных в рабочей области
- Справа расположена **панель** со всеми доступными действиями, сгруппированными по блокам

### Визуальные элементы шаблона

- **Последовательность действий** — линейная цепочка шагов
- **Ветвления (условия)** — развилки с несколькими путями выполнения
- **Циклы** — блоки, обведённые замкнутыми линиями; повторяются, пока не выполнено условие выхода

> **Пример из урока:** сложный типовой шаблон содержит многократные условия и циклы — это нормально для реальных процессов.

## Блоки действий в дизайнере

### 1. Обработка документа

**Назначение:** работа с текущим объектом (документом), по которому запущен БП.

**Ключевые возможности:**
- **Изменение документа** — записать значение в поле объекта (например: дата согласования, ответственный руководитель)
- **Запуск бизнес-процесса** — запустить *другой* БП по *любому другому* объекту системы (не только текущему)

> **Пример:** в процессе согласования отпуска «документ» — это строка в таблице отпусков. Действие «Изменить документ» сохраняет в неё поля «Руководитель, согласовавший отпуск» и «Дата согласования».

> **Важно:** действие «Запуск БП» даёт мощные возможности для цепочек автоматизации — один процесс может инициировать другой по совершенно иному объекту.

📎 Документация: https://helpdesk.bitrix24.ru/open/7449433/

---

### 2. Задания

**Назначение:** интерактив с пользователем — создание интерфейса для принятия решений.

**Что видит пользователь:**
- «Вам необходимо согласовать»
- «Вам необходимо утвердить / одобрить»

**Принцип работы:** задания создают **диалог между процессом и человеком** — процесс ждёт ответа пользователя, прежде чем двигаться дальше.

> **Ключевое отличие от «Уведомлений»:** задания — двусторонний диалог с ожиданием действия пользователя; уведомления — одностороннее информирование.

📎 Документация: https://helpdesk.bitrix24.ru/open/7451037/

---

### 3. Конструкции

**Назначение:** управляющие структуры, задающие логику выполнения процесса.

**Включают:**
- **Условия / ветвления** — выбор пути в зависимости от данных
- **Циклы** — повторение блока действий
- **Более сложные конструкции** — описаны в документации

📎 Документация: https://helpdesk.bitrix24.ru/open/7453445/

---

### 4. Уведомления

**Назначение:** коммуникация с пользователями без ожидания их ответа.

**Варианты уведомлений:**
- Отправить **сообщение в чат**
- Написать в **живую ленту**
- Поставить **задачу** *(логически ближе к блоку «Задания», но находится здесь)*

> **Разница от блока «Задания»:** уведомления — одностороннее информирование; задания — двусторонний диалог с ожиданием действия пользователя.

📎 Документация: https://helpdesk.bitrix24.ru/open/7471547/

---

### 5. Действия приложений

**Назначение:** кастомные (нестандартные) действия, добавляемые через приложения Bitrix24.

**Когда использовать:**
- Стандартных блоков недостаточно для реализации логики
- Нужна специфическая интеграция или функциональность

**Как добавить кастомное действие:**
1. Написать код действия *(требуются компетенции программиста)*
2. Обернуть в приложение для Bitrix24
3. Загрузить приложение на портал
4. Действие появится в этом блоке дизайнера

> **Важно:** работает в том числе в **облачном** Bitrix24.

---

### 6. CRM

**Назначение:** работа с объектами CRM-системы.

**Возможности:**
- **Создание объектов:** контакты, лиды, компании, сделки
- **Получение данных** из CRM
- **Выбор данных в CRM** — особенно полезное действие для поиска и фильтрации

📎 Документация: https://helpdesk.bitrix24.ru/open/7567357/

---

### 7. Диск

**Назначение:** работа с файлами и папками на Диске Bitrix24.

**Операции:** создание, копирование, перемещение файлов.

📎 Документация: https://helpdesk.bitrix24.ru/open/7544195/

---

### 8. Прочее

**Назначение:** полезные действия, не вошедшие в другие блоки.

**Ключевые действия:**

| Действие | Описание |
|---|---|
| **Выбор сотрудника** | Определяет конкретного пользователя: руководителя, участника группы, кого-то из заранее известного списка |
| **Прерывание процесса** | Останавливает выполнение БП при наступлении условия *(логически близко к конструкциям, но находится здесь)* |
| **Веб-хук** | Вызывает внешний URL с передачей данных через параметры — простой способ интеграции с внешними системами |

> **Пример использования веб-хука:** в нужный момент БП отправляет HTTP-запрос во внешнюю CRM, ERP или мессенджер, передавая данные (ID сделки, сумму, ответственного и т. д.) через параметры URL.

📎 Документация: https://helpdesk.bitrix24.ru/open/7557393/

## Пошаговые инструкции

### Как добавить кастомное действие через приложение

1. Написать код действия *(требуются компетенции программиста)*
2. Обернуть написанный код в приложение для Bitrix24
3. Загрузить приложение на портал Bitrix24
4. Перейти в Дизайнер БП → убедиться, что новое действие появилось в блоке **«Действия приложений»**

---

### Рекомендуемый порядок практического освоения дизайнера

1. Найти **типовой (стандартный) шаблон** БП в системе
2. Изучить его структуру — какие блоки использованы, как они связаны между собой
3. Внести **небольшое изменение** (модифицировать параметр действия, добавить уведомление)
4. Запустить БП и **проверить результат**

> **Почему так:** типовые шаблоны содержат проверенную логику — это безопаснее и быстрее, чем создавать процесс с нуля.

## Главное

1. **Дизайнер — визуальный редактор**, в котором шаблон БП строится из действий; справа — панель с блоками, сгруппированными по категориям.
2. **Документ = текущий объект БП.** Всё, что делает блок «Обработка документа», применяется именно к той сущности (строке, сделке, задаче), по которой запущен процесс.
3. **Блок «Задания» = диалог с человеком.** Когда нужно, чтобы пользователь что-то подтвердил или выбрал — это «Задания», а не «Уведомления». Уведомления — одностороннее информирование.
4. **«Запуск БП» — инструмент цепочек автоматизации.** Один процесс может запустить другой по любому объекту системы — открывает возможности для сложных сценариев.
5. **Конструкции управляют логикой процесса:** ветвления (IF/ELSE), циклы и параллельные блоки — всё это находится в блоке «Конструкции».
6. **Кастомные действия реальны даже в облаке.** Если стандартных блоков не хватает, можно написать приложение и добавить своё действие в дизайнер через блок «Действия приложений».
7. **Веб-хук — быстрая интеграция без разработки API.** Для простой передачи данных во внешнюю систему достаточно одного действия «Веб-хук» без написания серверного кода.
8. **CRM-блок позволяет создавать и получать объекты** (лиды, сделки, контакты, компании) прямо внутри БП.
9. **Изучить документацию по каждой категории — обязательно** перед самостоятельной разработкой; все ссылки структурированы по блокам.
10. **Начинать лучше с изменения типового БП**, а не с создания с нуля — это быстрее даёт понимание структуры и снижает риск ошибок.
